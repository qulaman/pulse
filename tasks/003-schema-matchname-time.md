## Шаги
1. `lib/ai/schema.ts` — **источник правды в виде zod** (zod уже установлен): `z.strictObject` для каждого вида сущности, `z.discriminatedUnion('kind', [...])` из семи видов, `ParseResultSchema = z.strictObject({ entities: z.array(EntitySchema) })`. Поля и типы — ровно как в AI.md §3 (включая `group_id`, `deadline_confidence: number|null`, `scheduled_send_at`, `question` у query, `note` у delegation). Nullable — через `.nullable()` (без `.optional()`: в structured outputs все поля обязательны). Экспортировать TS-типы через `z.infer` под теми же именами, что в AI.md (`Entity`, `TaskEntity`, `PointsEntity`, …, `ParseResult`, `Priority`). Экспортировать `ENTITIES_JSON_SCHEMA` = JSON Schema, полученная из `ParseResultSchema` через `z.toJSONSchema` (zod v4); если в результате не у каждого объекта стоит `additionalProperties: false` или nullable выражен не через `anyOf [type, null]` — добавить детерминированную пост-обработку (обход дерева), а не править схему руками. Тест `lib/ai/schema.test.ts`: (а) все объекты в `ENTITIES_JSON_SCHEMA` имеют `additionalProperties:false` и `required` = все ключи `properties`; (б) нигде нет `type: [..., "null"]` (только `anyOf`) — это ограничение валидатора Anthropic, подтверждено прототипом; (в) пример TaskEntity с `deadline_iso: null` проходит `ParseResultSchema.parse`; (г) объект с лишним полем — не проходит.
2. `lib/ai/config.ts` — `MatchingConfig = { autoThreshold: 0.45, minGap: 0.15, ambiguousThreshold: 0.30, modelConfidenceYellow: 0.8 }` (дефолты из AI.md §5), функция `resolveMatchingConfig(overrides?: Partial<MatchingConfig>)` — для будущего `company.settings.matching`. Никаких других настроек.
3. `lib/matchName.ts` — `type RosterUser = { id: string; full_name: string; aliases: string[]; is_active: boolean }`; `type AssigneeMatch = { status: 'matched' | 'ambiguous' | 'unmatched'; user_id: string | null; candidates: { user_id: string; full_name: string; score: number }[]; flag: 'ok' | 'check' }`. Функция `matchName(input: { assignee_id: string | null; assignee_queries: string[]; assignee_confidence: number }, roster: RosterUser[], cfg = resolveMatchingConfig()): AssigneeMatch` по шагам AI.md §5: (1) валидный и активный `assignee_id` → `matched` (flag `check`, если `assignee_confidence < cfg.modelConfidenceYellow`); (2) иначе fuzzy по `assignee_queries[0]`: нормализация + стем (из `lib/text/normalize.ts`), триграммное сходство (реализовать `trigramSimilarity(a,b)` в этом же файле: коэффициент Дайса по мультимножеству триграмм строки с пробелами по краям) против каждого surface (full_name + aliases, тоже нормализованных и стемированных по словам); score пользователя = max по surfaces; (3) пороги из cfg: лучший `≥ autoThreshold` и отрыв от второго `≥ minGap` → `matched` + flag `check`; лучший `≥ ambiguousThreshold` (или два близких выше auto) → `ambiguous` с 2–3 кандидатами; иначе `unmatched`. Неактивные пользователи из кандидатов исключаются всегда. Инициал в запросе (токен из 1 буквы, напр. «Б») сравнивается точно с инициалом в surface, не триграммами: совпал — surface подходит, не совпал — surface с инициалом отбрасывается. Тест `lib/matchName.test.ts` на ростере из `tests/stt/roster.json` (загрузить файл, добавить `is_active: true`): «Марату» → u-003 matched; «Ерлану» → ambiguous (u-001 и u-002, не matched!); «Ерлану Б.» → u-001; «Ерлан Д» → u-002; «Ерлан Т.» → НЕ matched ни к кому (ambiguous или unmatched — wrong=0); «Сәкенге» → u-004; «Баке» → u-007; «Алие» → u-008; «Динаре» → u-006; «Жандосу» → u-010; «абракадабра» → unmatched; `assignee_id: 'u-003'` с confidence 0.6 → matched + flag check; `assignee_id: 'u-999'` (нет в ростере) → fuzzy по query; u-003 с `is_active:false` и query «Марат» → unmatched; граничные score вокруг `autoThreshold`/`minGap` при кастомном cfg. Если какой-то кейс из списка не проходит при разумной реализации — НЕ подгонять пороги под тест; записать кейс в отчёт как открытый вопрос и пометить тест `it.todo`.
4. `lib/ai/time.ts` — детерминированные конвенции D-15, без внешних библиотек дат (таймзона Asia/Aqtobe = фиксированный `+05:00`, DST нет): `AQTOBE_OFFSET = '+05:00'`; `resolveConvention(text: string, now: Date): { deadline_iso: string; confidence: number; source_text: string } | null` — распознаёт из таблицы AI.md §2 правило 3: «до обеда», «к обеду», «вечером/к вечеру», «утром», «к концу недели», «на неделе», «к <дню недели>» (7 дней, русские формы «к понедельнику/вторнику/среде/четвергу/пятнице/субботе/воскресенью»), модификаторы «сегодня/завтра/послезавтра» перед конвенцией; ничего не распознано → `null` (никогда не выдумывать). Ближайший день недели — строго после сегодняшнего (если сегодня четверг, «к четвергу» = следующий). Вспомогательные: `toAqtobeIso(date)`, `aqtobeIsoToUtc(iso)`, `formatAqtobe(date)` (`DD.MM.YYYY HH:mm`), `weekdayRu(date)` («четверг»). Тест `lib/ai/time.test.ts`: при `now = 2026-08-13T10:00:00+05:00` (четверг): «завтра до обеда» → `2026-08-14T13:00:00+05:00` conf 0.7; «к вечеру» → сегодня 18:00; «на неделе» → `2026-08-14T18:00:00+05:00` conf 0.5; «к концу недели» → то же conf 0.6; «к понедельнику» → `2026-08-17T09:00:00+05:00`; «к четвергу» из четверга → `2026-08-20T09:00:00+05:00`; «сделай отчёт» → null; переход через полночь: now = 23:30 четверга, «утром» → пятница 09:00; `aqtobeIsoToUtc('2026-08-14T13:00:00+05:00')` → `2026-08-14T08:00:00.000Z`; `weekdayRu(now)` → «четверг».
