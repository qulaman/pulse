## Шаги
1. `supabase init` в корне (config.toml по умолчанию; в `[db]` оставить версию Postgres по умолчанию CLI; `[auth]` не трогать). Скрипты в package.json: `db:start` = `supabase start`, `db:reset` = `supabase db reset`, `test:rls` = `supabase test db`.
2. Миграция `supabase/migrations/20260907120000_foundation.sql` — одна фича «фундамент»: (а) `create extension if not exists moddatetime;` (б) ВСЕ enum-типы из DATABASE.md «Enum-типы» дословно (включая `shop_final` — НЕ создавать, как сказано в доке); (в) `companies` (id, name, settings jsonb default '{}', created_at); (г) `profiles` ровно по доку (id = fk `auth.users` без default, остальные поля/дефолты как в доке); (д) функции `auth_company_id()`, `auth_role()`, `subordinates(mgr uuid)` — дословно из раздела RLS; (е) RLS: `companies` — select членам компании (`id = auth_company_id()`), write — никому (только service role); `profiles` — select вся компания через `company_id = auth_company_id()` (НЕ подзапросом к profiles), update — владелец (`id = auth.uid()`) с запретом менять `role`, `company_id`, `is_active` (реализовать `before update` триггером `trg_profiles_guard`, сравнивающим OLD/NEW при `auth_role() <> 'director'`) + director (`company_id = auth_company_id() and auth_role() = 'director'`); insert/delete — нет политик (service role). (ж) индекс `profiles (company_id)`. Комментарии в SQL — на английском.
3. Миграция `supabase/migrations/20260907120100_tasks_and_messages.sql` — фича «задачи и сообщения»: (а) `tasks` по доку + `moddatetime` на `updated_at`; (б) `task_messages` по доку (`seq bigserial`, `meta jsonb default '{}'`); (в) индексы из раздела «Индексы» для tasks и task_messages (все 6 строк, включая partial); (г) триггер 1 `trg_task_status_guard` (before update of status): матрица BACKEND.md §7 — допустимые переходы: `scheduled→sent` (только когда `auth.uid() is null`, т.е. service role/cron), `sent→accepted` (assignee), `sent→declined`, `accepted→declined` (assignee), `accepted→pending_review` (assignee), `pending_review→done`, `pending_review→rework` (director), `rework→accepted` (assignee), `любой кроме done/declined/revoked → revoked` (director); всё остальное — `raise exception 'invalid_transition'` с `errcode = 'P0001'`; при `auth.uid() is null` (service role) роль не проверять, матрицу — проверять; попутно ставить `accepted_at` (при accepted, если null), `completed_at` (pending_review), `closed_at` (done/declined/revoked). (д) триггер 2 `trg_task_status_message` (after update of status): insert в `task_messages` строки `type='status_change'`, `sender_id = coalesce(auth.uid(), author_id)`, `meta = {old_status, new_status}`. (е) триггер 3 `trg_question_answered` (after insert on task_messages): если отправитель — director этой задачи (`sender_id = tasks.author_id`) и сообщение НЕ вопрос — проставить `meta.answered_at = now()` всем сообщениям этой задачи с `meta.is_question = true` и без `answered_at`. (ж) RLS `tasks`: `tasks_select` и `tasks_insert` — дословно из дока; `tasks_update` — `using` то же условие видимости, что select, плюс `with check (company_id = auth_company_id())` (детали переходов — триггер 1). Delete — только director и только `status='scheduled'`. RLS `task_messages`: select — участники задачи (существует task с этим id, видимая по тем же правилам: assignee/author/director/manager глубины 1); insert — участники, `sender_id = auth.uid()`, `company_id = auth_company_id()`; update/delete — нет политик (append-only; `answered_at` ставит триггер — он должен быть `security definer` или обновлять через функцию с `security definer`, иначе RLS без update-политики заблокирует).
4. `supabase/seed.sql` — только для локальной БД и dev (в prod не катится): компания «Demo Group» (фиксированный uuid, `settings` = `{}` — правила очков появятся в своём наряде); 8 пользователей в `auth.users` (фиксированные uuid, `email` вида `director@demo.local`, `encrypted_password = crypt('demo1234', gen_salt('bf'))`, `email_confirmed_at = now()`, `raw_app_meta_data = '{"provider":"email","providers":["email"]}'`, `aud='authenticated'`, `role='authenticated'`, `instance_id='00000000-0000-0000-0000-000000000000'`) + профили: director «Директор Демо», manager «Динара Ахметова» (u-006), shopkeeper «Тимур Салимов» (u-009), tv «TV Kiosk», employee — «Ерлан Байжанов» (aliases `{Ерлан, "Ерлан Б."}`), «Ерлан Досов» (aliases `{Ерлан, "Ерлан Д."}`), «Марат Оспанов» (aliases `{Марат}`, `manager_id` = Динара), «Айгуль Сапарова» (aliases `{Айгуль}`, `availability='vacation'`) — итого 8 профилей (в доке написано «7», но перечислено 1+1+1+1+4 = 8; верно 8). Задачи: по одной в КАЖДОМ статусе enum (9 штук, автор — director, исполнители — Ерланы/Марат/Айгуль; `scheduled` со `scheduled_send_at` завтра; `done` с `closed_at`; одна просроченная `sent` с `deadline` вчера), одна пара с общим `group_id`, у одной задачи в `sent` — сообщение от исполнителя с `meta = {"is_question": true}`. Вставлять задачи с готовым статусом напрямую (триггер guard срабатывает только на update) — это ок для seed.
5. pgTAP-тесты в `supabase/tests/` (формат `supabase test db`: `begin; select plan(N); … select * from finish(); rollback;`), контекст пользователя через `set local role authenticated; set local request.jwt.claims = '{"sub":"<uuid>","role":"authenticated"}'`: `001_rls_tasks.test.sql` — кейсы 1 (employee читает чужую task → 0 строк), 3 (employee не видит `scheduled` → 0 строк), 4 (manager Динара видит задачу подчинённого Марата), 5 (manager не видит задачу Ерлана — не подчинённый), 7 (anon → 0 строк из tasks и profiles); `002_rls_profiles.test.sql` — employee видит все профили компании; employee update своей `role` → исключение; employee update своего `position` → ок; `003_task_status_guard.test.sql` — assignee: `sent→accepted` ок; assignee `pending_review→done` → исключение `invalid_transition`; director `pending_review→done` → ок и в `task_messages` появилась строка `status_change`; `done→accepted` → исключение; `sent→revoked` director → ок; `004_question_answered.test.sql` — сообщение director в задачу с открытым вопросом проставляет `answered_at`.
