# SETUP.md — среды, переменные, развёртывание, новый клиент

Стенды, переменные, подъём с нуля, секреты, новый клиент, наблюдаемость и бэкапы — для того, кто разворачивает Pulse. Схема базы — `docs/DATABASE.md`, роуты и тик — `docs/BACKEND.md`, проверки — `docs/TESTING.md`.

## Карта

| Что | Где |
|---|---|
| Команды; регион и cron | `package.json`; `vercel.json` |
| Переменные | `lib/env.schema.ts`, `lib/env.public.ts`, `.env.example` |
| Миграции, сид, pgTAP | `supabase/migrations/`, `supabase/seed.sql`, `supabase/tests/` |
| Тик | `app/api/push/sweep/route.ts`, `scripts/dev-tick.ts` |
| Компании и операторы | `/ops`, `scripts/seed-client.ts`, `scripts/ops-grant.ts` |

## Правила

- Схема меняется только новой миграцией с политиками RLS в ней же; старые миграции не правятся.
- Миграция попадает в базу раньше кода, который на неё опирается: стенд собирается из `main` сразу.
- Env один на всех клиентов, отличия компании — в `company.settings` (D-134 п. 4).
- `supabase/seed.sql` — фикстуры разработки, в базу с настоящими клиентами не катится.

## 1. Среды

Есть один проект Supabase (dev, Франкфурт) и один проект Vercel на нём. В этой базе живут все компании, включая пилотную: граница между ними — `company_id` и RLS (D-134). Прод-стенда нет (D-19). Функции стоят в регионе базы, `fra1` (D-126).

Push в `main` — выкатка для всех компаний: Vercel только собирает и разворачивает, CI нет. Деплои веток смотрят в ту же базу. Локальной базы нет: `pnpm dev`, `db:*` и `test:rls` работают со слинкованным dev-проектом, с живыми данными.

Фоновую работу делает роут `/api/push/sweep`; `vercel.json` зовёт его раз в сутки, `0 3 * * *` (08:00 по Актобе): чаще тариф не позволяет. Пуши после действий уходят сразу. Локально минутный тик даёт `pnpm dev:tick`.

Миграция — файл в `supabase/migrations/` с именем из времени UTC (`YYYYMMDDHHMMSS`) и описания. `pnpm db:push` применяет все файлы, которых нет в базе, включая чужие незакоммиченные, — сначала `supabase migration list`. После — `pnpm db:types`.

## 2. Переменные окружения

Шаблон — `.env.example`, значения — `.env.local` (вне git) и env Vercel. Серверные проверяет `lib/env.schema.ts` при первом `getServerEnv()`, публичные — `lib/env.public.ts`. Новая переменная вносится в шаблон и схему.

| Переменная | Для чего | Где | Без неё |
|---|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` | база | всюду | не стартует |
| `SUPABASE_SERVICE_ROLE_KEY` | обход RLS; из него выводятся ключи кодов входа и прогонов корпуса | сервер, скрипты | падают сервисные роуты |
| `OPENAI_API_KEY` | STT `openai`, `whisper1` | сервер | нет STT и пушей |
| `ANTHROPIC_API_KEY` | парсер на Claude, `eval:parser` | сервер | нет разбора на Claude и пушей |
| `DEEPSEEK_API_KEY`, `DEEPGRAM_API_KEY`, `ELEVENLABS_API_KEY` | парсер `deepseek-*`, STT `deepgram`, `elevenlabs` | сервер | нет этих провайдеров |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` | Web Push | браузер, сервер | пуши не уходят |
| `CRON_SECRET` | Bearer тика | сервер, `dev:tick` | тик — 401 |
| `LOGIN_CODE_SECRET` | ключ кодов входа (D-135), в шаблоне нет | сервер | берётся из сервисного ключа |
| `OPS_HOST`, `OPS_APP_ORIGIN` | свой хост `/ops` (D-157) | сервер | консоль на любом хосте |
| `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD` | Supabase CLI, `smoke:ops` | скрипты | `supabase login` |
| `PARSER_MODEL`, `PARSER_ESCALATION_MODEL` | модели `eval:parser` | evals | Haiku и Sonnet |

Приложение берёт STT и модели из `settings.stt` и `settings.parser` компании. Не используются: `STT_PROVIDER`, `STT_FALLBACK_PROVIDER`, `QUERY_MODEL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `INTERNAL_FN_SECRET`, `SENTRY_DSN`, `NEXT_PUBLIC_SENTRY_DSN`.

Подписка на пуши привязана к публичному ключу VAPID, поэтому всё, что шлёт пуши из одной базы (и локальный `next dev`), держит одну пару. Новая пара обрывает доставку, пока приложение не подпишется заново при открытии (D-125).

## 3. С нуля

Нужны Node 20+, pnpm и Supabase CLI.

1. `pnpm install`, `.env.example` скопировать в `.env.local`.
2. Проект Supabase во Франкфурте с асимметричным ключом JWT: с ним `getClaims()` проверяет сессию без похода в Auth (`lib/auth.ts`). `supabase link --project-ref <ref>`.
3. На пустом проекте `pnpm db:reset` (стирает базу): миграции, бакеты, сид — демо-компания, учётки, pgTAP. Без сида — `pnpm db:push`.
4. `npx web-push generate-vapid-keys`, пару — в env.
5. Vercel: репозиторий и env из §2; регион и cron — из `vercel.json`.
6. Оператор консоли: `pnpm ops:grant <email>` печатает пароль один раз, аутентификатор подключается при первом входе на `/ops/login` (ещё `--revoke`, `--reset-mfa`, `--reset-password`). Затем первая компания (§5).
7. На телефоне: вход директора, тестовый пуш на заблокированный экран, фраза голосом до карточки сотрудника.

Локально: `pnpm dev` и `pnpm dev:tick`, с телефона в той же сети — `pnpm dev:https`. `pnpm db:clean` стирает активность и смоук-логины, оставляя людей и настройки, и работает только с dev-проектом.

## 4. Секреты

- Только env Vercel и `.env.local`: не код, коммиты, логи, `ai_logs`, бандл. `NEXT_PUBLIC_*` — только публичное. Модули с ключами помечены `import "server-only"`: импорт в клиентский код ломает сборку. Роуты логируют текст ошибки без тела запроса (`lib/api/handler.ts`).
- Утечка: отозвать и перевыпустить ключ, обновить env, передеплоить, проверить журнал провайдера, записать инцидент в `DECISIONS.md`. Ключ, побывавший в git, утёк навсегда: репозиторий публичный.
- Уходит разработчик: `pnpm ops:grant <email> --revoke`, затем GitHub, Supabase, Vercel и смена виденных им ключей.

## 5. Новый клиент (D-134)

Клиент — строки в общей базе. Отдельный инстанс (D-134 п. 2) — свои проекты Supabase и Vercel с тем же кодом, §3 против них, своя пара VAPID.

Консоль, `/ops/new` (D-157): название, адрес `/c/<slug>`, провайдер парсера, очки, директор. Сервер заводит компанию, директора, ТВ-киоск и стартовую витрину и выдаёт директору код входа. Людей добавляют директор и секретарь в приложении или оператор в карточке компании.

Анкета для компании со списком людей: `pnpm seed:client <анкета.json> [--dry-run] [--undo]`, образец — `scripts/client.example.json`, база — из `.env.local`. Повтор безопасен (учётки — по почте, компания — по имени), алиасы скрипт подсказывает сам (D-54), пароли генерирует и печатает один раз; секретаря назначают в приложении.

Перед передачей: директор вошёл с телефона, получил тестовый пуш, стена подключена, настройки совпадают с договорённым.

## 6. Наблюдаемость

- Логи Vercel: ошибки роутов и тика.
- `/api/health` — жив ли деплой; `/api/version` — номер сборки для телефона (D-115).
- `ai_logs`: каждый вызов STT и парсера; цены — в «Лаборатории» (`/lab`); `pnpm eval:harvest` — доля правок директора по дням (D-35).
- Реестр `/ops`: по компании — активные, ошибки разбора, очередь пушей, неудачные доставки, расход на модели.
- `push_health()` на экранах команды и пуш директору «Уведомления не доходят» (D-114).

## 7. Бэкапы

Своих бэкапов, PITR и проверенного восстановления нет — только то, что даёт тариф Supabase. Файлы Storage в дамп базы не входят. Консоль выгружает одну компанию (таблицы, файлы, манифест с SHA-256) в папку оператора; обратной загрузки нет. Голосовые файлы удаляются по `settings.voice_retention` (D-155 §3).

## Не построено

- Прод-стенд и CI (D-19).
- Минутный тик на стенде (В-8).
- Telegram-ярус и Edge Functions (D-21, G.20c).
- Мониторинг и оповещения об ошибках.

## Известные ограничения

- Продукт рассчитан на минутный тик, стенд тикает раз в сутки: отложенные задачи, напоминания, сигналы директору, ежедневный отчёт и повторы ждут 08:00.
- Отправка пушей проверяет всю серверную схему (`lib/push/send.ts`): без ключей OpenAI и Anthropic пуши не уходят.
- `seed:client` не доведён до общей базы (D-134 п. 6): при другой компании в базе требует `SEED_CLIENT_ALLOW_MULTI=1`, а `--undo` удаляет все компании с именем из анкеты.
- `db:clean` чистит все компании базы, `db:reset` стирает её целиком — пилот живёт там же.
