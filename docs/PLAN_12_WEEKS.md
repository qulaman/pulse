# План на 12 недель — WAG Pulse: от нуля до работающей системы в WAG

Цель 12 недель: продукт ежедневно используется всей компанией WAG, директор проводит через него все поручения, есть метрики для инвестора и материал для первого внешнего демо.

Сетка свёрстана под решение **D-40(в)**: MVP-ядро — 4 недели, пилот недель 5–6 идёт на голом ядре **без очков, рейтинга, магазина, ТВ и game feel**; они включаются по гейту адаптации недели 8. Арбитр спорных мест — `DECISIONS.md`. Значок ⏳ — зависимость от владельца/директора: без этого действия неделя буксует.

**⏳ Открытые действия владельца (следить с недели 1):** D-25 — дата старта (понедельник недели 1); D-26 — модель телефона директора + закупка тестовых Redmi/iPhone; D-42 — гарнитура директору до СТТ-гейта; D-23 — опрос парка устройств; D-22 — состав пилотной пятёрки; D-20 — имя и домен до недели 5; D-24 — hex фирменного цвета; D-13 — виза на товары/цены магазина (к неделе 10).

Реальная ёмкость: ~6–6.5 часов глубокой работы в день × 6 дней = 36–39 часов в неделю чистой разработки. Это много при работе с Claude Code, но план ниже свёрстан под эту ёмкость — не под фантазийные 12 часов.

**Недельный ритм:**
- **Пятница 16:00** — демо директору, 30 минут, что-то работающее КАЖДУЮ неделю. Это дисциплинирует сборку и держит инвестора вовлечённым.
- **Суббота** — лёгкий день: фиксы, документация, планирование следующей недели.
- **Воскресенье** — полный выходной. Не обсуждается. Марафон на 12 недель выигрывает отдохнувший.

## Недели 1–4: MVP-ядро

### Неделя 1 — главный гейт + фундамент
- **СТТ-ГЕЙТ по docs/STT_GATE.md (дни 1–3, всё остальное — после):** 50 реальных фраз директора (казахские имена, ≥10 со смешанной речью, шум цеха/машины). Метрика — поля карточки: адресат + суть + дедлайн верно ≥90%, ошибочный адресат ~0%. A/B: провайдеры (`gpt-4o-transcribe` с prompt-ростером vs ElevenLabs Scribe) × микрофон (встроенный vs гарнитура — ⏳ D-42 купить до гейта). Корпус гейта = будущие few-shot и evals (один корпус, G.8).
- Supabase dev + prod (Франкфурт), Vercel (preview→dev, production→prod), репозиторий и CI.
- Миграции ядра: companies, profiles, tasks, task_messages, notification_deliveries + RLS-паттерн (`auth_company_id()`/`auth_role()`) + **pgTAP негативный тест «сотрудник не видит чужого»**.
- **Опрос парка устройств (⏳ D-23 через директора) + замер доставляемости push/Telegram на 5 реальных телефонах, включая худший Huawei** — канал доставки подтверждается железом на неделе 1, не на неделе 8.
- ⏳ D-25: дата старта назначена; ⏳ D-26: телефон директора известен, тестовые устройства (Redmi-класс + iPhone) на руках.
- Б: финализация условий с инвестором (доли! риск 50/50), старт оформления ТОО.
- ✅ Критерий: **гейт пройден по числам** (или принято решение по данным: смена провайдера/микрофона), схема ядра в dev+prod, RLS-тест зелёный, парк устройств известен.

### Неделя 2 — auth, канал, подсистема доставки
- Auth: админ создаёт профиль → QR-инвайт → PIN; логин по телефону (D-06). Справочник сотрудников с алиасами — заполнить реальными людьми WAG.
- Лента личного канала (feed): карточка задачи, 3 кнопки (Принял / Уточнить / Не могу с причинами-чипами), композер (текст/фото/голосовое).
- «Мои дела»; **статусная машина целиком, переходы только через RPC — включая `scheduled` и `revoked`** (отзыв задачи — часть ядра, D-01).
- **Подсистема доставки:** outbox `notification_deliveries` (queued/sent/failed, attempts, cron-свип) + Web Push (VAPID) + **Telegram-ярус (grammY, привязка deep-link'ом на онбординге — D-21)** + ack-эндпоинт + эскалация по таймауту ~10 мин + индикатор директора «отправлено / увидел / принял» («не открывал с 9:14»).
- Онбординг-чек-лист как экран продукта: установить PWA → пуши → выключить оптимизацию батареи (MIUI) → тестовый пуш на глазах.
- ✅ Критерий: задача, созданная вручную в БД, доходит до телефона пушем; сотрудник принимает; директор видит квитанцию «увидел/принял»; при неоткрытии эскалация в Telegram срабатывает.

### Неделя 3 — голосовой конвейер целиком (включая мульти-сущности)
- Запись с FAB (зажал — голос, тап — текст), **стриминг чанков во время записи**, аудио в Storage по signed URL ДО AI-вызовов.
- STT за интерфейсом `transcribe()` (провайдер — победитель гейта) → Claude Haiku, **structured outputs, сразу мульти-сущности** (объявление + N задач + очки из одного голосового; «Ерлану и Марату» → N задач-копий с `group_id`, D-02).
- **/confirm:** чипы исполнителя/дедлайна/приоритета, **инлайн-правка title с клавиатуры, «🎤 переговорить сущность»**, нераспознанный адресат не блокирует остальные («Отправить 4 из 5», D-36); конвенции времени из таблицы директора (D-15); идемпотентность через `ingest_batches` + `client_request_id`.
- Staging-контур `inbox_items` (recorded → transcribed → parsed → confirmed/discarded) + `ai_logs` с diff правок — с первого дня.
- **Evals v1 из корпуса гейта** (`pnpm eval:parser`; гейты: assignee ≥97%, entity F1 ≥90%).
- ✅ Критерий: голосовое с 3+ сущностями → /confirm → точечная правка одной → отправка валидных; **p50 ≤ 6 с до интерактивного /confirm**; аудио не теряется при обрыве любого этапа.

### Неделя 4 — Пульс-минимум + приёмка + MVP end-to-end
- Пульс: статус-вердикт, **«Требует вас» на кнопках** (сортировка: просрочки → вопросы → приёмка; свайпы — неделя 9), живая лента на per-company `seq`-курсоре (realtime — лишь ускоритель), блок «Люди» с точками загрузки.
- Приёмка: pending_review → done/rework (rework → автоматически accepted); **отзыв задачи из карточки (revoked)**; ветка declined: Переназначить / Отменить / Настоять.
- Деградационные режимы: AI недоступен → «аудио сохранено, распознаю позже» + ручная задача из 3 полей; оффлайн-очередь действий сотрудника (IndexedDB, client_ts, состояние «отправится при связи»).
- Б: документы ТОО поданы; подготовка заявки Astana Hub.
- ✅ Критерий: **MVP-ядро end-to-end**: голос → мульти-задачи → квитанции доставки → принял → отчёт → приёмка/отзыв. Оффлайн-действие доезжает ровно один раз. Проверено на Redmi-классе и iPhone.

## Недели 5–6: пилот на ядре

### Неделя 5 — ПИЛОТ: директор + 5 сотрудников (только ядро)
- Скоуп пилота — D-40(в): голос → подтверждение → доставка → 3 кнопки → отчёт → закрытие/отзыв. **Никаких очков, рейтинга, магазина, ТВ, game feel.**
- Состав: 2 лояльных офисных + 2 полевых (стройка, худшая связь) + 1 скептик — ⏳ D-22 утвердить у директора. ⏳ D-20: имя и домен утверждены ДО онбординга (иконка PWA у людей на экранах).
- Онбординг лично каждого по чек-листу-экрану; договорённость: ВСЕ поручения этим 5 людям — только через систему, 30 дней.
- Ты — живая поддержка (реакция в тот же день); **ежедневно читать ai_logs/inbox_items**: что сказал, что понял парсер, что правилось.
- ✅ Метрики недели: % поручений через систему **>80%**; доля правок на подтверждении **<20%** (20–40% — дорабатываем промпт в фоне; >40% два дня подряд — стоп-неделя на промпт и корпус, D-35); доставляемость по квитанциям.

### Неделя 6 — фиксы пилота + Эфир (полубуфер)
- Первая половина — правки по реальному фидбеку пилота (их будет много — это нормально, для этого неделя и полубуферная).
- Эфир: объявления с аудио + транскрипт, кнопка «Ознакомился» с отметкой кто прочитал, публичные события.
- **Тихие часы доставки 08:00–21:00 Asia/Aqtobe (D-38):** вне окна — авто-`scheduled` на 08:00 с пометкой на /confirm «отправлю утром» и тапом «отправить сейчас».
- Б: заявка в Astana Hub подана.
- ✅ Критерий: утреннее голосовое директора разлетается на объявление + N задач одним подтверждением; главные боли недели 5 закрыты.

## Недели 7–8: ассистент и гейт адаптации

### Неделя 7 — ИИ-ассистент директора
- `@anthropic-ai/sdk` напрямую + ручной SSE-стриминг (Vercel AI SDK не вносить, G.6); модель Sonnet-класса; **strict tools** — 5–8 предопределённых инструментов (search_tasks, employee_tasks, who_not_reported, overdue_list, summary_today), не text-to-SQL.
- Вопросы голосом и текстом: «что там по Казхрому?», «кто не отчитался?». Ассистент доступен только директору (D-34).
- ✅ Критерий: директор задал 5 разных вопросов — получил верные ответы с карточками. **Демо-момент №2 — показать в пятницу обязательно.**

### Неделя 8 — ГЕЙТ АДАПТАЦИИ (D-40)
- **Условие гейта: директор пользуется системой ежедневно ≥2 недели** (по ai_logs, не по ощущениям). Решение фиксируется в DECISIONS.md.
- **Гейт пройден →** включаем слой мотивации:
  - Очки: `point_transactions` (баланс = SUM, append-only), ручные начисления тапом и голосом; снятие — только руками с причиной (D-30); **автоштрафы выключены весь калибровочный месяц (D-28)** + кнопка «Оспорить» в истории; бонус «в срок» — только за первый done (D-31); премия — только вверх (D-12).
  - Реакции с золотой обводкой — только на task_messages; рейтинг в Эфире (топ-5 публично, D-11); профиль с балансом и streak.
  - **Game feel — отдельная строка работ, не «само получится»:** `<EffectsLayer>`, стрела отправки, частицы очков, вонзание карточки; эффекты не блокируют запись данных; звуков нет (D-27); бюджет производительности на Redmi.
- **Гейт не пройден →** неделя уходит на удержание ядра: фиксы, промпт, доставляемость, разбор с директором «что мешает» — и гейт переносится, а не отменяется.
- ✅ Критерий: решение гейта записано; если включили — «Ерлану плюс десять» голосом работает, стрела летит, на Redmi-классе нет лагов.

## Правила выживания плана

1. **Скоуп-дисциплина.** Новые идеи (свои и директора) — в бэклог WORKLOG.md, не в текущую неделю. Пересмотр бэклога — по субботам. Фильтр прежний: добавляет тап к основному флоу — не берём. «Пригодится для SaaS» — не аргумент (G.15).
2. **Пятничное демо неприкосновенно.** Не готово идеальное — показывай что есть. Неделя без демо = первый звонок, две подряд = план пересматривается.
3. **Если неделя поплыла** — режем скоуп недели, не сон и не тренировки. График 5:00–22:00 и есть твоё главное преимущество перед командами; сломаешь его — сломаешь 12 недель.
4. **Буфер честности:** недели 6 и 12 наполовину буферные. Если всё идёт по плану — отлично, опережай. Если нет — они спасают график без паники.
5. **Б-трек не крадёт кодовое время.** Бюрократия ТОО/Hub — утренние окна и обеденные паузы. Один день полностью на бюрократию допустим раз в 2–3 недели.
6. **Гейты не перепрыгиваются.** СТТ-гейт (неделя 1) и гейт адаптации (неделя 8) — решения по данным, записываются в DECISIONS.md. Провал гейта — это работающий план (смена провайдера / неделя удержания), а не катастрофа.
