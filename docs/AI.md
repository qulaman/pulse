# AI.md — голосовой конвейер: STT, парсер, evals

Что это: описание построенного AI-контура продукта (STT, парсер, evals) — как он устроен в коде и какие правила нельзя потерять при правке. Арбитр — DECISIONS.md (сводка «Сейчас действует», абзац «Голос и разбор»). Схема БД (`ai_logs`, `inbox_items`) — docs/DATABASE.md; эндпоинты — docs/BACKEND.md; UI-состояния — docs/FRONTEND.md; протокол замера STT — docs/STT_GATE.md; казахская речь и гарнитура — открытые решения D-17, D-42.

**Где правда.** Текст промпта, схема сущностей и few-shot живут в коде — `lib/ai/prompt.ts`, `lib/ai/schema.ts`, `lib/ai/examples.ts`. Этот док описывает их устройство и правила, которые нельзя потерять при правке, и не копирует текст (копии расходились с кодом). «/confirm» ниже — подтверждение разбора: основное — карточками на доске Пульса, `/confirm` — запасной экран (D-60, 6-е уточнение).

## 1. STT: `lib/ai/stt.ts`

```ts
export interface SttOptions { language?: 'ru' | null; vocabularyHints?: string[]; signal?: AbortSignal } // null = без language-hint; signal — таймаут/отмена от политики ретраев
export interface SttResult  { text: string; durationMs: number; provider: string }
export interface SttProvider { name: string; transcribe(audio: Buffer, mime: string, opts: SttOptions): Promise<SttResult> }
```

- Реализации (`lib/ai/stt-providers.ts`): `openai-4o` (`gpt-4o-transcribe`, `prompt` = `hintsToPrompt(vocabularyHints)`), `whisper1`, `deepgram` (`nova-3`, keyterm — все имена и контрагенты), `elevenlabs` (`scribe_v2`, keyterms — только контрагенты, см. ниже). Primary — `gpt-4o-transcribe` (D-39). Выбор — `company.settings.stt.provider` / `.fallback` / `.language` (страница «Настройки», D-48; дефолты `openai` / `null` / `auto` — без language-hint). По D-48 env `STT_PROVIDER` / `STT_FALLBACK_PROVIDER` — дефолт инстанса; фактически `/api/voice/transcribe` передаёт провайдеров только из `settings.stt` (zod-дефолт `openai`), env читает `transcribe()`, вызванный без настроек (расхождение с D-48 — IDEAS И-90). **Политика ретраев (G.18, реализована в `transcribe()`):** primary с таймаутом 10 с → при 5xx / таймауте / сетевой ошибке fallback (если задан) с таймаутом 10 с → пауза 1 с → один повтор primary → `SttError('stt_failed')`; 4xx кроме 408/429 — без ретраев, сразу `stt_http`. Провайдер пишется в `ai_logs.provider`.
- `vocabularyHints` — ростер имён (full_name + алиасы; роль `tv` исключена в `loadRoster`, D-53) — не больше 60 человек (D-55, ниже) — плюс контрагенты из `company.settings.vocabulary`. Имена и слова ведут директор и секретарь на странице «Словарь» (`/settings/dictionary`, D-111): инструкция, проверка имени тем же `matchName`, правка сразу по тапу.
- **Подсказка gpt-4o — предложение, не список (D-53).** `hintsToPrompt` собирает: «Директор диктует поручения сотрудникам. В компании работают {полные имена}; коротко их зовут {алиасы}. Контрагенты и объекты: {…}.» Причина: gpt-4o-transcribe читает prompt как предшествующий текст и на коротком или шумном аудио продолжает список вместо расшифровки; связное предложение этого не делает, имена распознаются как раньше. Доля эха у guard считается по токенам имён (`hintSurfaces`), а не по всему промпту: слова каркаса («директор», «поручения») — обычная речь.
- **Размер подсказки (D-55).** `vocabularyHintsFor` (`lib/roster.ts`) даёт STT не больше `HINT_MAX_PEOPLE` = 60 человек (`lib/ai/hint-roster.ts`): при большем ростере — тех, кому директор чаще ставил задачи за 90 дней (`loadAssigneeCounts`, порядок стабилен: счётчик, потом id — ради кэша); остальных матчит парсер по полному ростеру, STT просто не подсказано их написание. Причина: на большом ростере шумная запись возвращается выдуманным поручением случайному человеку из ростера — класс, который матчер не ловит. Пересмотр порога — по замеру на ростере больше 60 (IDEAS И-98).
- **ElevenLabs Scribe (`scribe_v2`) — только fallback (D-53).** Промпта нет — эха нет; на шумном телефонном аудио хуже gpt-4o, автодетект языка нестабилен; keyterms с именами ростера на шуме дают список имён вместо речи — самый опасный класс, поэтому keyterms только контрагенты. В `settings.stt.fallback` по умолчанию не включён (`null`); включение — по данным замера (docs/STT_GATE.md).
- **Guard от галлюцинаций STT** (`lib/ai/stt-guard.ts`; Whisper на тишине/непонятной речи сочиняет связный текст): (а) клиент не отправляет аудио < 1000 мс; (б) на сервере — отношение `chars(text)/durationSec > 30` → результат отбрасывается; (в) транскрипт из известных фантомов («Продолжение следует», «Субтитры сделал…», «Спасибо за просмотр») → отбрасывается; (г) транскрипт из одного слова → фронту `empty_transcript`, Claude НЕ вызывается (D-52: два слова — «Марат сигареты», «Жандос кофе» — это распоряжение, оно идёт в парсер); (д) **эхо промпта** (STT возвращает кусок подсказки вместо речи): нормализованный транскрипт содержит подстроку ≥4 слов из vocabularyHints-строки ИЛИ ≥60% его слов входят в словарь подсказки → отбрасывается; (е) **зацикливание**: одна и та же фраза повторена ≥2 раз подряд и составляет >70% транскрипта → отбрасывается; (ж) **аномально низкая плотность речи** (в шуме STT возвращает обрывки и галлюцинированные имена из подсказки): `chars(text)/durationSec < 6` при длительности >3 с → результат помечается подозрительным, сущности с исполнителем из такого транскрипта получают принудительный `assignee_confidence ≤ 0.5` (жёлтый чип «проверь»). Отброса по плотности нет (D-52: медленная речь с паузами по плотности неотличима от шума — решает директор при подтверждении, guard только помечает). Это единственный guard против самого опасного класса: галлюцинация ВАЛИДНОГО имени из vocabularyHints, которую матчер не ловит. Все guard-отбросы → фронту `empty_transcript` («Не понял, повторить?»), в ai_logs — `status='error:stt_guard:<код>'` — без этого мусор становится объявлением «всем в Эфир».
- **Голосовые в задачах не распознаются вообще (D-66).** Сообщение в треде — запись не длиннее 10 секунд: она хранится в `voice` и проигрывается своим плеером, `transcribe` её не касается, парсер — тем более. STT остаётся только на входе директора (`context='director_input'`, роль director), где текст и есть продукт: из него рождаются сущности.
- **Заметка, надиктованная на экране «Заметки» (D-81):** `/api/voice/transcribe` принимает `note_id` — строка заметки с записью рождается до STT, транскрипт пишется в неё же (`text` — только пока он пуст, директор мог уже впечатать своё; `raw_transcript` — всегда). Закрытая вкладка или потерянный ответ не оставляют мысль без слов.
- Аудио всегда сохранено в Storage ДО вызова transcribe (принцип 5, signed URL с клиента).

## 2. Системный промпт парсера — `lib/ai/prompt.ts` + `lib/ai/kinds/`

Сборка детерминирована (наряд 026): `parserSystemPrompt(conventions, rules, kinds)` склеивает один системный текст в фиксированном порядке — **преамбула и общие правила → ростер → «Время» → разделы включённых видов → «Безопасность» → «Формат ответа» → правила компании**. Общие разделы — константы `prompt.ts`; раздел каждого вида — в его модуле `lib/ai/kinds/<вид>.ts` (там же его few-shot пары и его вариант схемы модели). `buildSystemBlocks(roster, conventions, rules, kinds)` отдаёт два system-блока: этот текст и ростер отдельным кэшируемым блоком (`rosterJson`: только активные, `{id, full_name, aliases, position}`, отсортирован по id, `cache_control`). Дата/время — ТОЛЬКО в user-сообщении (`buildUserMessage`), иначе кэш инвалидируется каждую минуту (§9).

**Виды по компании (наряд 026).** `settings.parser.kinds` — массив имён видов, по умолчанию все восемь, порядок фиксирован (`lib/ai/kinds/names.ts`), `task` выключить нельзя, неизвестное имя отбрасывается. Переключатели — «Настройки → ИИ-модель → Разбор поручений → Что модель различает». Выключенный вид исчезает из промпта, примеров и схемы. `/api/voice/parse` и «Лаб» (песочница, прогон корпуса, «Что видит модель») берут виды компании; `pnpm eval:parser` и тесты — все виды. Все восемь и без правил — ядро, которое меряет `pnpm eval:parser`.

**Правила компании (D-138).** Ядро — общее для всех компаний и меняется только кодом с `pnpm eval:parser`. Компания дописывает к нему до 2000 знаков своих правил (`settings.parser_rules.versions[0].text`, `lib/ai/rules.ts`): блок встаёт последним под заголовком «## Правила этой компании» с оговоркой, что запрет выдумывать («Общие правила»), «Безопасность» и «Формат ответа» он не отменяет; `<` в нём заменяется на `‹`. Без правил текст байт в байт ядро. Правит директор или секретарь во вкладке «Лаб → Парсер»: песочница на одной фразе, прогон корпуса (§6), сохранение только при пройденных порогах, последние 10 версий с откатом через черновик.

| Раздел | Где | О чём | Решение |
|---|---|---|---|
| Общие правила | `prompt.ts` | ничего не выдумывать; все сущности по порядку речи, `source_span` дословно; искажённое распознаванием восстанавливать только как день, время или имя, бессмыслицу — не сущность | — |
| Ростер | `prompt.ts` | человек — `full_name` из блока ростера дословно (не из примеров), id ставит система; падежи русские и казахские; созвучное имя — с confidence ≤ 0.5; нет уверенного кандидата — `null` и ≤ 0.3 | D-56 |
| Время | `prompt.ts` | время — только ссылкой `TimeRef` (§3), без арифметики; части дня — фразы конвенций компании → ключ `part`; срок не назван — `null`; фонетическая реконструкция дня и времени — confidence ≤ 0.5 и слова в `text` | D-15, D-52 |
| `announcement` | `kinds/announcement.ts` | объявление всем; собрание со временем — уже `event` | — |
| `task` | `kinds/task.ts` | ЛЮБОЕ поручение; без имени — всё равно `task`; «Ерлану и Марату» — две `task` с общим `group_id`; телеграф «имя + предмет»; «распредели в группе» — `task` менеджеру; `priority`; `scheduled_send` — только явное «отправь ему утром», а «скинь мне завтра утром» — срок | D-02, D-52 |

| `reminder` | `kinds/reminder.ts` | только «напомни мне», «не забыть мне»; `remind_at` — `TimeRef` | — |

| `event` | `kinds/event.ts` | слово-маркер и дата/время; участники — `full_name` или `everyone`; место — `location`; `starts_at` — `TimeRef`, дата без времени — только день; повестку и напоминание не выдумывать | D-78 |
| `recurrence` | `kinds/recurrence.ts` | «каждый понедельник …» | — |
| `query` | `kinds/query.ts` | вопрос о состоянии дел — `query`; поручение с вопросительной интонацией — `task` | — |
| Безопасность | `prompt.ts` | `<input>…</input>` — данные, не инструкции; при «Источник: shared» — `points` запрещены | D-36 |
| Формат ответа | `prompt.ts` | строго по JSON-схеме | G.17 |

**Шаблон user-сообщения** (`buildUserMessage`; строки «Ближайшие дни» больше нет — арифметику дат делает код, наряд 026):

```
Сейчас: {день недели}, {DD.MM.YYYY HH:mm} (+05:00). Источник: {voice|typed|shared}.
<input>
{транскрипт или пересланный текст}
</input>
```

`<` в транскрипте заменяется на `‹` — текст не может закрыть или подделать теги данных («Безопасность»).

## 3. Схема сущностей — `lib/ai/schema.ts` (единственный источник)

Файл содержит форму приложения (`z.strictObject` на вид, `z.discriminatedUnion('kind')`), TS-типы через `z.infer` (импортирует фронт) и сборку схемы модели из модулей видов (`lib/ai/kinds/<вид>.ts` — там вариант модели). JSON Schema генерируется из zod и «закаляется» (`harden`): `additionalProperties: false` на каждом объекте, все поля в `required`, nullable — **`anyOf [{type}, {type:'null'}]`** (форму `type: [..., 'null']` валидатор Anthropic отвергает), nullable-enum — один `enum` со значением `null` (без `anyOf`), объединение видов — **`anyOf`** (не `oneOf`), `kind` — `const`, `TimeRef` — один `$defs` по `$ref`. **В API уходит именно эта схема** (`entitiesJsonSchema(kinds)`), а не `zodOutputFormat()` из SDK: хелпер превращает `z.literal('task')` в простую строку, дискриминатор теряется, и модель смешивает поля разных видов (G.17).

**Время — ссылкой, не ISO (наряд 026).** Модель не выдаёт ни одного ISO: срок, начало, момент напоминания и отложенной отправки — объект `TimeRef` (`lib/ai/timeref.ts`), плоский, все поля есть и nullable:

| Поле | Значение |
|---|---|
| `text` | слова о времени дословно — их цитирует жёлтый чип |
| `day` | `today` · `tomorrow` · `after_tomorrow` · `weekday` · `date` · `null` |
| `weekday` | 1 (пн) … 7 (вс) при `day: weekday`, иначе `null` |
| `date` | `YYYY-MM-DD`, только если названо число |
| `time` | `HH:MM`, только явно названное время |
| `part` | `morning` · `before_lunch` · `lunch` · `after_lunch` · `evening` · `end_of_day` · `end_of_week` · `this_week` · `null` |
| `confidence` | уверенность модели, что она верно услышала; фонетическая реконструкция ≤ 0.5 |

`resolveTimeRef(ref, now, conventions, kind)` превращает ссылку в момент по часам Актобе: день недели — ближайший такой вперёд, сегодня — пока его момент впереди; только время или часть дня без дня — сегодня, а если уже прошло — следующий такой момент; час 1–7 без части дня — дневной («до шести» = 18:00), часть дня после обеда сдвигает утренний час; `part` — время строки конвенций по ключу (`end_of_week`, `this_week` — ближайшая пятница); день без времени — строка `day_default`, день недели без времени — `weekday_default`; мероприятие без времени — 09:00 и 0.5 (D-78). Уверенность — минимум из модельной и строки конвенций; явное время — модельная; момент раньше «сейчас» — не выше 0.7 (жёлтый чип). Конвенции — `company.settings.conventions`: строка на фиксированный ключ (`key`, `phrase` — синонимы через « / », их видит модель; `time` `HH:MM`; `day` `same | friday`; `confidence`); старые строки `phrase/meaning` при чтении приводятся по совпадению с прежними дефолтами, нераспознанные отбрасываются с записью в лог сервера.

**Две формы.** Схема модели — виды компании (по умолчанию восемь: `announcement`, `task`, `points`, `reminder`, `note`, `event`, `recurrence`, `query`), без `assignee_id`, время — `TimeRef`, мероприятие — урезанное. `EntitySchema` — форма приложения (confirm, UI, RPC): девять видов — те же плюс `delegation`, — с `assignee_id`, ISO-полями времени и полным мероприятием; перевод — `fromModelEntity` в `lib/ai/postprocess.ts` (вызывает `parseTranscript`). Почему в модели не больше восьми видов: API компилирует схему в одну грамматику и отвергает больше 16 nullable-параметров и «слишком большую» грамматику; девятый вид не помещается ни в какой форме, поэтому `delegation` обменяна на `event` (D-78), а `DelegationEntitySchema` осталась только в схеме приложения — строки, разобранные до обмена, валидны. Компания может виды выключать, добавить — нет.

**Вызов** — `@anthropic-ai/sdk` напрямую, `client.messages.create` со structured outputs: `output_config: { format: { type: "json_schema", schema: entitiesJsonSchema(kinds) } }`; параметр `thinking` для Haiku не передаётся, для остальных моделей Anthropic (эскалация) — `{ type: "disabled" }` (извлечение с few-shot не требует рассуждений, а adaptive thinking выбивал бюджет D-43). Напрямую и со своей схемой — потому что парсер опирается на возможности API в их собственной форме (своя JSON Schema, `cache_control` на отдельных блоках — §9, разбор `stop_reason`), а даже хелпер самого SDK терял дискриминатор (выше); прослоек поверх SDK нет (G.6). У Claude ответ приходит уже по схеме, поэтому шага «починить JSON и спросить снова» там нет — обрабатываются только: `stop_reason: "max_tokens"` → один повтор с лимитом ×2, затем `parse_failed`; refusal → `parse_refused` (§11); текст ответа проверяется zod-схемой видов как типизированная граница — несовпадение тоже `parse_failed`. **JSON-режим (DeepSeek и любой OpenAI-совместимый провайдер) — один повтор по схеме (наряд 026):** ответ не JSON или не по схеме уходит модели ещё раз — её ответ как assistant и «Ответ не прошёл схему: <issues>. Верни исправленный JSON по той же схеме»; второй промах — `parse_failed`. Оба вызова — в `calls` и в `ai_logs.raw_response.calls` (первый — `ok: false` со своими токенами). Семантику проверяет postprocess: `assignee_name` совпадает с `full_name` активного сотрудника (иначе — fuzzy по `assignee_queries`), `amount ≠ 0`, ISO парсится, для `source='shared'` нет `points` (страховка к «Безопасности»). **В схему модели `assignee_id` не входит (D-56):** на реальном uuid-ростере модель копирует id из few-shot, а имя из ростера копирует надёжно; побочная причина — лимит API на 16 nullable-полей. `pnpm eval:parser` по умолчанию подменяет демо-id на uuid-подобные — иначе эффект не виден (`--demo-ids` для сравнения со старыми прогонами); метрики «имя исполнителя от модели — из ростера» и «исполнитель без чипа «проверь»» — в отчёте.

Правила поверх схемы: любое поле с confidence < 0.8 — жёлтый чип при подтверждении (срок в прошлом — тоже: его уверенность не выше 0.7); `deadline_iso` конвертируется в UTC перед insert; N сущностей task с одним `group_id` = N независимых задач (D-02); отрицательный `amount` из голоса блокируется с подсказкой «снятие — только вручную с причиной» (D-30).

## 4. Few-shot — `lib/ai/kinds/*` + `lib/ai/examples.ts`

12 пар user/assistant после system-блоков (кэшируются, §9). Каждая пара живёт в модуле вида, которому учит; `fewShotPairs(kinds)` отдаёт пары включённых видов в порядке видов, и пара показывается, только если включены ВСЕ виды её ответа (пример выключенного вида учил бы ответу, который схема не примет). Тексты и полные ответы — в модулях; здесь — что каждый пример учит.

| № | Модуль | Что учит | Виды в ответе |
|---|---|---|---|
| П1 | `task` | Одиночная задача, явный дедлайн | `task` |
| П2 | `task` | Мульти-сущность: мероприятие всем + две задачи + очки | `event`, `task` ×2, `points` |
| П3 | `task` | Телеграфный стиль | `task`, `points` |
| П4 | `task` | Без исполнителя — `null`, не выдумывать | `task` |

| П7 | `task` | Казахские падежи и вставка казахского | `task` ×2 |

Правила few-shot:
- Ростер примеров — **единый демо-ростер `tests/stt/roster.json`** (тот же, что в seed.sql и корпусе замера STT; в проде в system-блоке — реальный): Айгуль → `u-005`, Ерлан → `u-001` (в речи — «Ерлану Б.», иначе двое Ерланов дают неоднозначность), Марат → `u-003`, Сакен → `u-004`, Тимур → `u-009`, Жандос → `u-010`.
- Контекст всех примеров — `FEW_SHOT_CONTEXT`: «Сейчас: четверг, 13.08.2026 16:32 (+05:00). Источник: voice.»
- Контрагент — нейтральная «Альфа», никогда не реальный партнёр клиента (код клиент-агностичен, V-02).
- Ответы написаны в форме модели: без `assignee_id` и `participant_ids`, время — `TimeRef` (то, что сказано, без вычислений; хелпер `spokenTime`), мероприятие — с `""` вместо `null`.
- Последний assistant-ответ несёт второй `cache_control`: system + ростер + few-shot — один кэшируемый префикс (§9).
- Пример не должен почти дословно повторять кейс evals: модель переносит поля примера на кейс.

## 5. Матчинг имён: модель + `lib/matchName.ts`

Модель матчит сама (ростер в промпте, склонения — её сила) и отвечает ИМЕНЕМ: `assignee_name` = `full_name` из ростера дословно (D-56: id она не копирует, имя — копирует). `matchName` — детерминированный слой поверх:

0. **Тёзки**: если упоминание — одно слово (без фамилии/инициала) и его стем совпадает со стемом имени у ≥2 активных сотрудников («Ерлану» при двух Ерланах) → `ambiguous` с этими кандидатами, **даже если модель уверенно назвала человека**. Ошибочный адресат — единственная недопустимая ошибка (STT_GATE §4).
1. **Имя от модели**: `assignee_name` совпадает (без регистра, ё=е) с `full_name` активного сотрудника → matched, чип по `assignee_confidence` (<0.8 — жёлтый). Имени нет или оно не из ростера → шаг 2. (Старый канал `assignee_id` матчер ещё принимает — для вызовов из кода, не от модели.)
2. **Fuzzy-фолбэк** по `assignee_queries[0]`: нормализация (`lib/text/normalize.ts`, общая с замером STT: нижний регистр, ё→е, без пунктуации, числительные словами → цифры) + рекурсивное усечение падежных окончаний (`-ға, -ге, -қа, -ке, -ды, -ді, -ты, -ті, -ом, -ой, -ей, -у, -е, -а, -ы, -ю, -я`, основа не короче трёх букв; инициалы не усекаются) → trigram similarity (коэффициент Дайса) против full_name+aliases; форма, чей инициал не совпал с названным, получает 0.
3. Пороги (в `lib/ai/config.ts`, переопределяются `company.settings.matching` — частичный объект тех же ключей, без UI, задаётся при провижининге по данным замера, D-16):
   - `≥ 0.45` и разрыв со вторым кандидатом `≥ 0.15` → авто-подстановка, **жёлтый чип** «проверь»; точное совпадение поверхности (score 1 после нормализации и стемминга: «Марат», «Марату», «Сәкенге») и единственный такой кандидат → авто **без** чипа (D-16 «точное совпадение → авто», D-56);
   - `0.30–0.45` или два близких → чип с выбором из 2–3 кандидатов тапом;
   - `< 0.30` → красный чип «Кому?», отправка ТОЛЬКО этой сущности заблокирована («Отправить N из M», D-36).
4. `assignee_confidence < 0.8` от модели → жёлтый чип даже при уверенном матче.
5. **Закреплённый исполнитель (D-84, `lib/ai/pin.ts`).** Если человек выбран до слов — тап по его кружку на экране ожидания или «Дать задачу» на его карточке, — `/api/voice/parse` получает `assignee_id`, и `pinAssignee` после матчинга ставит этого человека каждой сущности с одним исполнителем (`task`, `points`, `recurrence`, `delegation`): по id, зелёным, confidence 1, блок `assignee_unmatched` снимается. Исключение: модель сматчила человека с другим именем — оно прозвучало вслух («…и скажи Асхату привезти образцы»), такая сущность не трогается. id не из активного ростера ничего не закрепляет.

## 8. Порядок разбора и эскалация модели парсера

- **Порядок в `/api/voice/parse`:** (1) повтор с тем же `client_request_id` — вернуть прошлый разбор из `ai_logs`, модель не вызывается; (2) **матчер заявок до модели (D-79 §9, `lib/errands/matcher.ts`)** — фраза не длиннее трёх слов, без имени из ростера, начало которой совпало с `label` или `synonyms` кнопки каталога `company.settings.secretary.actions`, при активном секретаре → ответ `{ entities: [], errand, model: "matcher" }`, остаток фразы — примечание («кофе без сахара»); всё остальное — в парсер; (3) парсер с эскалацией (ниже); (4) postprocess и закрепление исполнителя (§5).
- **Базовая модель** — `company.settings.parser.model`, дефолт `claude-haiku-4-5` (страница «Настройки», «Лаб»). **Модель эскалации** — `settings.parser.escalation_model`, дефолт `claude-sonnet-5` (`lib/settings.ts`; тот же `DEFAULT_ESCALATION_MODEL` в `lib/ai/parse.ts`). **Выключатель эскалации** — `settings.parser.escalate` (дефолт `true`). Env `PARSER_MODEL` / `PARSER_ESCALATION_MODEL` читает `parseTranscript`, вызванный без настроек (`pnpm eval:parser`); роут всегда передаёт `settings.parser` (расхождение с D-48 — IDEAS И-90).
- **Триггеры эскалации** (G.17; до показа подтверждения, прозрачно для UI): транскрипт > 400 символов ИЛИ сущностей > 3 ИЛИ `assignee_confidence < 0.6` при непустом `assignee_queries` (задача без имени легитимно несёт 0 — сильная модель имени тоже не найдёт, второй вызов бесполезен; D-52) ИЛИ `deadline_confidence < 0.5` (ниже пола таблицы конвенций — «на неделе» легитимно даёт ровно 0.5) → повторный прогон модели эскалации (без thinking, §3), показывается её результат; оба вызова — в `ai_logs`. **Длинный транскрипт (>400 символов) эскалируется независимо от ответа Haiku, поэтому оба вызова стартуют одновременно** — директор ждёт более медленный, а не сумму (D-43). Сбой сильной модели при живом ответе слабой — не ошибка: показывается разбор Haiku с `escalated: false`.
- **Экспериментальный провайдер (D-63):** `deepseek-chat` / `deepseek-reasoner` за тем же контрактом (`lib/ai/deepseek.ts`): тот же промпт, ростер и few-shot в OpenAI-совместимый чат в JSON-режиме, схема — в системном промпте, форма проверяется zod; ответ не по схеме — один повтор с перечнем ошибок (§3, наряд 026). Выбирается через `company.settings.parser.model` (страница `/lab`); дефолт не меняется. Провайдер выбирается по id модели (`providerOf`), а не константой.
- **Смена базовой модели** — правка `settings.parser.model`, без кода; основание — evals (гейты §6), не ощущения; сама смена — решение в DECISIONS.md. Корпус на другой модели (без перепроверки) гоняется во вкладке «Лаб → Парсер» → «Модель прогона: Сравнить с …» — такой прогон только для сравнения, правила по нему не сохраняются (D-138).

## 10. Логирование и staging

- **`ai_logs`** — контракт полей в docs/DATABASE.md (kind, source, provider/model, transcript, raw_response, parsed_entities, confirmed_entities, was_edited, edit_fields, tool_calls, токены, latency с разбивкой stt_ms/parse_ms, status). Обязанности конвейера:
  - `/api/voice/parse` пишет `parsed_entities` (то, что показали);
  - **`/api/voice/confirm` ОБЯЗАН дописать в ту же строку `confirmed_entities`, `was_edited` и `edit_fields`** (diff parsed↔confirmed, `lib/ai/edit-diff.ts`) — без этого метрика «доля правок» (D-35) и петля evals (§6) не существуют;
  - идемпотентность parse: `client_request_id` и здесь — повторная отправка той же записи не рождает второй счёт за токены;
  - `raw_response.rules_version` — версия правил компании, с которой шёл разбор (0 — без правил, D-138): «до/после» правки видно в «Лаб».
  - Песочница и прогон корпуса «Лаб → Парсер» в `ai_logs` не пишутся (D-138): таблица «Лаба» — разборы директора, `eval:harvest` берёт только их.
- **`inbox_items`** (staging голосового, G.11, схема в DATABASE.md): `recorded → transcribed → parsed → confirmed | discarded`. Каждый этап конвейера продвигает статус; упавший этап оставляет item на прежнем статусе — «распознаю позже» работает с него; продукт сам копит датасет.
