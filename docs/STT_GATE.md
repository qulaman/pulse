## 2. Протокол записи (директор, D-42)

- Записывает **сам директор** в своей обычной манере речи (не «диктовка диктора»), на **свой телефон** — тот же микрофон, что в работе.
- **Каждая фраза — дважды: встроенный микрофон телефона и гарнитура/петличка** (A/B-сравнение микрофонов, D-42). Итого 100 файлов. Категория E — оба дубля в реальном шуме.
- Формат: `audio/mp4` (m4a/AAC) в максимальном качестве, запись напрямую (диктофон/тестовая страница `tests/stt/record.html`), НЕ через мессенджер (транскодирование убьёт сравнение).
- Именование: `NNN_{cat}_{mic}.m4a`, напр. `017_D_headset.m4a`.
- `tests/stt/record.html` («СТТ-студия») — запись фразы корпуса в браузере (`audio/mp4`, где браузер умеет, иначе `webm`), распознавание через OpenAI и разбор Claude по ключам, введённым на странице (хранятся в `localStorage`); скачивает файл `NNN_{cat}_phone.m4a|webm` и журнал сессии JSON — так собран `session-logs/2026-08-20-owner-session.json`.

## 4. Метрики и формулы

Нормализация текста перед всеми метриками (`normalize` в `run.mjs`; её копия `lib/text/normalize.ts` — у guard и `matchName` продукта): нижний регистр, `ё→е`, удалить пунктуацию, числительные словами → цифры («в десять» = «в 10»). Стем имени — рекурсивное усечение падежных окончаний русских и казахских (`-ға, -ге, -қа, -ке, -ды, -ді, -ты, -ті, -ом, -ой, -ей, -у, -е, -а, -ы, -ю, -я`; основа не короче трёх букв) — «Ерлан*» засчитывает «Ерлану» и «Ерланға», «Алияға» и «Алия» сходятся в «али».

**Метрика 1 — Name Recall (порог: ≥95%).**
`NameRecall = (число эталонных имён, чей стем найден в нормализованном транскрипте) / (всего имён в эталонах корпуса)`

**Метрика 2 — поле-метрики карточки (пороги: адресат ≥90%, ошибочный адресат ≤2%, цель 0%).**
Каждое эталонное имя (кроме `ambiguous`) проверяется детерминированным матчером `tests/stt/run.mjs` над транскриптом — своя нормализация и стемы, без LLM (замер меряет STT, не Claude); это не `lib/matchName.ts` из docs/AI.md §5:
- correct — эталонный сотрудник однозначно найден в транскрипте (стем имени, если такое имя в ростере одно, или многословная форма — ФИО, алиас с инициалом); wrong — он не найден, зато однозначно найден сотрудник, которого в эталоне фразы нет; иначе miss.
- `AssigneeAccuracy = correct / total ≥ 0.90`
- `WrongAssigneeRate = wrong / total ≤ 0.02`

**Почему это жёстче WER:** WER штрафует все слова одинаково, а продукт ломает одно слово — имя. Ошибки асимметричны: *miss* восстановим (красный чип «Кому?», директор тапает выбор — терпим до 10%), *wrong* — катастрофа: при автоматизационной слепоте «Всё верно» задача уедет не тому человеку, и директор узнает об этом через день. Поэтому miss ≤10%, wrong ≈ 0.

**Метрика 3 — WER (справочно, в порог не входит): ≤15%.**
`WER = (S + D + I) / N` (замены+удаления+вставки / слов в эталоне) по нормализованному тексту, в отчёте — среднее по файлам. Для смешанной русско-казахской речи 15% реалистичен; метрика нужна для сравнения провайдеров между собой, решение принимают метрики 1–2.

## 5. Провайдеры и конфигурации прогона

Продукт ходит в STT через единый интерфейс `lib/ai/stt.ts` (устройство — docs/AI.md §1); замер — через свои вызовы в `tests/stt/run.mjs`, без зависимостей:

| Провайдер | Конфигурация `run.mjs` | Роль в продукте |
|---|---|---|
| `gpt-4o-transcribe` | `gpt4o` — с подсказкой-предложением (D-53), `gpt4o-noroster` — без неё: вклад подсказки | primary (D-39) |
| `whisper-1` | `whisper` — с той же подсказкой (базовая линия) | альтернатива |
| Deepgram `nova-3` | `deepgram` — усиление именами ростера и контрагентами параметром `keywords` (`термин:2`); провайдер продукта шлёт `keyterm` (keyterm prompting nova-3), так что замер Deepgram не равен продукту (IDEAS И-100) | альтернатива |
| ElevenLabs `scribe_v2` | `scribe` — без keyterms; в продукте keyterms — только контрагенты (D-53) | только fallback (D-53) |

Открытый вопрос — держится ли казахский у Scribe на СМЕШАННОЙ речи, а не на чистом казахском (D-17).

Базовая решётка (дефолты `run.mjs`): все конфигурации, для которых задан ключ, × микрофон phone × language-hint `ru`. Дополнительно (по потребности, см. §7): без language-hint (`--lang none`, D-17 — не режет ли `ru` казахские вставки; в продукте дефолт — без хинта, `settings.stt.language = auto`, D-48), микрофон headset (`--mic headset`).

## 6. Скрипт `pnpm test:stt`

`pnpm test:stt` = `node tests/stt/run.mjs [--providers …] [--mic phone|headset|all] [--lang ru|none] [--fixtures …] [--stamp …]`; `run.mjs smoke <файл> "<эталон>"` — проверка одного файла (транскрипт, найденные сотрудники, WER), не замер корпуса. Ключи — env `OPENAI_API_KEY`, `DEEPGRAM_API_KEY`, `ELEVENLABS_API_KEY`; конфигурация без ключа пропускается.

1. Читает `corpus.jsonl` и файлы `tests/stt/fixtures/NNN_{cat}_{mic}.m4a`, гоняет каждый файл через каждую конфигурацию `провайдер×параметры`.
2. Считает метрики §4 по корпусу целиком и в разрезе категорий (отдельно D и E — они решающие).
3. Печатает таблицу `конфиг → гейт ✅/✖ | NameRecall | AssigneeAcc | WrongRate | WER | p50 latency | стоимость корпуса` (колонка «гейт» — проход порогов §7).
4. Пишет `tests/stt/results/<время>.json` и `manifest.jsonl`; повторный запуск печатает дельту NameRecall к прошлому прогону.

## 7. Пороги и что пробовать, если конфигурация не проходит

**Порог:** конфигурация `провайдер×параметры` на микрофоне phone проходит, если одновременно NameRecall ≥95% ∧ AssigneeAccuracy ≥90% ∧ WrongRate ≤2% (`run.mjs` печатает это строкой «Гейт» под таблицей). Лучшая — кандидат в `company.settings.stt.provider`, вторая по метрикам — в `settings.stt.fallback` (D-48, страница «Настройки»); смена — решение в DECISIONS.md. Результат headset — вход в решение D-42 (гарнитура).

**Не проходит — что пробовать, по одной ступени за итерацию:**
1. Прогнать лучших кандидатов **без language-hint** (казахские вставки, D-17).
2. Вариации подсказки: только полные ФИО vs «ФИО + алиасы + контрагенты» — всегда связным предложением (D-53), не больше 60 человек (D-55).
3. Проходит **только headset** — результат с пометкой «гарнитура обязательна», вход в D-42.
4. Агрессивный keyterm-boosting Deepgram; свежие модели провайдеров.
5. Ничего не помогло — смена STT-провайдера (План Б D-39), решение владельца в DECISIONS.md.
