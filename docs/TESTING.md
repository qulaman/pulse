# TESTING.md — тесты, гейты, Definition of Done

Контракт по качеству WAG Pulse. Арбитр — `DECISIONS.md`. Схема, seed и список RLS-кейсов уровня БД — `docs/DATABASE.md` (разделы seed.sql и «RLS-тесты»); среды и смоук деплоя — `docs/SETUP.md`; СТТ-гейт недели 1 — `docs/STT_GATE.md`.

## 1. Пирамида и команды

| Уровень | Команда | Что покрывает | Когда гоняется |
|---|---|---|---|
| Unit (Vitest) | `pnpm test` | matchName, время, баланс/hold, идемпотентность, статусные переходы (§3) | каждый коммит, CI на PR |
| RLS (pgTAP) | `pnpm test:rls` → `supabase test db` | политики и RPC-инварианты (§2) | каждый PR с миграцией; CI на PR |
| Evals парсера | `pnpm eval:parser` | точность извлечения сущностей (§4) | каждый PR, трогающий промпт/схему/few-shot |
| СТТ-гейт | `pnpm test:stt` | корпус 50 фраз, метрики D-40 | неделя 1; повторно при смене STT-провайдера/микрофона |
| E2E-смоук | вручную по чек-листу §5 (+ Playwright по мере роста) | сквозной флоу на реальных устройствах | перед каждым демо/релизом в prod |

Принцип: вниз пирамиды — всё детерминированное; AI-качество меряется evals, не unit-тестами. E2E не автоматизируем раньше, чем стабилизируется ядро (соло-разработчик, цена поддержки).

## 2. RLS-тесты (pgTAP, `supabase/tests/`, на seed-фикстурах)

Полная таблица из 12 кейсов — в DATABASE.md («RLS-тесты»); она — источник правды. Обязательный минимум, без которого миграция с новой таблицей/политикой не мержится:

| # | Кейс | Ожидание |
|---|---|---|
| 1 | employee читает чужую task | 0 строк |
| 2 | employee делает insert в point_transactions | ошибка RLS |
| 3 | employee читает task в status='scheduled' | 0 строк |
| 4 | manager читает задачу прямого подчинённого (глубина 1) | видит |
| 5 | manager читает задачу чужого поддерева | 0 строк |
| 6 | роль tv читает tv_events своей компании / tasks, profiles, point_transactions | видит / 0 строк или ошибка |
| 7 | anon — любая таблица | 0 строк |
| 8 | employee читает чужие ai_logs / inbox_items | 0 строк |
| 9 | Storage: чтение чужого файла из private-бакета прямым путём (без signed URL) | отказ; доступ к чужому аудио/фото — только signed URL, выданный сервером |

Плюс инварианты RPC (тоже pgTAP, кейсы 8–12 DATABASE.md): двойной `create_shop_order` при балансе на один — второй падает; повторный `confirm_voice_batch` с тем же `client_request_id` — тот же result без новых строк; повторный `overdue_sweep` — один штраф; `fn_rating` при `rating_mode='top5'` от employee — ≤5 строк + своя.

Правило: **новая таблица = RLS в той же миграции = минимум один негативный pgTAP-кейс в том же PR.** Позитивного («видит своё») недостаточно — DoD требует именно негативный.

## 3. Unit-критичное (Vitest, `pnpm test`)

Обязательные сьюты; фикстуры — на русском, реальные паттерны:

- **`matchName`** (lib/matchers): падежи и уменьшительные («Марату», «Айгуль», «Ерлану Б.»); коллизия «два Ерлана» из seed → возврат кандидатов, не авто-выбор; пороги и отрыв (D-16) читаются из конфига — тест фиксирует поведение на граничных score; 0 кандидатов → «не распознан», никогда «наугад».
- **Конвенции времени** (D-15): «до обеда»=13:00, «к вечеру»=18:00, «на неделе»=пт 18:00 в Asia/Aqtobe → корректный UTC ISO; без дедлайна → null (парсер не выдумывает); переходы через полночь/выходные.
- **Баланс и hold**: баланс = SUM(point_transactions), никакого поля; hold-final (D-10): заказ → −price, отмена → +price ровно на сумму hold по order_id, выдача → ноль новых транзакций; «заморожено» = сумма hold по pending|approved.
- **Идемпотентность**: повтор мутации с тем же `client_request_id` не создаёт дублей и возвращает тот же результат (unit — на уровне обёрток/очереди оффлайна; сквозное — pgTAP-кейс §2).
- **Статусные переходы**: матрица `trg_task_status_guard` продублирована таблицей в тесте — допустимые проходят, недопустимые (sent→done, done→accepted, любой выход из revoked) отклоняются; ролевые ограничения: закрыть (pending_review→done|rework) и отозвать может только директор.

## 4. Evals парсера (`pnpm eval:parser`, `tests/ai/parser_evals.jsonl`)

Один корпус = СТТ-гейт = few-shot = evals (G.8). Формат фикстуры — JSONL, по строке на кейс:

```json
{"id":"e-042","source":"voice","transcript":"марат кп казхром завтра до обеда, ерлану +10",
 "expected":{"entities":[{"kind":"task","assignee_query":"Марат","deadline_iso":"<резолвится от frozen_now>"},
                          {"kind":"points","assignee_query":"Ерлан","amount":10}]},
 "frozen_now":"2026-08-17T09:00:00+05:00"}
```

`frozen_now` обязателен — относительные даты сравниваются детерминированно. Скоринг: точность адресата (доля сущностей с верным assignee после matchName) и entity F1 (по kind+ключевым полям). Отчёт пишется в файл и прикладывается к PR.

**Гейты: assignee ≥ 97%, entity F1 ≥ 90%.** Правило из CLAUDE.md: **PR, трогающий промпт парсера, схему сущностей или few-shot, без приложенного результата `pnpm eval:parser` не мержится.** Ниже гейта — PR не мержится, даже если «на глаз стало лучше». Корпус пополняется из реальных правок директора (`ai_logs.edit_fields`, staging `inbox_items`) — каждая систематическая ошибка становится фикстурой до фикса промпта.

## 5. Девайс-смоук перед каждым демо (реальные устройства, не эмулятор)

Устройства: бюджетный Android (Redmi-класс) + iPhone (D-26). Чек-лист:

- [ ] **Аудио кросс-платформенно:** запись голосового на Android → воспроизведение на iPhone (и обратно); формат по матрице mimeType (audio/mp4 первым, G.8).
- [ ] **Push на MIUI:** уведомление доходит на Xiaomi/Redmi при выключенной оптимизации батареи (шаг онбординга, H.14); телефон заблокирован ≥5 минут.
- [ ] **Свернул/развернул:** приложение в фоне 5 минут, за это время создана задача → развернул → лента актуальна без перезагрузки (realtime + refetch).
- [ ] **Оффлайн:** самолётный режим → «Принял» на карточке → сеть → действие доезжает ровно один раз (идемпотентность, дублей в БД нет).
- [ ] **Cold start по пушу:** тап по push при убитом приложении → интерактивная карточка задачи < 2–3 с на Redmi-классе.
- [ ] **Голосовое не теряется:** обрыв сети сразу после записи → аудио в Storage, ретрай транскрипции без перезаписи.

Любой красный пункт — демо не проводим, чиним.

## 6. Definition of Done фичи

Фича готова, когда всё ниже выполнено (расширение краткой версии из CLAUDE.md):

1. **Мобильный смоук на двух платформах:** визуально проверено в эмуляции iPhone SE и среднего Android; фичи с аудио — реальный кросс-девайс смоук «Android-запись → iPhone-воспроизведение» (§5).
2. **RLS — негативный тест:** для каждой новой таблицы/политики есть pgTAP-кейс «чужое не видно / запретный insert падает» (§2), прогнан, зелёный.
3. **Realtime без перезагрузки:** свернул на 5 минут → развернул → данные актуальны; изменение в БД видно на открытом экране без F5.
4. **Оффлайн не теряет:** действие без сети доезжает после появления сети ровно один раз (`client_request_id`); голосовое сохранено в Storage до любых AI-вызовов при любом сбое.
5. **Ошибки сети/AI обработаны:** STT упал → «Не расслышал, отправить ещё раз?» с ретраем по сохранённому аудио; парсер упал → сырой транскрипт с «Повторить»; у пользователя всегда понятное состояние, вызов залогирован в ai_logs.
6. **Тесты по слоям:** затронута критичная логика §3 → unit-тесты; промпт/схема/few-shot → evals с приложенным результатом (§4).
7. **Учёт:** статус задачи обновлён в `tracker/index.html`, запись в WORKLOG.md, conventional commit.

## 7. Регрессия: раскатка недели 9 и каждый новый клиент (V-02)

**Перед раскаткой на всю компанию (неделя 9):** полный прогон `pnpm test` + `pnpm test:rls` + `pnpm eval:parser` (гейты §4) → девайс-смоук §5 на обоих устройствах → замер доставляемости push на ≥5 реальных телефонах сотрудников (H.14; Huawei без GMS → Telegram-канал) → проверка эскалации Telegram (push проигнорирован → дубль через таймаут) → бэкап prod и подтверждённая процедура восстановления (SETUP.md §7).

**Перед передачей каждого нового инстанса клиенту (V-02):** это часть чек-листа приёмки инстанса (SETUP.md §5): pgTAP-сьют прогнан **на самом инстансе** (не «на dev было зелёно»), смоук-чек-лист деплоя SETUP.md §3.10 пройден на устройстве, версия миграций = HEAD `main`, `company.settings` соответствует анкете. Инстанс без зелёной регрессии клиенту не передаётся.
