Специалисты НЕ должны прочитать текущие доки (`docs/*`, `/reviews/*`) — иначе они будут якориться на уже выбранных решениях. Поэтому:

## Продуктовый бриф (вставлять специалистам дословно, целиком)

```
ПРОДУКТ (внутренний, компания ~45 человек, Казахстан; горизонт — SaaS для похожих компаний СНГ):

Директор управляет компанией голосом. Утром наговаривает поток: объявления,
поручения конкретным людям с дедлайнами, начисления бонусных очков. Система
превращает речь в структурированные объекты, показывает директору на
подтверждение (правки — минимальными касаниями), затем разносит адресатам.

Сотрудники получают поручения на свои личные телефоны, отвечают: принял /
уточнить / не могу; отчитываются текстом, фото и голосом. Закрывает задачу
только директор. Есть общая лента объявлений, рейтинг сотрудников по очкам,
магазин мерча за очки, и ТВ-экран в кабинете директора с живой лентой
происходящего, которым директор управляет с телефона.

Директор также задаёт системе вопросы голосом: «что там по Казхрому?»,
«кто не отчитался?» — и получает ответы по данным системы.

ЖЁСТКИЕ УСЛОВИЯ:
- Речь: русская с казахскими именами и вставками казахского; шум (цех, машина).
- Устройства сотрудников: личные телефоны, много бюджетных Android
  (Xiaomi/Redmi, встречается Huawei без Google-сервисов), часть iPhone.
  Корпоративного MDM нет. Установка должна быть тривиальной: онбординг
  делается очно за 2 минуты.
- Связь: на объектах (стройплощадка) плохой интернет; действия сотрудника
  не должны теряться.
- Уведомления критичны: «сотрудник не увидел поручение» = провал продукта.
  Сегодня вся коммуникация компании живёт в Telegram и WhatsApp.
- Директор: 37 лет, требователен к полировке (эталон — Kaspi/Telegram),
  ненавидит лишние действия. Скорость «голос → карточка на подтверждении»
  — главный конкурентный параметр против «просто написать в Telegram».
- Разработчик: ОДИН человек, пишет преимущественно руками ИИ-агентов
  (Claude Code), срок — 12 недель до полного развёртывания на компанию,
  первый пилот на 5 людях — через 4–5 недель. Бюджет на облака/API —
  скромный (десятки долларов в месяц), на разовые покупки — сотни.
- После запуска систему сопровождает тот же один человек.
- Персональные данные — закон РК; публичный рейтинг требует согласий.
- Геймификация — часть продукта: анимации «полёта задачи», очки, streak,
  магазин. Должна работать плавно на бюджетном Android.
```

## Пять специалистов + еретик

Запусти всех ШЕСТЕРЫХ параллельно (одно сообщение, 6 вызовов Agent tool). Отчёты — в `/reviews/alt/`, на русском.

Общий формат отчёта (вставлять в каждый промпт):

```markdown
# Альтернативы: <роль>
## Постановка: как я понял задачу своей области из брифа
## Кандидат A / B / C — для каждого:
   суть, сильные стороны ИМЕННО для этих условий, слабые/риски,
   влияние на 12-недельный срок соло-разработчика с ИИ-агентами,
   стоимость (месячная и разовая)
## Мой выбор и почему (с учётом: скорость до пилота, сопровождение одним
   человеком, качество генерации кода ИИ-агентами для этой технологии)
## Что бы заставило меня передумать (условия-триггеры)
## Неочевидное: что в этой области все обычно упускают в подобных продуктах
```

Требование к глубине: каждый кандидат — не абзац-отписка, а честный разбор; минимум 3 кандидата на специалиста; «модно» — не аргумент, «скучно и надёжно» — аргумент.

### 1. `reviews/alt/ALT_PLATFORM.md` — Архитектор платформы доставки
Главный вопрос: **в какой форме продукт попадает на телефоны сотрудников?** Кандидаты обязаны включать минимум: (а) PWA; (б) нативная кроссплатформа (React Native/Expo или Flutter, дистрибуция без сторов — возможна ли на iOS без MDM?); (в) **Telegram Mini App + бот** (вся компания уже живёт в Telegram: уведомления, установка и авторизация бесплатны «из коробки» — разобрать всерьёз, включая ограничения: оффлайн, пуш-логика, зависимость от платформы, риски блокировок мессенджеров в регионе); (г) гибриды (директору — одно, сотрудникам — другое; ТВ — третье). Отдельно: у директора и сотрудника кардинально разные требования — обязана ли это быть одна платформа?

### 2. `reviews/alt/ALT_FRONTEND.md` — Senior Frontend
Фреймворк и рантайм UI при разных платформенных сценариях: Next.js vs Vite+SPA vs Remix/TanStack Start vs Expo/RN vs Flutter vs Svelte. Оффлайн-архитектура (очереди, local-first: Replicache/PowerSync/RxDB — стоит ли?), анимационный стек для game feel на бюджетном Android, realtime-обновления. Оцени отдельно: с какой технологией ИИ-агенты генерируют наиболее рабочий код (объём обучающих данных, зрелость экосистемы).

### 3. `reviews/alt/ALT_BACKEND.md` — Senior Backend/Infra
BaaS vs самосбор: Supabase vs Firebase vs Convex vs PocketBase vs Appwrite vs «VPS + Postgres + свой API» (Hetzner/местный хостинг — данные в РК?). Serverless vs долгоживущий сервер (очереди, cron, вебхуки, стриминг аудио). Доставка уведомлений как система (push/Telegram/SMS-фолбэки). Деплой и среды для соло-разработчика. Отдельно: где реально живут данные по закону РК и что это значит для выбора.

### 4. `reviews/alt/ALT_DATA.md` — Специалист по данным
Модель данных для «поток событий + задачи + очки + лента + рейтинг»: классическая реляционная vs event sourcing vs гибрид (append-only журнал + проекции). СУБД: Postgres vs SQLite (Turso/litestream — для такого масштаба?) vs документная. Realtime-синхронизация клиентов как проблема данных. Мультитенантность для SaaS-перспективы: схемы, изоляция, цена ошибки. Что из этого потянет один человек и сгенерируют агенты без тонких багов.

### 5. `reviews/alt/ALT_AI.md` — Специалист по AI-конвейеру
Речь→структура: (а) классика STT (какой провайдер для русско-казахской смешанной речи в шуме: Whisper/gpt-4o-transcribe/Deepgram/Gemini/ElevenLabs Scribe/локальные модели?) + LLM-парсер; (б) **аудио напрямую в мультимодальную LLM** (минуя отдельный STT — Gemini/GPT-4o audio: качество на казахских именах? стоимость? латентность?); (в) realtime/streaming конвейеры (распознавание во время записи). LLM для парсинга и для вопросов к данным: Claude vs GPT vs Gemini vs локальные; агентные вопросы к БД — tool use vs text-to-SQL vs семантический слой. TTS для сводок. Оценка помесячных затрат каждого варианта на объёмах брифа.

### 6. `reviews/alt/ALT_HERETIC.md` — Еретик (главный по «а надо ли это строить?»)
Роль: атаковать саму постановку. Обязательные вопросы: Можно ли НЕ строить продукт — собрать на готовом (Bitrix24/Planfix/Asana/ClickUp + голосовой слой поверх? n8n/Make + Telegram-бот?) и потратить 12 недель на другое? Что если продукт — это только бот в Telegram без своего UI вообще? Что если главная ценность — не задачи, а «структурированный голос» (и продавать надо парсер, а не платформу)? Где концепция переусложнена (ТВ? магазин? game feel?) и что бы еретик вычеркнул, чтобы пилот был через 2 недели, а не 5? Какие риски все проигнорировали (директор перестанет пользоваться через месяц — что тогда со всем стеком?). Единственный из шести, кому МОЖНО прочитать `docs/CONCEPT.md` — но только после того, как сформулирует атаки от брифа.

## Финал: сравнение с текущим чертежом (делаешь сам)

После всех отчётов прочти `docs/CONCEPT.md`, `CLAUDE.md` (текущий стек: Next.js+PWA / Supabase / Vercel / Whisper+Claude) и `reviews/SYNTHESIS.md` (блокеры раунда 1). Напиши `reviews/alt/ALT_SYNTHESIS.md`:

1. **Таблица по слоям** (платформа / фронт / бэк / данные / AI): текущий выбор ↔ лучшая альтернатива от специалистов ↔ вердикт: `подтверждён` / `сменить` / `гибрид` / `отложенная опция` — с ценой переключения сейчас vs позже.
2. **Упущенное**: идеи из отчётов, которых нет ни в CONCEPT, ни в раунде 1 — то самое «может мы что-то упустили».
3. **Совместимость с раундом 1**: если альтернатива снимает блокеры раунда 1 (например, Telegram Mini App снимает всю боль iOS-push и аудиоформатов) — отметь это явно; если создаёт новые — тоже.
4. **Рекомендация тимлида**: финальный стек/подход одним абзацем + 3 главных аргумента + что закладываем как «план Б».
5. Помни о рамке: 12 недель, один человек, пилот через 4–5 недель. Красивая архитектура, срывающая пилот, — проигрыш. Но и «оставить как есть», если альтернатива очевидно сильнее, — трусость. Решай честно.

Затем append-запись в `WORKLOG.md` (формат внутри файла): итоги, вердикты по слоям, ссылка на ALT_SYNTHESIS.md; открытые развилки — в раздел «Открытые вопросы» одной строкой каждая.
