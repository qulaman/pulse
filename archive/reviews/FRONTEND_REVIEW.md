# Ревью: Senior Frontend — WAG Pulse

## Вердикт

Готовность фронтенд-области к агентной разработке — **5/10**. Продуктовая логика экранов описана отлично (редкий случай, когда UX-поведение прописано до жестов), но инженерный слой под ней дырявый: не выбран SW-фреймворк, не решена главная кроссплатформенная проблема — формат аудио iOS↔Android (записанное на Android голосовое не воспроизведётся на iPhone — это ломает «сердце продукта»), не задан state manager, не специфицированы офлайн-очередь, жизненный цикл Realtime в свёрнутой PWA и способ измерения целевых метрик. Агент, строящий по этим докам, будет гадать минимум в десяти местах, и половина его догадок сломается именно на iOS. Неделя доработки спеки (или один документ FRONTEND_TECH.md с решениями ниже) поднимает готовность до 8/10.

## Критические проблемы

### 1. Формат аудио: webm/opus не играет на iOS — голосовые задачи не услышит сотрудник с iPhone

**Где:** FRONTEND.md §Производительность: «Аудио: opus/webm, битрейт ~24kbps»; BACKEND.md §1: «webm/opus или m4a, из MediaRecorder»; CLAUDE.md принцип 5: «Аудио директора всегда сохраняется... и доступно сотруднику».

**Суть:** MediaRecorder на iOS Safari не умеет `audio/webm;codecs=opus` — отдаёт `audio/mp4` (AAC). И наоборот: iOS Safari **не воспроизводит** webm/opus (поддержка opus у Apple — только в CAF/чистом контейнере, поведение нестабильно по версиям). Итог: директор с Android записывает webm → сотрудник с iPhone видит плеер, который молчит. Принцип 5 CLAUDE.md нарушен архитектурно.

**Последствие:** ключевой флоу («аудио доступно сотруднику») не работает для части парка устройств; обнаружится на пилоте недели 5, чинить придётся в панике.

**Решение (зафиксировать в доке):**
1. Матрица записи: пробовать mimeType в порядке `audio/mp4` (Chrome 126+, Safari — играет везде) → `audio/webm;codecs=opus` → `audio/webm`. Выбранный mimeType слать на бэкенд и хранить в метаданных файла.
2. Если в компании остаются webm-записи — серверный транскод в AAC (Edge Function + облачный транскодер или очередь на отдельном воркере; на Vercel Edge ffmpeg не поднять — учесть).
3. Смоук-тест воспроизведения «Android-запись → iPhone-плеер» включить в Definition of Done голосового конвейера (неделя 3). Whisper, к счастью, ест оба формата — проблема только в playback.
4. `audioBitsPerSecond: 24000` на iOS игнорируется — «~24kbps» описывать как best-effort, не как контракт.

### 2. serwist vs next-pwa не выбран — а это первое, что агент должен установить

**Где:** CLAUDE.md §Стек: «PWA: next-pwa / serwist»; FRONTEND.md §PWA: «service worker (serwist/next-pwa)».

**Суть:** это не синонимы. `next-pwa` фактически заброшен (workbox 6, проблемы с App Router и Next 15), `@serwist/next` — живой преемник от мейнтейнера workbox-совместимого кода. Агент, выбравший next-pwa, получит конфликты сборки на Next 15 и перепишет всё позже.

**Решение:** зафиксировать **@serwist/next**, убрать слэш из обоих доков. Дополнительно указать: SW пишем свой на базе serwist (не авто-генерация), потому что нужны кастомные обработчики `push`, `notificationclick` (deep-link по `tag: task_id`) и POST-роут Web Share Target — это в доке сейчас нигде не сказано.

### 3. «Голос → карточка < 3 сек» физически недостижима в лоб и ничем не меряется

**Где:** FRONTEND.md §Производительность: «голосовое → экран подтверждения < 3 сек»; CONCEPT §1: «голосовое → карточка < 3 сек»; PLAN неделя 3: «< 3 сек на распознавание».

**Суть:** последовательная цепочка = upload аудио (30-сек фраза ≈ 100–300КБ, на «стройплощадке с плохой связью» это уже 1–3 сек) + Whisper API (1.5–4 сек на 30-сек аудио) + Claude Haiku парсинг (0.7–2 сек). Сумма p50 ≈ 4–7 сек. Метрика провалена ещё до написания кода, а три дока считают её от разных точек («распознавание» ≠ «до экрана подтверждения»).

**Решение:**
1. Параллелить: писать MediaRecorder с `timeslice` и стримить чанки на сервер **во время записи** — к моменту отпускания кнопки аудио уже на сервере, остаётся только STT+parse.
2. Переопределить метрику: «от отпускания кнопки до интерактивного /confirm, p50 ≤ 3 c, p90 ≤ 6 c на 15-секундной фразе, 4G».
3. Измерение: тайминги каждого этапа (upload / stt / parse / render) писать в `ai_logs` (поле там уже есть — latency, расширить до разбивки) + web-vitals в Vercel Analytics. Пока экран ждёт — шиммер-скелетон из FRONTEND.md уже предусмотрен, это правильно.

### 4. Realtime в свёрнутой PWA: подписки умирают молча — «живая лента» будет показывать вчерашний день

**Где:** FRONTEND.md §Пульс п.3 («Realtime insert → элемент вплывает»), §Производительность («1 запрос + 1 подписка»); heartbeat/reconnect описан **только** для /tv (§ТВ-режим).

**Суть:** iOS Safari и Android агрессивно рвут WebSocket у свёрнутой PWA. supabase-js сам не гарантирует восстановление подписки после длинного фона, и главное — **события, пришедшие за время разрыва, потеряны навсегда**: лента после разворачивания выглядит живой, но неполна. Для дашборда, по которому директор принимает решения, это хуже, чем отсутствие Realtime.

**Решение:** зафиксировать паттерн «snapshot + subscribe»: на `visibilitychange → visible` и `online` — (а) рефетч агрегата/ленты (у ленты — курсор `created_at` последнего элемента), (б) teardown и пересоздание каналов. Реализовать один хук `useRealtimeQuery(queryKey, channelSpec)` и обязать все экраны использовать только его. Записать в Definition of Done: «свернул на 5 минут → развернул → лента актуальна без pull-to-refresh».

### 5. Офлайн-очередь в IndexedDB названа, но не спроектирована — а Background Sync на iOS нет

**Где:** FRONTEND.md §PWA: «очередь неотправленных сообщений/аудио в IndexedDB с авто-ретраем» — одна строка на всю подсистему.

**Суть:** агент должен угадать: схему записей, что именно ставится в очередь (только аудио? текст? фото-отчёты? принятие задачи?), стратегию ретраев, поведение при закрытой вкладке. Background Sync API в Safari отсутствует — «авто-ретрай» возможен только пока приложение открыто/разворачивается. Плюс идемпотентность: `client_request_id` в BACKEND.md есть только у /voice/confirm — ретраи transcribe и сообщений композера создадут дубли.

**Решение:** мини-спека в FRONTEND.md:
- Store `outbox`: `{id(uuid=client_request_id), kind: 'voice'|'message'|'photo'|'ack'|'status', payload, blob?, created_at, attempts, next_retry_at, status: 'queued'|'sending'|'failed'}`.
- Триггеры отправки: `online`, `visibilitychange`, старт приложения, ручной тап по бейджу «N не отправлено» (бейдж — обязательный UI-элемент, сейчас не описан).
- Backoff 5с/30с/2м, после 5 попыток — статус failed + явный UI.
- `client_request_id` обязателен на **всех** мутирующих эндпоинтах (правка в BACKEND.md).
- Blob-ы аудио в IDB считать против квоты; на iOS для установленной PWA eviction мягче, но лимит ~1ГБ — чистить отправленное.

### 6. Хаптики на iOS: `navigator.vibrate` не существует, «iOS через тапы» — не решение

**Где:** FRONTEND.md §Дизайн-принципы: «Хаптики (navigator.vibrate / iOS через тапы): подтверждение голосового, свайп-приёмка, удары „стрел"...».

**Суть:** `navigator.vibrate` в iOS Safari не реализован вообще. Фраза «iOS через тапы» не имеет технического смысла — веб-API хаптик на iOS нет (существует только хак с `<input type="checkbox" switch>` в iOS 17.4+, непригодный для произвольных моментов). Агент потратит день на поиск несуществующего API или вставит карго-культ.

**Решение:** переписать пункт: «Хаптики — прогрессивное улучшение, только Android (`navigator.vibrate`, паттерны ≤30мс). На iOS хаптик отсутствует — компенсируем микро-скейлом кнопки и звуком (вне тихого режима). Обёртка `lib/haptics.ts` с no-op на iOS».

### 7. Долгое нажатие FAB (запись) сломается о системные жесты iOS

**Где:** FRONTEND.md §Кнопка ввода: «Зажал — голос... отпустил — отправка».

**Суть:** длинный тап на iOS вызывает callout/выделение текста/контекстное меню; палец, уползший с кнопки, прервёт запись; случайный скролл во время удержания — тоже. Walkie-talkie-паттерн в вебе требует явной обвязки, которая нигде не описана. Плюс: разрешение микрофона на iOS в standalone-PWA запрашивается заново по сессиям — первый «зажал» уткнётся в системный диалог и запись не начнётся (директор решит, что «не работает»).

**Решение:** спецификация в FRONTEND.md: Pointer Events (`setPointerCapture`), `touch-action: none`, `-webkit-user-select: none`, `-webkit-touch-callout: none`, `contextmenu preventDefault`; порог 250мс между тапом (текст) и удержанием (голос); свайп вверх при удержании = отмена записи (стандарт мессенджеров — сюда же); отдельный первый онбординг-шаг «дай доступ к микрофону» с тестовой записью, а не в боевом флоу.

## Дыры проектирования (агент будет гадать)

### 1. State manager не задан нигде
CLAUDE.md перечисляет стек без слова о состоянии. **Рекомендация:** TanStack Query v5 — единственный владелец серверного состояния (кеш = источник для optimistic-обновлений «данные мгновенно, эффект поверх»); Zustand — только эфемерное UI (состояние записи, очередь EffectsLayer, тихий режим); никакого Redux/Context-зоопарка. Realtime-события пишутся в кеш Query через `setQueryData` внутри `useRealtimeQuery` из проблемы №4. Зафиксировать в CLAUDE.md §Стек.

### 2. Куда попадает пользователь на `/` и как охраняются route groups
Структура `/(director)/pulse`, `/(employee)/feed` не задаёт URL-неймспейсов (groups невидимы в URL) и не задаёт, кто куда редиректится. **Рекомендация:** middleware.ts: нет сессии → /login; role=director → /pulse; иначе → /feed; role-гард в layout каждой группы (server component, читает profile). Прописать в FRONTEND.md таблицу «роут → роли → layout».

### 3. Контракт данных экрана /confirm
FRONTEND.md описывает чипы и свайпы, но не форму данных: что приходит от /api/voice/parse при неоднозначном матчинге (BACKEND.md: «вернуть варианты»)? **Рекомендация:** зафиксировать TS-тип: `entity.assignee: {status:'matched'|'ambiguous'|'unmatched', user_id?, candidates?: {user_id, full_name, score}[]}`; чип «не распознан» — красный, блокирует «Отправить» пока не выбран вручную. Один shared-файл `lib/types/parse.ts`, на который ссылаются оба дока.

### 4. Web Share Target: метод, роут, обработка
Названа фича — нет спеки. **Рекомендация:** manifest `share_target: {action: '/share-target', method: 'POST', enctype: 'multipart/form-data', params: {title, text, url}}`; POST принимает route handler `/app/share-target/route.ts` → кладёт текст в sessionStorage/query → redirect на /confirm с `source:'shared'`. Явно записать: **работает только на Android в установленной PWA; на iOS фичи нет** (см. вопросы владельцу — телефон директора).

### 5. Пагинация лент — не упомянута ни разу
/feed («отскролленная к задаче»), живая лента Пульса, /ether, ТВ-лента. Через месяц пилота в feed сотни сообщений. **Рекомендация:** cursor-based (created_at + id), страница 30, `useInfiniteQuery`; «отскроллить к задаче» = загрузка окна вокруг task_id (endpoint «messages around anchor»), не скролл через всю историю. Виртуализация — только если профилирование покажет необходимость (не авансом, по принципу CLAUDE.md).

### 6. «Стрела летит к аватарке исполнителя» — а если аватарки нет на экране?
§Game Feel: снаряд летит «к аватарке исполнителя», но на /confirm после мульти-сущностей аватарка может быть за скроллом или её нет вовсе. **Рекомендация:** контракт EffectsLayer: `fireProjectile({fromRect, toRect?})`; цель ищется по `data-effect-target="user:{id}"` через getBoundingClientRect; нет цели в вьюпорте → короткая версия (карточка сворачивается и улетает за верхний край, 300мс). Записать в каталог эффектов.

### 7. Библиотеки эффектов: «canvas/tsParticles/Lottie» — вилка на 400КБ
tsParticles полный ~150КБ+, lottie-web ~250КБ — вместе съедают бюджет холодного старта <2c. **Рекомендация:** свой canvas-эмиттер (~2КБ, частицы это 100 строк) для очков/искр; для огня/конфетти — `@lottiefiles/dotlottie-web` (меньше и быстрее lottie-web) с `next/dynamic` и загрузкой после first paint; tsParticles не брать. Деградация: `hardwareConcurrency ≤ 4 || deviceMemory ≤ 2` → полурежим (вдвое меньше частиц, без screen shake), плюс прописанный prefers-reduced-motion.

### 8. «<2 сек холодный старт» — не сказано что и на чём мерить
**Рекомендация:** определить как LCP ≤ 2.0c и TBT ≤ 300мс на профиле «Moto G Power / 4x CPU throttle, Fast 3G» в Lighthouse CI (порог в CI на PR) + полевые web-vitals через Vercel Speed Insights. Следствие для агента: JS-бюджет initial route ≤ 200КБ gz — Recharts, dotLottie, EffectsLayer, AudioPlayer только через dynamic import.

### 9. Звуки существуют или нет?
«Тихий режим — без звуков и TTS» подразумевает, что звуки есть, но каталог Game Feel описывает только визуал и хаптики. Агент будет гадать, озвучивать ли стрелу. **Рекомендация:** v1 — без звуковых эффектов вообще (кроме воспроизведения голосовых), тихий режим глушит TTS и автоплей аудио. Звуковой дизайн — отдельной итерацией. (И см. вопрос владельцу.)

### 10. /app/dev песочницы компонентов — в проде?
§Компонентная база: «каждому компоненту страница-песочница в /app/dev (только dev-режим)». Механизм не указан. **Рекомендация:** в layout `/app/dev/layout.tsx`: `if (process.env.NODE_ENV === 'production') notFound()` — одна строка, но её надо потребовать явно, иначе песочницы уедут в прод с обходом RLS-паттернов.

## Противоречия между документами

1. **Формат аудио.** FRONTEND.md §Производительность: «Аудио: opus/webm, битрейт ~24kbps» ↔ BACKEND.md §1: «webm/opus **или m4a**, из MediaRecorder». Бэкенд знает про iOS, фронтенд-док — нет; агент фронта закодирует только webm. Привести FRONTEND.md к матрице форматов (критическая проблема №1).
2. **Сроки MVP.** CONCEPT §7: «MVP — 3 нед» ↔ PLAN_12_WEEKS: MVP = недели 1–4 («Неделя 4 — ✅ MVP готов»). Мелочь, но агент, планирующий по CONCEPT, срежет скоуп недели 4.
3. **TTS-сводки: итерация 3 или 4+?** CONCEPT §6: «TTS-сводки — OpenAI TTS / ElevenLabs (итерация 3)» ↔ FRONTEND.md §Пульс п.1: «кнопка 🔊 сводки (итерация 4+)» ↔ CONCEPT §7 и CLAUDE.md очерёдность: TTS в этапе +4/5. Зафиксировать: итерация 4+, поправить CONCEPT §6.
4. **Vercel AI SDK.** PLAN неделя 7: «Vercel AI SDK: streamText + tools + useChat» ↔ CLAUDE.md §Стек («не менять без обсуждения») — AI SDK в стеке отсутствует, и это отдельная клиентская зависимость + паттерн стриминга, влияющий на фронт (useChat = свой state-слой рядом с TanStack Query). Либо внести в CLAUDE.md, либо неделя 7 делается на голом Claude API.
5. **Состав «Требует вас».** CONCEPT §3.3: стопки «На приёмке / Вопросы / Просрочки / **Заявки магазина**» ↔ FRONTEND.md §Пульс п.2: заявки магазина не упомянуты. Уточнить состав стопок в FRONTEND.md (и что по тапу на «Заявки» — тоже свайп-режим? У заявки магазина другие действия: подтвердить/отклонить, а не принято/доработка).
6. **Авторизация ТВ.** DATABASE.md §RLS: ТВ работает «через отдельный ограниченный token/anon-роль... к событийным view» ↔ BACKEND.md §5: «/tv слушает канал», права на **публикацию** описаны, а как анонимный ТВ-клиент **подписывается** на приватный broadcast-канал `tv_control:{company_id}` (Realtime authorization требует авторизованного клиента) — не сказано нигде. Решить: длинный подписанный URL-токен для ТВ (`?tv_token=`) → отдельный Supabase-JWT c ролью `tv` → и Realtime, и view через него.

## Улучшения

- **[high] Стриминг загрузки аудио во время записи** (timeslice-чанки) — главный рычаг метрики <3 сек, см. крит. №3.
- **[high] Бейдж офлайн-статуса и очереди** («N не отправлено», тап = ретрай) в шапке feed/pulse — без него офлайн-очередь невидима и не вызывает доверия на стройплощадке.
- **[high] Единый хук `useRealtimeQuery`** (snapshot+resubscribe+setQueryData) как обязательный примитив — переводит крит. №4 из «помнить всем» в «нельзя сделать иначе».
- **[mid] Скелетоны как контракт**: для каждого экрана зафиксировать layout-скелетон (FRONTEND.md декларирует «скелетоны, не спиннеры», но не какие) — иначе каждый агент нарисует свои и будет layout shift.
- **[mid] `<AudioPlayer>` волна**: не декодировать аудио на клиенте ради волны (decodeAudioData на 3-минутном файле на Redmi = фриз) — генерировать массив пиков на сервере при загрузке (или в момент записи из AnalyserNode) и хранить в meta.
- **[mid] Push-подписка: обработка «отказал»** — на iOS отказ в разрешении необратим без переустановки PWA; после отказа сразу предлагать привязку Telegram, не пилить пользователя повторными запросами.
- **[mid] ТВ: обновление версии** — location.reload() в 04:00 хорош, но добавить в SW проверку новой версии и `skipWaiting` по каналу tv_control (`{mode:'reload'}`) — деплой не должен ждать ночи.
- **[low] `dvh` вместо `vh`** и `viewport-fit=cover` + safe-area-inset для FAB и композера — обязательная строчка для standalone iOS, иначе FAB спрячется за home-indicator.
- **[low] AnimatePresence popLayout уже прописан** — добавить лимит DOM-элементов живой ленты (например 50) с усечением хвоста, особенно для /tv (24/7).
- **[low] Recharts на ТВ** — один bar chart не оправдывает 90КБ на киоске; для /tv нарисовать столбики div-ами/SVG руками.

## Вопросы владельцу продукта

1. **Какой телефон у директора — iPhone или Android?** Если iPhone: Web Share Target недоступен (фича «письмо заказчика за два тапа» умирает), хаптиков нет, пуши требуют iOS 16.4+ и установки на главный экран. Это меняет приоритеты недель 2–3.
2. **Парк устройств сотрудников:** доля iPhone (и старше iOS 16.4?), доля «проблемных» Android (Xiaomi/Huawei без Google Push)? Определяет, является ли Telegram fallback-ом или фактически основным каналом — и сколько вкладывать в Web Push UI.
3. **Фирменный цвет и логотип WAG** — «один акцент — фирменный цвет WAG», «снаряд в стиле WAG», «лого WAG → перестроение» на ТВ: нужны hex/ассеты/брендбук до недели 1, иначе агент выдумает бренд.
4. **Звуки в приложении** — нужны ли звуковые эффекты game feel в принципе (офис, открытые кабинеты)? Тихий режим намекает «да», каталог молчит.
5. **Будет ли выдан тестовый бюджетный Android (Redmi-класс) и iPhone** — Definition of Done требует проверку на обоих; без физических устройств пункт невыполним (iOS-симуляция в Chrome ≠ Safari).
6. **Гостевой режим ТВ**: кто и когда решает включать `?guest=1` — постоянная настройка кабинета или тумблер в пульте? Влияет на UI пульта.

## Чего не хватает в доках для агентной разработки

1. **Дизайн-токены файлом**: полная палитра (акцент WAG, статусные, золотой), шрифтовая пара (гарнитура не названа вообще), шкала кеглей, радиусы, тени — `tailwind.config` + `docs/DESIGN_TOKENS.md`. Сейчас заданы только два hex фона.
2. **TS-контракты API как код**: типы запросов/ответов /api/voice/*, /api/tv/control, форма entity с вариантами матчинга (`lib/types/*.ts`) — прозой в BACKEND.md недостаточно, агенты фронта и бэка разойдутся на первом же поле.
3. **Спека офлайн-очереди** (схема outbox, триггеры, backoff, UI-статусы) — см. крит. №5.
4. **Матрица аудио-форматов** запись/воспроизведение по платформам + решение по транскоду — см. крит. №1.
5. **Фикстуры фраз директора**: 30 реальных фраз СТТ-гейта недели 1 оформить как тест-фикстуры (`fixtures/phrases.json`: транскрипт → ожидаемые entities) — они же тесты парсера, которые CLAUDE.md требует; фронту из них же — моки для /confirm и /app/dev.
6. **Полный manifest.json**: name/short_name, иконки (maskable!), splash для iOS (apple-touch-startup-image), share_target, display, theme_color — сейчас одна строка «manifest + service worker».
7. **Каталог состояний экранов**: empty/loading/error/offline для каждого экрана (что видит сотрудник без задач? Пульс без событий? /confirm при упавшем Claude?) — BACKEND.md описывает ошибки AI, но не остальные состояния.
8. **Спека жестов**: пороги свайпов SwipeDeck (расстояние/скорость/углы для право/лево/верх), тайминг long-press vs tap для FAB, отмена записи — числа, а не прилагательные.
9. **Perf-контракт в CI**: конфиг Lighthouse CI с порогами (LCP/TBT/бюджет JS) на PR — иначе «<2 сек» останется пожеланием.
10. **Онбординг-флоу пошагово**: экраны установки PWA (iOS/Android отдельно), запрос микрофона, запрос push после первого действия, привязка Telegram — сейчас разбросано тремя фразами по трём докам, а это первое, что увидят все 45 человек.
