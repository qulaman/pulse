# Ревью: Senior Product/UX — WAG Pulse

## Вердикт

**Готовность области UX к агентной разработке: 6/10.** Концепция сильная и редко-цельная: ценностная метрика («убранные действия»), 3 кнопки, game feel с железными правилами — это уровень зрелого продукт-мышления. Но документы описывают «счастливый путь» и почти не описывают стыки: как пользователь попадает в систему (auth/онбординг не спроектирован вообще), что происходит при `declined`, как директор правит текст неверно распознанной задачи, что означают свайпы для трёх из четырёх стопок «Требует вас». Агент, строящий по этим докам, будет гадать в 10+ местах, и в половине из них угадает неправильно, потому что правильный ответ — продуктовый, а не инженерный. Неделя доработки спеки сэкономит три недели переделок.

## Критические проблемы

### К1. Онбординг и заведение аккаунтов не спроектированы вовсе
**Суть.** Нигде (CONCEPT, FRONTEND, BACKEND, DATABASE) не описано, как сотрудник попадает в систему: email/password? magic link? телефон? У прораба на стройке может не быть email. Нет флоу инвайта, нет флоу привязки `telegram_chat_id` (в DATABASE.md поле есть, но как оно заполняется — deep-link `/start` с кодом? вручную админом?). PLAN_12_WEEKS неделя 1 требует «Auth + роли», неделя 5 — «онбординг лично каждого», но онбордить не по чему.
**Последствие.** Блокирует недели 1–2 разработки; агент выберет email-magic-link и это не взлетит на аудитории «водители и завхозы».
**Решение.** Отдельная секция в BACKEND.md: директор/админ создаёт профиль → генерируется одноразовая ссылка-инвайт (QR для онбординга лично) → вход по телефону + OTP или по ссылке с установкой PIN. Привязка Telegram: кнопка в профиле → deep-link на бота с одноразовым токеном → бот пишет `telegram_chat_id`. iOS-онбординг: детект in-app-браузера (Telegram/WhatsApp) → экран «Открой в Safari» до инструкции «Добавь на экран» (FRONTEND.md упоминает оверлей, но не этот кейс — а инвайт-ссылку пришлют именно в мессенджер).

### К2. Экран подтверждения: текст задачи нельзя исправить
**Суть.** FRONTEND.md `/confirm`: «Правки — только тапом: чип исполнителя… чип дедлайна… свайп влево — удалить». Правка `title/body` не предусмотрена. При этом CONCEPT §8 прямо говорит: «Если директор хоть раз правит распознавание руками системно — бросит». Whisper на казахских названиях контрагентов («Казхром», «КазАзот») будет ошибаться регулярно — и единственный выход директора: удалить сущность и наговорить всё голосовое заново.
**Последствие.** Главный экран продукта не покрывает самый частый сбой конвейера. Директор бросает продукт на неделе 5–6.
**Решение.** Тап по тексту карточки → инлайн-редактирование title (клавиатура), плюс кнопка «🎤 переговорить эту сущность» — перезапись одной карточки без потери остальных. Правка суммы очков — тем же паттерном (сейчас у сущности `points` вообще нет описанных правок). Зафиксировать в FRONTEND.md.

### К3. `declined` — тупиковая ветка без переназначения
**Суть.** CLAUDE.md: статус-машина заканчивается на `declined` (сотрудник «Не могу» + причина). Что дальше — не описано ни в одном доке: директор видит причину где? Как переназначить на другого? Пересоздавать голосовое с нуля?
**Последствие.** Реальный кейс первой недели пилота («я в командировке») превращает задачу в мёртвую запись; агент не построит флоу, которого нет.
**Решение.** Карточка `declined` попадает в стопку «Требует вас» с действиями: «Переназначить» (выбор сотрудника чипом → задача клонируется в `sent` новому исполнителю, старая закрывается со ссылкой) / «Отменить задачу» / «Настоять» (возврат в `sent` с комментарием). Дописать в FRONTEND.md (Пульс) и в статус-машину.

### К4. Пилот стартует раньше мульти-сущностей: поведение парсера на «5 поручений одним голосовым» в MVP не определено
**Суть.** CONCEPT §7 и PLAN: MVP-парсер — «одна задача»; мульти-сущности — неделя 6. Пилот с обязательством «ВСЕ поручения через систему» — неделя 5. Директор гарантированно наговорит утром поток из объявления + 3 задач + очков в первый же день. Что делает парсер: берёт первую? падает? — нигде не сказано.
**Последствие.** Первое впечатление директора — «система поняла четверть того, что я сказал». По CONCEPT §8 это фатально для адаптации.
**Решение.** Либо (а) сдвинуть мульти-сущности до пилота (парсер и так возвращает массив `entities` по BACKEND.md — «одна задача» в MVP выглядит искусственным ограничением UI, а не парсера), либо (б) определить деградацию: парсер извлекает всё, /confirm показывает всё, но сложные kinds (recurrence, delegation, scheduled) в v1 помечаются «пока не умею — создам как обычную задачу?». Вариант (а) правильнее.

### К5. Свайп-приёмка: нет undo, не определены свайпы для «Вопросы», «Просрочки», «Заявки магазина»
**Суть.** FRONTEND.md/CONCEPT §3.3 определяют жесты только для отчётов (вправо/влево/вверх). «Требует вас» содержит 4 стопки — что значит свайп вправо по вопросу сотрудника? По просрочке? По заявке магазина? Не сказано. И нигде нет отмены ошибочного свайпа: карточка «улетела с зелёным шлейфом», а директор промахнулся — задача закрыта, очки начислены, push ушёл.
**Последствие.** Агент придумает свою семантику для трёх стопок; директор, один раз ошибочно закрыв задачу без возможности отката, перестанет доверять свайпам.
**Решение.** (1) Тост «Принято ✓ — Отменить» 5 сек после каждого свайпа; отмена = компенсирующие записи (статус назад, сторнирующая point_transaction). (2) Таблица жестов по типам стопок в FRONTEND.md: вопросы — вправо=ответ-чипы(«Да/Нет/Позже/Действуй сам», переиспользовать тихий режим), влево=ответить голосом; заявки магазина — вправо=approve, влево=cancel с причиной; просрочки — вправо=«продлить дедлайн» (пресеты), влево=голосовое сотруднику. (3) Задать очки за свайп-вверх (сейчас «+🔥+очки» — сколько? Предлагаю значение из company.settings, по умолчанию +5).

### К6. Обещан «индикатор недоставки push», который Web Push технически не даёт
**Суть.** CONCEPT §8: «индикатор недоставки у директора („Марат не получил“ ≠ „Марат игнорирует“)». Web Push не имеет delivery receipt: сервер знает только, что push-сервис принял сообщение, а не что устройство его показало.
**Последствие.** Агент либо построит врущий индикатор (хуже, чем никакого — директор начнёт делать оргвыводы по ложным данным), либо застрянет.
**Решение.** Переопределить семантику: «доставлено» = service worker отправил ack-fetch на `/api/push/ack` при показе нотификации ЛИБО пользователь открыл приложение после отправки. Статусы у директора: «отправлено / увидел / принял». Спека ack-эндпоинта — в BACKEND.md §2. Честная формулировка в UI: «не открывал с 9:14», а не «не получил».

### К7. Автоштраф −5 за просрочку по дедлайну, который выдумал AI, при отсутствующем механизме возражения
**Суть.** BACKEND.md: «завтра до обеда» → парсер сам ставит 13:00. Директор жмёт «Всё верно» не глядя (CONCEPT §8 сам это предсказывает — «автоматизационная слепота»). Сотрудник получает −5 (DATABASE.md pg_cron №6) за срок, который никто осознанно не назначал. CONCEPT §8 обещает «канал возражения по начислениям» — но ни экрана, ни таблицы, ни флоу для него нет нигде.
**Последствие.** Первый несправедливый штраф на публичном рейтинге = локальный бунт против системы; сотрудники начнут саботировать (не принимать задачи, чтобы не попасть под правила).
**Решение.** (1) В истории начислений у каждой транзакции — кнопка «Оспорить» → создаёт сообщение в личный канал директора с контекстом транзакции; директор одним тапом «Вернуть очки» (компенсирующая транзакция source='manual'). (2) Автоштраф в калибровочный месяц выключен по умолчанию (company.settings), включается осознанно. (3) На /confirm дедлайны, которые парсер вывел сам (а не услышал явно), подсвечивать как low-confidence чип.

### К8. Статус `in_progress` существует в схеме, но не имеет ни одного UI-триггера
**Суть.** CLAUDE.md и DATABASE.md содержат `in_progress(опц.)`, но ни FRONTEND.md (3 кнопки + «Выполнено»), ни BACKEND.md не описывают, кто и где его ставит.
**Последствие.** Агент либо добавит четвёртую кнопку сотруднику (нарушение принципа №2), либо статус останется мёртвым кодом с ветками в v_employee_load и статистике.
**Решение.** Выкинуть из v1. Если оставлять — единственный допустимый триггер: авто-переход при первом сообщении сотрудника в канале задачи после accepted. Зафиксировать явно.

## Дыры проектирования (агент будет гадать)

### Д1. Что происходит на /confirm с сущностью «исполнитель не распознан»?
BACKEND.md: 0 кандидатов → «пометить „не распознан“». Блокирует ли это кнопку «Всё верно»? Можно ли отправить остальные 4 сущности?
**Мой ответ:** «Всё верно» отправляет только валидные сущности; невалидные остаются на экране с красным чипом «Кому?» → тап открывает полный список сотрудников. Кнопка показывает счётчик: «Отправить 4 из 5».

### Д2. Допустима ли задача без дедлайна и как она живёт?
Парсер возвращает `deadline_iso: null`, если срок не назван. Дальше: как её красит v_employee_load (там только red/yellow/green по дедлайну)? Попадает ли в «в срок +3»?
**Мой ответ:** да, допустима; в load-логике считается green; авто-правила очков к ней не применяются; в «Моих делах» сортируется после дедлайновых с чипом «без срока». Прописать в DATABASE.md (v_employee_load) и FRONTEND.md.

### Д3. Как определяется стопка «Вопросы» в «Требует вас»?
Статуса «вопрос» нет. Это task_messages type='text' от сотрудника при status='sent'? А если сотрудник спросил после accepted?
**Мой ответ:** «Уточнить» создаёт task_message с meta `{is_question: true}`; вопрос «открыт», пока директор не ответил в канале задачи (любое сообщение директора после — закрывает). Стопка = открытые вопросы. Нужен явный контракт в DATABASE.md.

### Д4. `rework → снова accepted` — автоматически или сотрудник заново жмёт «Принял»?
CLAUDE.md запись двусмысленна.
**Мой ответ:** автоматически в accepted (сотрудник уже брал обязательство; повторный тап — лишнее действие и мусор в статистике времени реакции). Push: «Директор вернул на доработку: [голосовой комментарий]».

### Д5. Где сотрудник жмёт «Выполнено» — только в /tasks или и на карточке в /feed?
FRONTEND.md описывает кнопку только в «Мои дела». Основной экран сотрудника — лента.
**Мой ответ:** и там, и там: после accepted карточка в ленте меняет набор кнопок на «Выполнено» (+ композер всегда доступен). Нужна таблица «состояние задачи → набор кнопок карточки» — её нет, а это ядро UI сотрудника.

### Д6. Получают ли сотрудники push об объявлениях Эфира, и какие вообще события пушатся?
BACKEND.md §2 описывает только триггер на tasks/task_messages.
**Мой ответ:** нужна матрица нотификаций (событие → получатель → текст → deep-link → канал). Объявления — да, push всем с deep-link в Эфир; реакции — push; начисление очков — push; выдача заказа — push. Без матрицы агент реализует случайное подмножество.

### Д7. Оффлайн-очередь и таймстампы: «принял за 10 мин +1» при плохой связи
Сотрудник на стройке тапнул «Принял» без сети; запись ушла через 2 часа. accepted_at = время тапа или время доставки? Авто-правило +1 сработает?
**Мой ответ:** очередь в IndexedDB пишет `client_ts`; сервер сохраняет оба, авто-правило считает по client_ts (с санити-проверкой ≤ server_ts). И у карточки в оффлайне — явное состояние «Принято, отправится при связи» (иконка-часики как в мессенджерах), иначе сотрудник будет тапать повторно.

### Д8. Паттерн заморозки очков в магазине не выбран
DATABASE.md сам говорит: «hold остаётся финальным ИЛИ пара release+final — выбери один». Это финансовая логика, оставленная на волю агента.
**Мой ответ:** hold остаётся финальным (меньше записей, баланс всегда честный); при выдаче — только `orders.status=delivered` + событие в Эфир. Зафиксировать комментарием в миграции, как требует док.

### Д9. Навигационная модель приложения отсутствует
FRONTEND.md перечисляет экраны, но нигде нет: таб-бар? Сколько вкладок у сотрудника (feed, tasks, ether, shop, профиль — уже 5)? У директора (pulse, confirm, ether, shop, tv-пульт)?
**Мой ответ:** сотрудник — нижний таб-бар 4 вкладки: Лента / Дела / Эфир / Профиль (магазин — внутри профиля через прогресс-бар «до худи», это же и мотивационная петля); директор — Пульс / Эфир / Люди? Нет: Пульс уже содержит людей. Пульс / Эфир / Профиль + глобальная FAB. Требую схему навигации в FRONTEND.md до старта UI-недель.

### Д10. Тексты уведомлений и пустых состояний не специфицированы
«Тон — короткий, деловой, без канцелярита» — это не спека. Push о штрафе −5 может быть написан как приговор или как факт; для адаптации это критично.
**Мой ответ:** копи-дек (см. последний раздел). Принципы: штрафы — нейтрально-фактически без восклицаний («−5: просрочен дедлайн по „КП Казхром“»); похвала — эмоционально («🔥 +10 от директора за скорость!»); задачи — глагол+срок («Новая задача до 18:00: …»).

## Противоречия между документами

1. **Длительность MVP.** CONCEPT §7: «MVP | 3 нед». PLAN_12_WEEKS: MVP = недели 1–4 («Неделя 4 … ✅ Критерий: MVP готов»). Агент, планирующий спринты, получит два разных скоупа недели. Привести CONCEPT к 4 неделям.
2. **Свайп-приёмка: в MVP или нет.** FRONTEND.md (Пульс, блок 2): «тап открывает **режим свайпов**» — без оговорок об этапности; CLAUDE.md очерёдность: свайп-приёмка — этап 3; PLAN неделя 4: «приёмка пока кнопками, свайпы позже», неделя 9: «Свайп-приёмка». Агент недели 4 построит свайпы по FRONTEND.md. В FRONTEND.md нужна пометка «v1: кнопки Принято/Доработка; свайпы — неделя 9». Заодно: CONCEPT §7 относит свайпы к этапу «+2» (~неделя 8), PLAN — к неделе 9.
3. **TTS-кнопка в Пульсе.** CONCEPT §3.3 блок 1 описывает «Кнопка „Послушать сводку“ (TTS)» как часть блока без оговорок; FRONTEND.md — «итерация 4+»; CLAUDE.md — этап 5. Убрать из описания блока 1 или везде одинаково пометить этап.
4. **Реакции на объявления невозможны по схеме.** CONCEPT §3.3: живая лента (куда входят и announcements) — «долгий тап → реакция»; DATABASE.md: `reactions … message_id fk task_messages` — на announcement реакцию не повесить. Либо полиморфная ссылка (entity_type + entity_id), либо в CONCEPT ограничить реакции сообщениями задач.
5. **Гостевой режим ТВ.** CONCEPT §8: «гостевой режим ТВ по умолчанию при фокус-режимах с ПД»; FRONTEND.md: гость — статический `?guest=1` в URL киоска. Query-параметр нельзя переключить «при фокус-режимах» — это взаимоисключающие механики. Решение: guest — состояние, управляемое с пульта (`tv_control: {guest: true}`), кнопка «Посетитель» в шторке пульта директора; `?guest=1` — лишь стартовое значение. Иначе приватность при посетителях — декларация: директор не будет перезагружать киоск с другим URL, когда в кабинет кто-то зашёл.
6. **Интервал recurrence в DATABASE.md** записан как поток сознания: «каждый час... нет, каждые 5 минут». Мелочь, но в «проектном контракте» такого быть не должно — агент может прочитать буквально.

## Улучшения

- **[high] Тихие часы доставки.** Директор встаёт в 5:00 (PLAN, ритм) и наговорит задачи до рассвета — сотрудники получат push в 6 утра. Дефолт: доставка 08:00–21:00 Asia/Aqtobe, вне окна — авто-`scheduled_send_at`=08:00 с пометкой на /confirm «отправлю утром» (переопределяется тапом «отправить сейчас»).
- **[high] /confirm при 5+ сущностях: компактный режим.** Карточки с чипами при 6–8 сущностях = 3 экрана скролла и риск не заметить ошибку в середине. Сущности — однострочные свёрнутые строки (иконка + исполнитель + суть + дедлайн), тап разворачивает; «Отправить (N)» — sticky снизу; невалидные строки подсвечены и подсчитаны. Узким горлышком экран становится не из-за числа сущностей, а из-за отсутствия иерархии «просмотреть быстро / править точечно».
- **[high] Рейтинг: справедливость = нормировка.** Очки коррелируют с числом полученных задач (офис-менеджер получает 20/нед, водитель — 3): рейтинг измеряет близость к директору, а не работу. Дать в настройках второй режим рейтинга «% в срок» и/или ранги по личному прогрессу, а не только абсолютную сумму. Публичность по умолчанию — top5 (сейчас дефолт не задан).
- **[mid] «Не могу» ≠ «это не мне»: причины-чипы.** Свободное поле причины на морозе на стройке никто заполнять не будет. Пресеты: «Это не ко мне» / «Занят другим срочным» / «Нет ресурсов/материалов» / «Буду позже: [дата]» + свободный текст. Дешёво, структурирует данные для директора и снимает страх кнопки.
- **[mid] Фото-отчёт на плохой связи: прогресс и сжатие.** Спеки нет: клиентское сжатие до ~1600px/качество 0.8 перед укладкой в IndexedDB-очередь, индикатор загрузки на пузыре сообщения, ретрай без повторного выбора файла. Стройплощадка — заявленный ключевой контекст (FRONTEND.md, PWA), а флоу самого тяжёлого вложения не описан.
- **[mid] Разделить «Принял» и «Принял к сведению» лексически.** Две кнопки с почти одинаковым словом и разной семантикой (обязательство vs прочтение) в двух разных лентах — предсказуемая путаница «где что» между Эфиром и личным каналом. Эфир: «Ознакомился». Личный канал: «Принял». И на онбординге сотрудника — один экран «Эфир — для всех, Лента — лично тебе».
- **[mid] Стрелы к аватаркам при 5 задачах разным людям** (FRONTEND.md, веер с интервалом 100мс): аватарки исполнителей после /confirm не на экране — куда летят стрелы? Определить: улёт к верхней кромке + сводка-тост «5 отправлено: Марат, Ерлан…». Не давать агенту изобретать сцену.
- **[low] Комбо-счётчик свайпов** («Разобрано N подряд») — убрать из v1: геймификация директора сомнительна, он и так мотивирован; риск ощущения «система играет со мной, пока я работаю».
- **[low] `?guest=1` дублировать физической кнопкой/ярлыком** на мини-ПК для секретаря — «гостевой ярлык» на случай, когда директора нет в кабинете, а посетитель есть.
- **[low] Web Share Target** — вынести из ранних недель явно (в PLAN его нет — и правильно; но FRONTEND.md описывает без пометки этапа, агент недели 3 может закопаться в manifest share_target).

## Вопросы владельцу продукта

1. Дедлайн, выведенный AI из «до обеда», — юридически «назначенный срок» для автоштрафа, или штрафы только по явно названным срокам? (Определяет доверие к очкам.)
2. Рейтинг по умолчанию: полный список или top5? Показывать ли падение (↓) публично? (CONCEPT §8 называет риск, но дефолт не выбран.)
3. Рейтинг меряет сумму очков (≈ объём задач) — устраивает ли, что полевые роли с малым числом поручений системно внизу? Готовы ли на нормированный режим?
4. Может ли `manager` начислять очки своей группе, или очки — монополия директора? (RLS сейчас: только director.)
5. Конвертация очков в премию (CONCEPT §5 «перспектива») — входит ли в 12 недель хотя бы как публичное обещание сотрудникам? Это меняет мотивацию пилота.
6. Гостевой режим ТВ: что считается ПД для посетителей — только фамилии/очки или и названия контрагентов в задачах на экране? (Задача «КП для Казхрома» на стене при визите конкурента — утечка.)
7. Пилот недели 5: пять человек — офисные или включить хотя бы одного полевого? (Определяет приоритет оффлайн-очереди против полировки.)
8. Кто «владелец» экономики очков после калибровочного месяца — директор в админке сам, или правки через разработчика?

## Чего не хватает в доках для агентной разработки

1. **Спека Auth/онбординга** (К1): создание аккаунтов, инвайты, привязка Telegram, платформенные ветки iOS/Android/in-app-браузер. Без неё не стартует неделя 1.
2. **Таблица статусной машины**: переход × кто имеет право × UI-триггер (какая кнопка на каком экране) × побочные эффекты (push, очки, task_message system). Сейчас статусы описаны строкой в CLAUDE.md, а триггеры размазаны по трём докам с дырами (in_progress, declined, rework).
3. **Матрица уведомлений**: событие → получатель → канал (push/tg) → точный текст → deep-link → tag/коалесценция. (Д6, Д10.)
4. **Копи-дек**: тексты пушей, пустых состояний (пустая лента новичка, пустой Пульс), ошибок (offline, AI down, «не расслышал»), подтверждений. Тон задан одной строкой — этого мало для консистентности между сессиями агентов.
5. **Фикстуры парсера**: 30+ реальных фраз директора (STT-гейт их и так даст) в паре с эталонным JSON `entities` — как тестовый набор в репозитории. CLAUDE.md требует тесты парсера, но эталонов нет.
6. **Контракт «вопроса»** (Д3) и определение всех четырёх стопок «Требует вас» как SQL/view — сейчас определена только «На приёмке».
7. **JSON-схема `company.settings`**: авто-правила очков, reaction_points, публичность рейтинга, тихие часы, курс очков — перечислены словами в DATABASE.md, но без схемы каждый агент будет придумывать свои ключи.
8. **Wireframe-уровень для трёх экранов**: /confirm (компактный+развёрнутый режимы), режим свайпов (включая жесты по типам стопок и undo), лента /feed (наборы кнопок карточки по статусам). Хватит ASCII/маркдаун-скетчей — важна не картинка, а однозначность.
9. **Спека оффлайн-очереди**: что кладётся в IndexedDB (действия? сообщения? фото?), порядок доставки, конфликты, client_ts vs server_ts, UI-состояния «в очереди/отправлено». Одна строка в FRONTEND.md «очередь с авто-ретраем» — это не спека.
10. **Семантика «доставлено» для push** (К6): ack-контракт и словарь статусов у директора.
