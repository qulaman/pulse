# Альтернативы: Senior Frontend

## Постановка: как я понял задачу своей области из брифа

Мне нужно выбрать UI-рантайм и фреймворк для продукта с тремя очень разными поверхностями:

1. **Телефон директора** — «пульт»: подтверждение распознанных голосовых, дашборд, управление ТВ. Требователен к полировке уровня Kaspi/Telegram, ненавидит лишние тапы.
2. **Телефоны ~45 сотрудников** — личные, без MDM, много бюджетных Xiaomi/Redmi, есть Huawei **без Google-сервисов**, часть iPhone. Онбординг очно за 2 минуты. Плохой интернет на объектах, действия не должны теряться. Уведомления критичны.
3. **ТВ-экран** — живая лента, read-only, управляется с телефона директора.

Ключевые ограничения, которые реально определяют выбор:

- **Один разработчик, 12 недель до полного развёртывания, пилот через 4–5 недель.** Это исключает всё, где придётся дебажить платформу вместо продукта.
- **Код пишут ИИ-агенты (Claude Code).** Значит, качество генерации кода под конкретный стек — не «приятный бонус», а прямой множитель скорости. Нужен стек с максимальным объёмом обучающих данных и предсказуемыми паттернами.
- **Huawei без GMS** ломает нативный push через FCM — это тихая мина под любым «просто сделаем нативное приложение».
- **Геймификация должна быть плавной на бюджетном Android** — т.е. анимационная дисциплина важнее выбора «модной» библиотеки.
- **Бюджет — десятки долларов в месяц**, значит managed-сервисы с щедрым free tier, никакого своего инфраструктурного зоопарка.

Отдельные подвопросы: оффлайн-архитектура (нужен ли local-first: Replicache/PowerSync/RxDB), анимационный стек, realtime.

## Кандидат A — Next.js (App Router) + PWA (serwist) + Supabase Realtime

**Суть.** Один Next.js-проект на Vercel: PWA для сотрудников и директора, роут `/tv` для телевизора, API-роуты для голосового конвейера (Whisper/LLM), Web Push через VAPID. Realtime и БД — managed (Supabase или аналог). Одна кодовая база, один деплой, один язык.

**Сильные стороны именно для этих условий.**

- **Онбординг за 2 минуты — честно выполняется.** «Открой ссылку → Добавить на главный экран → разреши уведомления». Работает на Xiaomi, на Huawei (браузером), на iPhone (iOS 16.4+ поддерживает Web Push для установленных PWA). Ни App Store review, ни APK-раздачи, ни AppGallery.
- **Мгновенные обновления.** Соло-разработчик, который чинит баг и через минуту он у всех 45 человек — это несравнимо с циклом ревью сторов. За 12 недель будут десятки хотфиксов; PWA превращает это из риска в рутину.
- **Три поверхности из одной кодовой базы.** `/tv` — это просто ещё один роут с теми же realtime-подписками; «пульт ТВ» — состояние в БД + подписка. В нативном сценарии ТВ-экран стал бы отдельным приложением/вебвью — лишняя сущность.
- **Серверная часть в том же репо.** Голосовой конвейер (upload аудио → STT → LLM-парсинг → карточка на подтверждение) — это API-роуты рядом с UI. Для одного человека «один репозиторий = вся система» резко снижает когнитивную нагрузку и стоимость сопровождения.
- **Генерация кода ИИ-агентами — лучший вариант из всех.** React + Next.js + TypeScript + Tailwind — самый большой корпус обучающих данных в вебе вообще. Claude Code выдаёт рабочие компоненты, серверные экшены, роуты и хуки с первой-второй итерации; паттерны App Router (server/client components, route handlers) многократно представлены в данных. Tailwind — отдельный ускоритель: стили описываются текстом в разметке, агент не теряет контекст между файлами. shadcn/ui даёт агенту знакомую библиотеку примитивов, которую он умеет модифицировать, а не только вызывать.
- Экосистема закрывает всё специфичное: `serwist` (service worker, precache, offline), `web-push` (VAPID), Framer Motion, Recharts/визуализация для дашборда.

**Слабые стороны / риски.**

- **Push — главный риск PWA-пути, и его надо назвать честно.**
  - iPhone: Web Push работает только после «Добавить на экран Домой» — если сотрудник откроет просто в Safari, уведомлений не будет. Лечится очным онбордингом (он и так очный).
  - Xiaomi/MIUI агрессивно убивает фон и режет уведомления даже нативным приложениям; для PWA в Chrome push доставляется через FCM-канал самого Chrome — работает, но на MIUI надо на онбординге выключить оптимизацию батареи для браузера.
  - **Huawei без GMS: Web Push через Chrome недоступен (нет Play Services), фирменный браузер Huawei push не даёт.** Рабочие обходы: поставить Firefox (у Mozilla свой autopush-сервер, GMS не нужен) — или дублировать критичные уведомления в Telegram-бота. Вывод: **Telegram-бот как дублирующий канал уведомлений обязателен в архитектуре с первого дня**, не как «фолбэк потом». Это, кстати, снимает риск целиком: сегодня вся компания и так живёт в Telegram/WhatsApp.
- App Router сложнее классического SPA: границы server/client компонентов — источник ошибок и у людей, и у агентов («`useState` в серверном компоненте»). Смягчение: в этом продукте почти весь UI интерактивный и realtime — можно честно писать 90% как client components и не изображать RSC-пуризм.
- Game feel в браузере на бюджетном Android достижим, но требует дисциплины (см. раздел про анимации в «Моём выборе») — потолок «сочности» ниже, чем у Flutter/RN со Skia, однако для «полёта карточки, конфетти, счётчика очков» его хватает с запасом.
- Vercel + serverless: длинные аудио-обработки упираются в таймауты функций — конвейер STT надо строить асинхронно (upload → фоновая обработка → realtime-уведомление), это архитектурное требование, а не блокер.

**Влияние на 12 недель соло + ИИ-агенты.** Самый короткий путь из всех кандидатов. Пилот на 5 людях к неделе 4 реалистичен: недели 1–2 — каркас, auth, карточки задач, realtime; недели 3–4 — голосовой конвейер и push. Нет ни одного этапа «борьбы с платформой», кроме настройки push-каналов (закладываю 3–4 дня на матрицу устройств).

**Стоимость.** Vercel: $0 (hobby) → $20/мес (pro). Supabase: $0 → $25/мес. Push (VAPID) — бесплатно. Telegram Bot API — бесплатно. Итого **$0–45/мес** плюс расходы на STT/LLM API (общие для всех кандидатов). Разовые: $0. В бюджет «десятки долларов» помещается.

## Кандидат B — Vite + React SPA (+ отдельный лёгкий бэкенд)

**Суть.** Классическое SPA: Vite, React, React Router/TanStack Router, TanStack Query. Бэкенд отдельно — Fastify/Hono-сервис или полностью BaaS (Supabase: auth, БД, realtime, edge functions). Хостинг статики — Cloudflare Pages/Netlify. Тоже PWA.

**Сильные стороны.**

- **Проще ментальная модель, чем App Router.** Нет server/client-границ, нет гидратационных сюрпризов: всё — клиент. Для ИИ-агентов это тоже плюс: классический SPA-React — самый «выученный» паттерн из существующих, ошибок класса «не там использовал серверный API» просто не бывает.
- Для этого продукта SSR не нужен вообще: всё за логином, SEO нет, все три поверхности — интерактивные realtime-приложения. SPA — честная архитектура без лишнего слоя.
- Vite-сборка быстрая, бандл контролируемый; PWA через `vite-plugin-pwa` — зрелый, документированный путь.
- Все плюсы PWA из кандидата A (онбординг, мгновенные обновления, `/tv` как роут) сохраняются.

**Слабые стороны / риски.**

- **Бэкенд надо где-то писать.** Голосовой конвейер, генерация push, серверная логика вопросов к данным — это не «чуть-чуть кода». Варианты: (а) отдельный Node-сервис — второй деплой, второй репозиторий/пакет, CORS, больше DevOps на одного человека; (б) всё в edge functions BaaS — работает, но dev-опыт и логи хуже, чем у API-роутов рядом с UI.
- Секреты (ключи STT/LLM) нельзя держать в клиенте — значит серверный слой обязателен, и «SPA без бэкенда» — иллюзия; фактически получается два проекта вместо одного.
- ИИ-агентам с двумя кодовыми базами работать хуже, чем с одной: контракты между фронтом и бэком приходится синхронизировать руками (или тащить tRPC/openapi-генерацию — ещё инструменты).

**Влияние на срок.** Сопоставимо с A по UI, но +1–2 недели суммарно на второй деплой, склейку и сопровождение двух частей. Для соло-разработчика каждая лишняя движущаяся часть — это налог не только на разработку, но и на все 12 недель поддержки после.

**Стоимость.** Статика $0; Node-сервис — Railway/Fly $5–15/мес или edge functions в составе BaaS; Supabase $0–25. Итого примерно как A, **$5–40/мес**, но больше операционной работы.

## Кандидат C — Remix (React Router v7) / TanStack Start

**Суть.** Полноценные fullstack-React-фреймворки: Remix с loader/action-моделью, либо TanStack Start (SSR поверх TanStack Router). Тот же React, та же PWA-стратегия, другой каркас.

**Сильные стороны.**

- Remix: модель loader/action проще и предсказуемее, чем RSC; прогрессивное улучшение форм — красиво для плохой связи (формы могут работать даже при деградации JS).
- TanStack Start: типобезопасность маршрутов и данных сквозная, лучшая в классе.
- Оба — React, значит основной корпус знаний ИИ-агентов о React-компонентах применим.

**Слабые стороны / риски.**

- **Худшее соотношение «выгода/нестабильность знаний» для ИИ-агентов.** Remix за последние два года пережил слияние с React Router (v7), переименования и смену рекомендуемых паттернов — в обучающих данных перемешаны Remix v1/v2 и RRv7, агенты стабильно путают импорты и конвенции. TanStack Start к моменту старта — молодой фреймворк с маленьким корпусом примеров: агент будет чаще галлюцинировать API. Для проекта, где скорость генерации — главный ресурс, это прямой минус.
- Экосистемные рецепты (PWA, web-push, деплой, фоновые задачи) для Next.js существуют в виде готовых, многократно проверенных гайдов; для Remix/Start — придётся собирать самому.
- Никакого продуктового преимущества перед A эти каркасы здесь не дают: SEO нет, публичных страниц нет, вся ценность Remix-модели (документы, формы, прогрессивность) второстепенна для realtime-приложения за логином.

**Влияние на срок.** +1–3 недели чистого налога: не на фичи, а на «как это принято делать в этом фреймворке» и на исправление уверенных, но неверных ответов агента. При сроке 12 недель — неоправданно.

**Стоимость.** Как A: $0–45/мес.

## Кандидат D — Expo / React Native (+ веб для ТВ)

**Суть.** Нативное приложение на React Native через Expo: сборки EAS, OTA-обновления (expo-updates), push через FCM/APNs, анимации Reanimated + Skia. ТВ-экран — отдельная маленькая веб-страница. Раздача: TestFlight/App Store для iPhone, APK/сторы для Android.

**Сильные стороны.**

- **Потолок полировки выше.** Reanimated (анимации на UI-потоке) + RN Skia + haptics дают «нативный» game feel, который на бюджетном Android стабильнее браузерного. Для директора с эталоном Kaspi/Telegram это самый убедительный кандидат по ощущению.
- Нативный push надёжнее web push **на iPhone и обычных Android**: не зависит от «установил ли пользователь PWA правильно», меньше страдает от браузерных ограничений.
- Фоновые возможности: запись голоса директора с экраном заблокированным, аудио-сессии — в нативе это штатно, в вебе — компромиссы.
- Это всё ещё React + TypeScript: значительная часть навыка ИИ-агентов переносится; Expo — самый документированный путь в RN, корпус данных большой.

**Слабые стороны / риски.**

- **Huawei без GMS — прямое попадание.** FCM не работает; нужен либо HMS Push Kit (отдельная интеграция, слабо представленная в обучающих данных, публикация в AppGallery), либо тот же Telegram-фолбэк. То есть главный аргумент «нативный push надёжнее» частично обнуляется на самом проблемном сегменте парка устройств.
- **Дистрибуция против «онбординга за 2 минуты».** iPhone без App Store — только TestFlight (лимиты, приглашения) или платный аккаунт + ревью (задержки, риск реджекта внутреннего приложения). Android без стора — APK с «разрешить установку из неизвестных источников» на личном телефоне сотрудника: очный онбординг растягивается и выглядит стрёмно. OTA-обновления Expo смягчают проблему обновлений, но не первой установки.
- **Цикл разработки тяжелее.** Нативные модули → пересборка EAS (минуты–десятки минут), отладка на ферме реальных устройств (MIUI!), платформенные баги RN на дешёвых Android. Для соло-разработчика это второй «проект внутри проекта».
- ИИ-агенты в RN хороши в компонентах и навигации, но ощутимо слабее в нативной обвязке (конфиги EAS, entitlements, push-сертификаты, HMS) — именно там, где сожрётся время.
- ТВ-экран всё равно потребует отдельного веб-приложения → две кодовые базы.

**Влияние на срок.** Пилот к неделе 4–5 — на грани: неделя уйдёт только на конвейер сборки/раздачи и push-сертификаты. Полное развёртывание к неделе 12 возможно, но буфер на полировку (ради которой всё и затевалось) съедается инфраструктурой. Для соло с ИИ-агентами — заметно рискованнее A.

**Стоимость.** Apple Developer **$99/год**, Google Play $25 разово; EAS free tier ограничен, реально $19+/мес на сборки; плюс бэкенд как в A. Итого **~$20–50/мес + ~$125 разово** — в бюджет влезает, но дороже и больше движущихся частей.

## Кандидат E — Flutter

**Суть.** Одна Dart-кодовая база: Android + iOS (+ web для ТВ-экрана). Своя отрисовка (Impeller/Skia) — анимации не зависят от возможностей браузера.

**Сильные стороны.**

- Лучший в списке потолок по плавности на слабом железе: собственный рендер, 60fps на бюджетных устройствах достижимы стабильнее, чем где-либо. «Полёт задачи», конфетти, счётчики — родная стихия Flutter.
- Единый визуальный результат на всех устройствах, никакой браузерной фрагментации.

**Слабые стороны / риски.**

- **Все дистрибуционные и push-проблемы кандидата D** (TestFlight/APK/GMS-Huawei) — без исключений.
- **Dart — смена языка для всего.** Бэкенд всё равно будет TS/Node (STT/LLM SDK, web-push, Telegram) → два языка у одного человека. Экосистема пакетов беднее npm именно в нужных местах (телеграм-боты, web-push, LLM-тулинг).
- **Генерация кода ИИ-агентами — заметно слабее React-стека.** Корпус Dart/Flutter в разы меньше; агенты чаще промахиваются по версиям API (null-safety-эпохи, смены виджетов), а главное — не переиспользуют веб-знания (Tailwind-паттерны, headless-компоненты). Скорость итераций падает именно там, где она — главный ресурс проекта.
- Flutter web для ТВ-экрана — тяжёлый и странный (canvas-рендер, огромный бандл); реалистично ТВ пришлось бы писать отдельно на вебе → снова два стека.

**Влияние на срок.** Наименее совместим с «12 недель, один человек, руки — ИИ-агенты». Честная оценка: пилот к неделе 6–7, полировка к 12-й — впритык и без запаса.

**Стоимость.** Как D: ~$125 разово, хостинг бэкенда $5–25/мес.

## Кандидат F — SvelteKit (PWA)

**Суть.** Тот же PWA-план, что и A, но на Svelte 5 + SvelteKit: меньше рантайма, реактивность компилятором, встроенные transitions.

**Сильные стороны.**

- Меньший бандл и меньше работы в главном потоке — на бюджетном Android это реальные миллисекунды. Встроенные `transition:`/`animate:` дают приятную анимацию «из коробки» дешевле, чем Framer Motion.
- SvelteKit — полноценный fullstack (endpoints, form actions): один репозиторий, как в A.

**Слабые стороны / риски.**

- **Svelte 5 (runes) сломал совместимость с корпусом Svelte 3/4.** В обучающих данных доминирует старый синтаксис (`$:`, stores); агенты регулярно смешивают эпохи — `$state` рядом с `export let`, старые паттерны stores там, где нужны runes. Каждая такая ошибка — итерация, а итерации — валюта проекта.
- Экосистема тоньше: нет эквивалента shadcn/ui той же зрелости, меньше готовых рецептов под web-push/PWA/realtime, меньше ответов на нестандартные вопросы.
- Технический выигрыш (бандл, перф) в этом продукте не конвертируется в продуктовое преимущество: узкое место game feel — дисциплина анимации (transform/opacity), а не рантайм фреймворка; React с той же дисциплиной даёт тот же результат на тех же телефонах.

**Влияние на срок.** UI-скорость сопоставима с A для человека, но **ниже для ИИ-агента**. Оценка: +1–2 недели на итерации из-за путаницы Svelte-эпох и самостоятельной сборки рецептов.

**Стоимость.** Как A: $0–45/мес.

## Оффлайн-архитектура (сквозной вопрос)

**Local-first движки (Replicache/Zero, PowerSync, RxDB, ElectricSQL) — не стоит.** Аргументы:

- Это системы для *двусторонней* синхронизации произвольных мутаций с разрешением конфликтов. Здесь конфликтов почти нет по построению: задачу закрывает только директор, ответы сотрудника («принял», отчёт с фото) — append-only события, очки — append-only транзакции. Платить архитектурной сложностью (sync-протокол, схемы клиентской БД, миграции клиентских данных у 45 человек) за проблему, которой нет, — классическая ошибка.
- Replicache/PowerSync — коммерческое лицензирование/подписка и малый корпус в обучающих данных: агенты пишут их плохо. RxDB с полноценной репликацией — платные плагины и много кода.
- Сопровождение: отладка «почему у Армана на телефоне не та версия задачи» в local-first системе — худший сценарий для одного человека.

**Достаточная архитектура — Outbox + кэш чтения:**

1. **Outbox-очередь действий** в IndexedDB: каждое действие сотрудника (принял / уточнить / не могу / отчёт) пишется локально мгновенно (UI реагирует сразу — это и есть game feel), фоновая доставка с ретраями и экспоненциальным бэкофом; Background Sync API где доступен, плюс досылка при возврате приложения на передний план и при событии `online`.
2. **Идемпотентность на сервере**: каждое действие несёт client-generated UUID; повторная доставка безопасна. Это 20 строк на сервере и снимает весь класс проблем «двойной тап на плохой связи».
3. **Кэш чтения**: последняя загруженная лента задач в IndexedDB (через TanStack Query persist) — открыл приложение в подвале стройки, видишь свои задачи и можешь по ним отчитаться в очередь.
4. **Фото-отчёты**: файл кладётся в очередь (Blob в IndexedDB), UI показывает «отправляется…», доставка фоном. Не терять — важнее, чем отправить быстро.
5. Честный **индикатор состояния** («3 действия ждут сети») — дешёвый способ доверия на плохой связи.

Это ~3–5 дней работы с агентами против 2–3 недель встраивания local-first движка, и оно полностью закрывает требование «действия не должны теряться».

## Анимационный стек для game feel на бюджетном Android (сквозной вопрос)

- **Правило №1: только `transform` и `opacity`** — свойства композитора. Никаких анимаций `width/height/top/box-shadow`, никакого `filter: blur` на больших областях. Это правило дисциплины, и его надо записать в системные инструкции агентам, иначе они будут анимировать что попало.
- **Framer Motion (motion)** как основной инструмент: spring-физика, layout-анимации через FLIP (то есть тоже transform), жесты (свайпы по карточкам), `AnimatePresence` для «полёта задачи». Огромный корпус в обучающих данных — агенты пишут её лучше всех альтернатив.
- «Полёт карточки к адресату», конфетти при начислении очков — clone-элемент + transform-анимация; конфетти — canvas (`canvas-confetti`) — дёшево и стабильно.
- Сложные векторные эффекты — **Lottie дозированно** (короткие, по событию, не в цикле на списках) или Rive; на слабых GPU постоянные Lottie-циклы — главный источник лагов.
- **Бюджет производительности как процесс**: тестовый Redmi 9/A-серия на столе, Chrome DevTools CPU throttling 6x в каждой итерации полировки; списки задач — виртуализация после ~50 элементов; haptics через Vibration API на Android (мелочь, дающая «нативность»).
- Уважать `prefers-reduced-motion` и давать выключатель эффектов — на самых слабых устройствах это и опция доступности, и предохранитель.

## Realtime (сквозной вопрос)

- **Supabase Realtime (Postgres changes / channels)** — управляемый WebSocket без своей инфраструктуры: лента ТВ, обновление статусов у директора, «пульт ТВ» (директор пишет команду в таблицу/канал — ТВ подписан). Альтернативы того же класса — Ably/Pusher ($0–29/мес), но при Supabase как BaaS отдельный сервис не нужен.
- 45 человек + 1 ТВ — это игрушечная нагрузка для любого из этих сервисов; выбирать здесь надо по принципу «нулевое сопровождение», а не по бенчмаркам.
- Обязателен **фолбэк**: при разрыве WS — refetch по reconnect/visibilitychange (TanStack Query это умеет из коробки). На плохой связи realtime — это «ускорение», а источником правды остаётся запрос.

## Мой выбор и почему

**Кандидат A: Next.js PWA + Tailwind + Framer Motion + Supabase (Postgres/Auth/Realtime/Storage) + Web Push (VAPID) + обязательный Telegram-бот как дублирующий канал уведомлений. Оффлайн — outbox-очередь в IndexedDB с идемпотентными мутациями, без local-first движков.**

Решающие аргументы в порядке веса:

1. **Скорость до пилота.** Единственный кандидат, где к неделе 4 реалистично иметь весь контур (голос → карточка → push → отчёт → приёмка) без единого дня, потраченного на сборки, сертификаты и раздачу бинарников. Дистрибуция — ссылка; это идеально совпадает с «очный онбординг за 2 минуты».
2. **Качество генерации ИИ-агентами — максимум по рынку.** React + Next + TS + Tailwind + Framer Motion + Supabase — каждый элемент стека в топе по объёму обучающих данных и предсказуемости паттернов. Для проекта, где агенты пишут почти всё, это буквально главный производственный фактор: меньше галлюцинаций API, меньше итераций, больше «заработало с первого раза». Remix/Start, Svelte 5 и Flutter проигрывают именно здесь, независимо от их технических достоинств.
3. **Сопровождение одним человеком.** Один репозиторий, один деплой, managed-БД/realtime/storage, ноль своих серверов. После запуска этот же человек чинит и развивает систему — каждая невыбранная движущаяся часть экономит его время каждую неделю.
4. **Риск уведомлений закрыт архитектурно, а не надеждой.** Web Push покрывает iPhone (PWA) и большинство Android; Telegram-бот гарантирует доставку всем, включая Huawei без GMS — и он же страхует сам продукт: критичное поручение никогда не потеряется из-за браузерных капризов. Компания уже живёт в Telegram — фолбэк лежит на знакомой территории.
5. «Скучно и надёжно» здесь совпадает с оптимально: у Next.js PWA нет ни одного свойства, из-за которого продукт бы не получился, а у всех альтернатив есть хотя бы одно (дистрибуция и GMS у D/E, налог на незрелость знаний у C/F, второй деплой у B).

Осознанная плата: потолок «нативности» ощущений ниже, чем у RN/Flutter, и push на iPhone зависит от корректной установки PWA. Обе платы управляются: первая — дисциплиной анимаций и полировкой хаптики/переходов, вторая — очным онбордингом и Telegram-дублем.

## Что бы заставило меня передумать (условия-триггеры)

- **Пилот покажет недоставку push у >10–15% сотрудников**, несмотря на онбординг и Telegram-дубль (например, MIUI будет убивать и браузерный канал, а Telegram сотрудники замьютят) → миграция сотрудницкого клиента на Expo/RN (кандидат D), с сохранением Next.js для директора/ТВ/бэкенда — стек React позволяет переносить логику, а не переписывать.
- **Директор после пилота скажет, что PWA «не дотягивает» до Kaspi по ощущению** (жесты, переходы, скролл), и это подтвердится как причина неиспользования → тот же переход на Expo для мобильного клиента; это решение дешевле принимать на неделе 5, чем на неделе 0, когда о реальной чувствительности директора известно всё из брифа, но ничего из рук.
- **Понадобится фоновая/длинная запись голоса с заблокированным экраном** как обязательный сценарий диктовки директора → у веба тут стеклянный потолок; нативная оболочка (хотя бы только для директора) станет оправданной.
- **SaaS-масштабирование на десятки компаний с требованием «приложение в сторе» от клиентов** → публикация становится маркетинговым требованием; Expo-обёртка вокруг существующего React-кода — план Б, заложенный выбором React.
- **Появление второго разработчика с глубокой экспертизой во Flutter/RN** → фактор «ИИ-агенты пишут React лучше» теряет монопольный вес.

## Неочевидное: что все обычно упускают в подобных продуктах

1. **Матрица доставки уведомлений — это продуктовая фича №1, а не инфраструктурная деталь.** Все проектируют «отправку» push и почти никто — **подтверждение получения**. Здесь провал «сотрудник не увидел» определён как провал продукта — значит нужна доставка с квитанциями: push → нет открытия за N минут → Telegram → нет реакции → эскалация на дашборд директора («Ерлан не видел поручение 40 минут»). Это превращает ненадёжность каналов из риска в управляемый процесс — и одновременно даёт директору ощущение контроля, за которое он и покупает систему.
2. **Onboarding-скрипт — часть кодовой базы.** Очная установка за 2 минуты на MIUI — это конкретная последовательность: установить PWA, разрешить уведомления, выключить оптимизацию батареи для браузера, тестовый push «на глазах». Нужен внутренний чек-лист-экран «проверка устройства» (push дошёл? стендалон-режим? версия свежая?), который админ прогоняет при онбординге. Никто это не планирует — потом это узнаётся на пилоте болью.
3. **Идемпотентность мутаций важнее оффлайн-кэша.** На плохой связи главный баг — не «не видно данных», а «нажал дважды / запрос ушёл, ответ не пришёл». Client-generated ID на каждое действие решает это дёшево; без него любой оффлайн-слой генерирует дубли «принял» и двойные начисления очков.
4. **ТВ-экран — это не «ещё одна страница», это appliance.** Нужны: автозапуск в kiosk-режиме, переживание перезагрузки телевизора/мини-ПК, watchdog на зависший WebSocket (тихий мёртвый экран в кабинете директора — репутационная катастрофа продукта), запрет screensaver, обновление страницы по ночам. Полдня работы, если знать заранее; неделя позора, если нет.
5. **Game feel убивают не анимации, а джанк между ними.** Дёрганый скролл из-за тяжёлых теней, layout shift при загрузке аватарок, 300мс задержки перед реакцией на тап — директор с эталоном Kaspi заметит это раньше, чем оценит конфетти. Бюджет полировки надо тратить сначала на «ничего не дёргается и всё отвечает мгновенно» (optimistic UI поверх outbox — тот самый механизм), и только потом на спецэффекты.
6. **Право на публичный рейтинг — UI-задача.** Согласие на публичный рейтинг/ТВ (закон РК о персональных данных) — это флаг в профиле и режим анонимизации на ТВ-экране («сотрудник №7»), предусмотренный в вёрстке с первого дня. Прикручивать анонимизацию к готовому лидерборду постфактум — переделка всех поверхностей сразу.
