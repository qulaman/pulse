# Задание: экспертное ревью концепта командой специалистов — WAG Pulse

Ты — **тимлид виртуальной ИТ-команды**. Твоя задача: развернуть из себя 5 параллельных субагентов-специалистов (через Agent tool), дать каждому концепт проекта «на съедение» со своей профессиональной колокольни, собрать их отчёты и свести в единый синтез. Ты сам код не пишешь и доки не правишь — ты организуешь ревью и синтезируешь результат.

## Контекст и координация

- Прочти сначала `WORKLOG.md` (правила координации окон) и `CLAUDE.md`.
- Документы проекта: `CONCEPT.md`, `FRONTEND.md`, `BACKEND.md`, `DATABASE.md`, `PLAN_12_WEEKS.md`. **Внимание:** параллельный агент, возможно, уже перенёс их в `/docs/` — проверь оба места, работай с тем, что есть.
- ❌ НЕ менять содержание существующих доков. ❌ НЕ писать код приложения. ❌ НЕ создавать `DECISIONS.md`.
- ✅ Твоя зона: папка `/reviews/` (создай) и append-записи в `WORKLOG.md`.
- Если репозиторий уже git (окно 2 могло сделать `git init`) — в конце закоммить `/reviews`: `docs(reviews): expert team review of the blueprint`. Если git ещё нет — просто оставь файлы.

## Как запускать специалистов

Запусти всех 5 субагентов ПАРАЛЛЕЛЬНО (одним сообщением, 5 вызовов Agent tool). Каждому в промпт включи:
1. Его роль и фокус (ниже).
2. Список файлов для чтения: его профильный док + обязательно `CONCEPT.md` и `CLAUDE.md` целиком, остальные — по мере надобности.
3. Требование: писать отчёт на русском, в файл `reviews/<ИМЯ>.md`, строго по общему формату (ниже).
4. Установку: «Проект будет строиться ИИ-агентами по этим докам. Твоя цель — найти всё, что сломается, недоспроектировано или заставит агента гадать. Хвалить не нужно, вежливость не нужна — нужна профессиональная жёсткость. Но критика без конкретного предложения не засчитывается».

## Общий формат отчёта специалиста

```markdown
# Ревью: <роль> — WAG Pulse
## Вердикт (3–5 предложений: готовность моей области к разработке по 10-балльной шкале и почему)
## Критические проблемы (сломается / заблокирует разработку — каждая: суть, где в доках, последствие, конкретное решение)
## Дыры проектирования (агент будет вынужден гадать — каждая: вопрос + мой рекомендуемый вариант ответа)
## Противоречия между документами (цитаты/ссылки на оба места)
## Улучшения (не блокируют, но подняли бы качество; с приоритетом high/mid/low)
## Вопросы владельцу продукта (только то, что НЕ может решить инженер — бизнес/продуктовые развилки)
## Чего не хватает в доках для агентной разработки (какие спецификации/контракты/фикстуры я бы потребовал перед стартом)
```

## Пять специалистов

### 1. `reviews/FRONTEND_REVIEW.md` — Senior Frontend (Next.js 15 App Router, PWA, Framer Motion)
Фокус: реализуемость FRONTEND.md. PWA на iOS (push, standalone, ограничения Safari), serwist vs next-pwa, MediaRecorder на iOS (формат аудио!), офлайн-очередь в IndexedDB, Realtime-подписки и жизненный цикл в фоне, бюджет производительности game feel на бюджетном Android, целевые метрики (<2 сек старт, <3 сек голос→карточка) — реалистичны ли и чем меряем, структура роутов и route groups, состояние (какой state manager — в доках не сказано), Web Share Target на практике.

### 2. `reviews/BACKEND_REVIEW.md` — Senior Backend (Next.js API, Supabase Edge Functions, интеграции)
Фокус: BACKEND.md. Голосовой конвейер: тайминги, ретраи, идемпотентность confirm (client_request_id — как именно), гонки при двойном тапе. Push-цепочка: Postgres trigger → pg_net → Edge Function — надёжность, что при падении, очередь недоставленных, индикатор недоставки директору (как технически узнаём?). Telegram-fallback: когда именно срабатывает. Лимиты Vercel (таймауты route handlers на аудио!), стриминг больших файлов, безопасность endpoint'ов (/api/tv/control), rate limiting. Секреты, среды dev/prod, две среды Supabase или одна.

### 3. `reviews/DATABASE_REVIEW.md` — Senior DBA / Postgres (RLS, Supabase)
Фокус: DATABASE.md. Полнота схемы против всех фич CONCEPT (найди сущности, упомянутые в фичах, но отсутствующие в схеме — напр. ai_logs описан только вскользь, статусы «прочитано», тихий режим, ранги). RLS-политики: реальные дыры (manager и поддерево manager_id — рекурсия?), ТВ-режим с anon-ролью — как безопасно. mv_pulse_summary: refresh concurrently требования, гонки. point_transactions: выбери и обоснуй паттерн заморозки (hold-final vs release+final). Индексы, партиционирование не нужно ли task_messages, миграционная дисциплина, seed-данные для dev.

### 4. `reviews/AI_REVIEW.md` — Специалист по LLM/агентным системам (STT, Claude API, tool use)
Фокус: голосовой конвейер как AI-система. СТТ-гейт: методика теста 30 фраз (как считать точность имён, чем нарезать), Whisper vs Deepgram vs gpt-4o-transcribe для русско-казахской смешанной речи, кастомные словари. Промпт парсера: оцени JSON-схему сущностей из BACKEND.md, чего не хватает (confidence на поле! неоднозначность дедлайнов, часовой пояс, «Ерлану и Марату» — один task или два), структура few-shot, нужен ли structured output API vs JSON в тексте. Evals: как построить регрессионный набор фраз и гонять при каждой правке промпта (это критично — вписать в процесс). Голосовые вопросы (tool use): границы, что при галлюцинации. ai_logs: схема полей для последующего анализа. Стоимость: оценка $/месяц на 45 человек. Модель: claude-haiku-4-5 достаточно ли для парсинга — где порог перехода на Sonnet.

### 5. `reviews/UX_REVIEW.md` — Senior Product/UX-дизайнер (mobile-first, B2B)
Фокус: пользовательские сценарии от и до, по шагам. Пройди мысленно: (а) директор утром наговорил 5 поручений — весь путь до push у сотрудников, где трение; (б) сотрудник на стройке с плохой связью получил задачу — принял — отчитался фото; (в) директор в конце дня разбирает 12 отчётов свайпами; (г) первый день нового пользователя (онбординг PWA + push, особенно iOS). Экран подтверждения: не станет ли узким горлышком при 5+ сущностях. 3 кнопки сотрудника: хватает ли на реальные ситуации («сделал наполовину», «это не мне»). Эфир vs личный канал: не запутается ли сотрудник, где что. Геймификация: риски демотивации, антирейтинг, справедливость очков глазами сотрудника. ТВ в кабинете: приватность при посетителях. Тексты и тон уведомлений. Что бы выкинул из MVP.

## Синтез (после получения всех 5 отчётов)

Напиши `reviews/SYNTHESIS.md`:
1. **Сводный вердикт** готовности чертежа (и оценки каждой области).
2. **Блокеры перед стартом разработки** — дедуплицированный список со ссылками на отчёты, отсортированный по тяжести.
3. **Все вопросы владельцу продукта** — собранные из отчётов, сгруппированные по темам, без дублей. Это сырьё для будущего `DECISIONS.md` (его пишет окно 1 — не создавай сам).
4. **Противоречия между областями** — где специалисты предлагают несовместимое (отметь, нужен арбитраж).
5. **Топ-10 улучшений** по соотношению ценность/усилия.

Затем допиши в `WORKLOG.md` (append, формат внутри файла): запись «Окно 3 — экспертное ревью команды» с итогами, и продублируй в раздел «Открытые вопросы» краткий список вопросов владельцу (одной строкой каждый, со ссылкой на SYNTHESIS.md).

## Definition of Done

- [ ] 5 отчётов в `/reviews/`, каждый строго по формату, содержательный (не менее 8–10 конкретных находок на специалиста; вода и пересказ доков не считаются).
- [ ] `reviews/SYNTHESIS.md` со сводкой, блокерами и вопросами владельцу.
- [ ] Запись в `WORKLOG.md` + «Открытые вопросы» пополнены.
- [ ] Если есть git — один коммит с `/reviews`.
