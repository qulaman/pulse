## Что это за проект

**Видение (V-01): коммерческий SaaS-продукт «голосовое управление компанией», цель — 100+ компаний-клиентов в Казахстане и СНГ, с выходом за рубеж.** Мы строим не внутренний инструмент одной фирмы, а тиражируемый продукт с выручкой в миллионы. West Arlan Group (~40–50 сотрудников, Казахстан) — клиент №1, полигон и живая витрина для продаж: на ней продукт обязан доказать ценность, прежде чем масштабироваться.

Как это работает: директор голосом раздаёт задачи/объявления/очки → STT + Claude парсят → сотрудники получают карточки в PWA → отчитываются → дашборд «Пульс» и ТВ-экран показывают всё в реальном времени. Плюс рейтинг очков и магазин мерча.

Следствия видения для кода (обязательны всегда): **модель SaaS — изолированные инстансы (V-02): у каждого клиента СВОЯ БД и СВОЙ деплой**, никакой общей БД на всех клиентов; ничего компанийно-специфичного в коде — всё настраиваемое живёт в `company.settings` и env; данные только в переносимом Postgres (изоляция позволяет размещать базу клиента в его юрисдикции — ст. 12 закона РК о ПД); тексты UI — без упоминаний WAG вне конфига.

Дисциплина скоупа при этом не отменяется: «пригодится для SaaS» — НЕ аргумент тащить фичу в текущую неделю (DECISIONS.md G.15). Видение определяет архитектуру, а не порядок работ: сначала продукт, влюбляющий клиента №1, потом тираж.

## Стек (финализирован слепым исследованием, D-39; не менять без записи в DECISIONS.md)

- **Next.js 15+ (App Router), TypeScript strict, Tailwind, Framer Motion, Recharts**
- **State**: TanStack Query v5 (всё серверное состояние, optimistic-обновления) + Zustand (только эфемерное UI). Realtime — через единый хук `useRealtimeQuery` (см. docs/FRONTEND.md)
- **Supabase** (регион Франкфурт): Postgres + RLS, Auth, Realtime, Storage, Edge Functions, pg_cron. Materialized views не используем — обычные view
- **PWA**: `@serwist/next` (next-pwa запрещён — заброшен, конфликтует с Next 15), Web Push (VAPID), свой service worker
- **AI**: STT — `gpt-4o-transcribe` c prompt-ростером имён за сменным интерфейсом `lib/ai/stt.ts` (fallback-провайдер через env); парсинг — Claude API `claude-haiku-4-5` через **structured outputs** (никакого «парсим JSON из текста» + repair-retry); вопросы к данным — Sonnet-класс, strict tools. SDK — `@anthropic-ai/sdk` напрямую + ручной SSE-стриминг; **Vercel AI SDK не вносить**
- **Доставка уведомлений — подсистема с квитанциями** (это продуктовая фича №1, см. docs/BACKEND.md): Web Push + Telegram-бот (grammY) как гарантийный ярус с эскалацией; SMS — заложенный интерфейс канала, не строим
- Деплой: Vercel (preview→dev, production→prod); два проекта Supabase (dev+prod) с первого дня

## Незыблемые принципы

1. **Ценность = количество убранных действий.** Основной вход директора — голос ИЛИ свободный текст одной строкой; оба идут в один парсер (включая Web Share Target). Каждая новая фича проходит фильтр: «добавляет ли она хоть один тап к основному флоу?» — если да, переделать или не выпускать. Насмотренность директора ≠ желание сложности: глубина только вторым слоем по явному тапу.
1a. **Game feel обязателен, но включается по гейту адаптации** (неделя 8, после 2–3 недель ежедневного использования директором — D-40) **и никогда не блокирует действие**: данные пишутся мгновенно, эффекты играют поверх через `<EffectsLayer>`. Тестировать на бюджетном Android (Redmi-класс).
2. **У сотрудника максимум 3 кнопки** на карточке задачи: Принял / Уточнить / Не могу (причины-чипами).
3. **Задачу закрывает только директор** (pending_review → done | rework). Отзыв задачи (revoked) — тоже только директор.
4. **Баланс очков = SUM(point_transactions)**. Никогда не хранить и не мутировать баланс как поле. Append-only; заморозка магазина — паттерн hold-final.
5. **Аудио всегда сохраняется до AI-вызовов** (клиент грузит напрямую в Storage по signed URL) и доступно адресату задачи. Голосовое не может потеряться ни при каком сбое.
6. **Модель SaaS — изолированные инстансы (V-02).** Каждый клиент = отдельная БД (свой Supabase-проект) + отдельный деплой. Следствия: (а) код полностью клиент-агностичен — никаких ветвлений «если клиент X»; (б) провижининг скриптован (клиент под ключ за день, см. docs/SETUP.md); (в) миграции на флот — только через CI; (г) `company_id` + RLS в схеме СОХРАНЯЮТСЯ (защита ролей внутри компании + страховка), но кросс-клиентской логики не существует.
7. **Идемпотентность обязательна на каждой мутации**: `client_request_id` (uuid с клиента) на всех мутирующих вызовах; многотабличные операции — только Postgres-функции `security definer` через `rpc()` (supabase-js транзакций не умеет — не пытаться).
8. **Доставка — с квитанциями.** Каждое уведомление проходит outbox `notification_deliveries`; статусы директору: «отправлено / увидел / принял» (формулировка «не открывал с 9:14», не «не получил»); эскалация в Telegram через таймаут. Тихие часы доставки 08:00–21:00 Asia/Aqtobe.
9. Язык интерфейса — русский. Комментарии в коде — английский.
10. Мобильный-first. Отдельный роут `/tv` — только чтение, ноль интеракций; киоск — auth-пользователь роли `tv`.

## Статусы задач (enum; расширение — только через DECISIONS.md)

`scheduled → sent → accepted → pending_review → done | rework(→ снова accepted) | declined | revoked`

- `scheduled` — отложенная отправка, невидима адресату; push только на переходе в `sent`.
- `in_progress` существует в enum, но в UI v1 НЕ используется (D-04).
- `declined` («Не могу» + причина) — у директора действия: Переназначить / Отменить / Настоять.
- `revoked` — отзыв директором (D-01); правка задачи = отзыв + новая.
- «Уточнить» — НЕ статус: сообщение с `meta.is_question`, закрывается первым ответом директора (`meta.answered_at`).

## Регламент работы агента (каждая сессия)

1. **Одна задача = одна сессия = одна ветка** (`feat/...`). Задачи бери из `/tasks/NNN-*.md` или из недельного плана; вне скоупа задачи ничего не делай, идеи — в бэклог WORKLOG.md.
2. Порядок: прочитать CLAUDE.md + профильные docs/*.md → план → код → тесты → самопроверка `/code-review` → обновить `tracker/index.html` (статус задачи в DATA) → запись в WORKLOG.md → conventional commit.
3. **Стоп-правила**: нужно решение, которого нет в DECISIONS.md, — остановись и спроси. Противоречие доков — прав DECISIONS.md, о противоречии сообщи. Секрет в код не попадает никогда.
4. Любое изменение схемы БД — только новой миграцией (`YYYYMMDDHHMMSS_описание.sql`), RLS-политики в той же миграции; правки старых миграций запрещены; `db push` в прод запрещён.
5. **PR, трогающий промпт парсера / схему сущностей / few-shot, обязан приложить результат `pnpm eval:parser`** (гейты: assignee ≥97%, entity F1 ≥90%). Правка без evals не мержится.
6. Все времена в БД — timestamptz UTC; отображение — Asia/Aqtobe (UTC+5); расписания pg_cron — в UTC.
7. Коммиты мелкие, по фиче; conventional commits.

## Очерёдность разработки (по docs/PLAN_12_WEEKS.md, скоуп пилота — D-40(в))

1. **Недели 1–4, MVP-ядро**: СТТ-гейт (50 фраз) → миграции ядра + RLS-паттерн → auth (QR-инвайт + PIN) → личный канал → подсистема доставки (push + Telegram-ярус + квитанции) → голосовой конвейер с мульти-сущностями → /confirm с правками → Пульс-минимум → приёмка кнопками → отзыв задачи.
2. **Недели 5–6, пилот на ядре** (директор + 5 сотрудников): БЕЗ очков, магазина, ТВ и game feel. Фиксы + Эфир.
3. **Неделя 7**: ассистент (вопросы к данным, strict tools, SSE).
4. **Неделя 8 — гейт адаптации**: директор пользуется ежедневно ≥2 недели → очки + реакции + game feel; иначе неделя на удержание ядра.
5. **Недели 9–12**: раскатка на компанию + согласия → магазин → ТВ + пульт → полировка, безопасность, отчёт инвестору.

## Definition of Done для фичи (полная версия — docs/TESTING.md)

- Работает на телефоне (эмуляция iPhone SE и среднего Android) — проверено визуально; аудио-фичи — смоук «Android-запись → iPhone-воспроизведение».
- RLS проверена негативным тестом (сотрудник не видит чужого).
- Realtime: свернул приложение на 5 минут → развернул → данные актуальны без перезагрузки.
- Оффлайн: действие, сделанное без сети, доезжает после появления сети ровно один раз (идемпотентность).
- Ошибки сети/AI обработаны: у пользователя всегда понятное состояние, голосовое не теряется.
- Статус задачи обновлён в `tracker/index.html`, запись в WORKLOG.md сделана.
