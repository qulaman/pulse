# Синтез экспертного ревью — WAG Pulse

Сводка по пяти отчётам виртуальной команды: [FRONTEND_REVIEW.md](FRONTEND_REVIEW.md), [BACKEND_REVIEW.md](BACKEND_REVIEW.md), [DATABASE_REVIEW.md](DATABASE_REVIEW.md), [AI_REVIEW.md](AI_REVIEW.md), [UX_REVIEW.md](UX_REVIEW.md).

## 1. Сводный вердикт

**Готовность чертежа к агентной разработке: ~4.5/10.** Продуктовая концепция цельная и зрелая (это отметили все пятеро), но инженерный слой описан намерениями, а не контрактами: три несущих механизма (атомарность записи, идемпотентность, надёжность доставки push) не спроектированы, ключевые таблицы (ai_logs, доставка уведомлений, идемпотентность) отсутствуют в схеме, JSON-контракт парсера неполон, auth/онбординг не описан вовсе. Каждый специалист независимо пришёл к одному выводу: агент соберёт happy path и молча заложит потерю данных/дубли/дыры безопасности. Оценка команды: **1–2 недели плотной доработки спецификаций до старта недели 1 поднимают готовность до 8/10** — почти все находки закрываются правками доков, а не кодом.

| Область | Оценка | Главная претензия |
|---|---|---|
| UX/Product | 6/10 | Описан только «счастливый путь»; auth/онбординг, declined, правка текста на /confirm — дыры с продуктовыми ответами |
| Frontend | 5/10 | Аудиоформат iOS↔Android ломает «сердце продукта»; SW-фреймворк, state manager, офлайн-очередь не выбраны |
| Backend | 4/10 | Транзакции, идемпотентность и push-цепочка — лозунги без контрактов; лимиты Vercel убьют /transcribe |
| Database | 4/10 | Невозможные конструкции Postgres (CONCURRENTLY из триггера, view с параметром), рекурсия RLS, недостающие сущности |
| AI/LLM | 4/10 | СТТ-гейт неизмерим, схема сущностей без confidence, evals отсутствуют, маршрутизация «команда vs вопрос» не спроектирована |

## 2. Блокеры перед стартом разработки

Дедуплицировано; отсортировано по тяжести (сломает данные/безопасность → заблокирует неделю → дискредитирует продукт).

### Целостность данных и безопасность

1. **Атомарные операции невозможны через supabase-js** — все многотабличные записи (confirm, магазин, авто-очки) оформить как Postgres-функции `security definer`, вызываемые через `rpc()`. Список функций и сигнатуры — в BACKEND.md. → [BACKEND №1](BACKEND_REVIEW.md), [DATABASE №4](DATABASE_REVIEW.md)
2. **Идемпотентность confirm не спроектирована**: `client_request_id` упомянут, но нет ни таблицы, ни семантики при дубле; ретраи заложены в дизайн офлайн-очереди — дубли задач и очков гарантированы. Двое предложили разные механизмы (см. §4.3) — выбрать один и распространить на все мутирующие эндпоинты. → [BACKEND №2](BACKEND_REVIEW.md), [DATABASE дыра 4](DATABASE_REVIEW.md), [FRONTEND №5](FRONTEND_REVIEW.md), [AI улучш.](AI_REVIEW.md)
3. **RLS-паттерн не задан**: наивная политика на profiles = бесконечная рекурсия 42P17; «поддерево manager_id» = рекурсивный CTE на каждую строку. Зафиксировать `auth_company_id()`/`auth_role()` (или JWT-клеймы) и глубину 1 для менеджера. → [DATABASE №2, №3](DATABASE_REVIEW.md)
4. **Double-spend в магазине**: `FOR UPDATE` на stock не защищает SUM-баланс; advisory-lock по user_id + страховочный constraint-триггер. Паттерн заморозки зафиксирован командой: **hold-final**, `shop_final` удалить из enum (сошлись трое независимо). → [DATABASE №4, №5](DATABASE_REVIEW.md), [BACKEND противоречие 5](BACKEND_REVIEW.md), [UX дыра 8](UX_REVIEW.md)
5. **ТВ-режим на anon-ключе — дыра**: RLS не работает на MV/view, публикация в broadcast-канал открыта любому сотруднику, аутентификация киоска не описана. Нужна единая архитектура (варианты разошлись — см. §4.5). → [BACKEND №6](BACKEND_REVIEW.md), [DATABASE №8](DATABASE_REVIEW.md), [FRONTEND противоречие 6](FRONTEND_REVIEW.md)
6. **Рейтинг несовместим с RLS «свои транзакции читает каждый»** — отдавать только через `fn_rating()` security definer с учётом настройки top5/full; события мерча — через публичную таблицу событий. → [DATABASE №9](DATABASE_REVIEW.md)

### Заблокирует конкретную неделю плана

7. **Auth/онбординг не спроектирован вовсе** (аккаунты, инвайты, привязка Telegram, in-app-браузеры iOS) — блокирует недели 1–2; аудитория «водители и завхозы» не переживёт email-magic-link. → [UX К1](UX_REVIEW.md), [BACKEND дыра 1](BACKEND_REVIEW.md)
8. **Аудиоформат iOS↔Android**: webm/opus не играет на iPhone — принцип «аудио всегда доступно сотруднику» нарушен архитектурно. Матрица mimeType (audio/mp4 первым) + план транскода + смоук-тест в DoD. → [FRONTEND №1](FRONTEND_REVIEW.md)
9. **Лимиты Vercel убьют /api/voice/transcribe** (body 4.5 МБ, maxDuration): аудио грузит клиент напрямую в Storage по signed URL, в API — только путь. → [BACKEND №5](BACKEND_REVIEW.md)
10. **Push-цепочка fire-and-forget**: pg_net не ретраит и не сообщает об ошибках; обещанный «индикатор недоставки» (неделя 2!) строить не из чего, а Web Push вообще не имеет delivery receipt — нужна таблица доставки + ack-контракт + честная семантика «не открывал» (схемы разошлись — см. §4.2). → [BACKEND №3, №4](BACKEND_REVIEW.md), [DATABASE дыра 1](DATABASE_REVIEW.md), [UX К6](UX_REVIEW.md)
11. **ai_logs не спроектирована**, а на ней главная метрика пилота «доля правок»; /confirm обязан писать diff parsed↔confirmed. Три варианта схемы — унифицировать (см. §4.4). → [BACKEND №9](BACKEND_REVIEW.md), [DATABASE №7](DATABASE_REVIEW.md), [AI №7](AI_REVIEW.md)
12. **JSON-схема сущностей неполна**: нет confidence-полей (CONCEPT требует подсветку!), мульти-исполнителей (`assignee_queries[]` → N задач), пометки интерпретированных дедлайнов; парсинг перевести на structured outputs вместо «ТОЛЬКО JSON»+repair-retry. → [AI №3, №4](AI_REVIEW.md)
13. **Маршрутизация «команда vs вопрос» не спроектирована**: одна FAB, два эндпоинта, никто не решает, куда идёт транскрипт. Добавить `kind:"query"` в схему парсера. → [AI №6](AI_REVIEW.md)
14. **СТТ-гейт неизмерим**: «точность имён 95%» не определена (падежи!), корпус не специфицирован, `prompt` Whisper с ростером имён — главный рычаг точности казахских имён — не задействован. → [AI №1, №2](AI_REVIEW.md)
15. **Evals парсера отсутствуют в процессе** — правки промпта после пилота будут чинить одну фразу и молча ломать три. Фикстуры фраз + скоринг + правило «PR с правкой промпта без eval не мержится». → [AI №5](AI_REVIEW.md)
16. **`REFRESH MV CONCURRENTLY` из триггера невозможен** в Postgres + нет обязательного unique-индекса на MV (судьба самой MV — предмет арбитража, см. §4.1). → [DATABASE №1](DATABASE_REVIEW.md)
17. **Отложенная отправка сломана**: статус `draft/null` не существует, push-триггер на insert отправит пуш ночью. Добавить `scheduled` в enum (двое сошлись), push — только на переход в `sent`. → [BACKEND №7](BACKEND_REVIEW.md), [DATABASE №10](DATABASE_REVIEW.md)
18. **`rule_code` для идемпотентности авто-очков отсутствует в схеме** — cron будет штрафовать одну просрочку многократно. → [BACKEND №8](BACKEND_REVIEW.md), [DATABASE №6](DATABASE_REVIEW.md)
19. **Среды dev/prod не определены** (один проект Supabase = миграции на живом пилоте; смена VAPID-ключей убивает все подписки). → [BACKEND №10](BACKEND_REVIEW.md)
20. **serwist vs next-pwa не выбран** — первое, что агент установит; next-pwa мёртв и конфликтует с Next 15. Зафиксировать @serwist/next. → [FRONTEND №2](FRONTEND_REVIEW.md)

### Дискредитирует продукт на пилоте

21. **/confirm не позволяет править текст задачи** — при ошибке Whisper директор переговаривает всё заново; CONCEPT сам называет это фатальным. → [UX К2](UX_REVIEW.md)
22. **Пилот (нед. 5) раньше мульти-сущностей (нед. 6)** — «5 поручений одним голосовым» прозвучит в первый день; сдвинуть мульти-сущности до пилота. → [UX К4](UX_REVIEW.md), [AI противоречие 4](AI_REVIEW.md)
23. **`declined` — тупик без переназначения**; **свайпы без undo и без семантики для 3 из 4 стопок**; **автоштраф −5 по AI-выведенному дедлайну без канала возражения**; **`in_progress` без единого UI-триггера**. → [UX К3, К5, К7, К8](UX_REVIEW.md)
24. **Realtime в свёрнутой PWA умирает молча** (потерянные события = директор видит вчерашний день) — обязательный паттерн snapshot+resubscribe; **метрика «голос→карточка <3 сек» недостижима последовательной цепочкой** — стриминг чанков при записи + переопределение как p50/p90. → [FRONTEND №3, №4](FRONTEND_REVIEW.md)

## 4. Противоречия между областями (нужен арбитраж)

Места, где специалисты предлагают несовместимое. Решение — за окном 1 / владельцем.

1. **Судьба mv_pulse_summary.** DBA чинит refresh (pg_net → Edge Function + advisory lock, unique-индекс) и сохраняет MV; Backend считает MV на 45 человек преждевременной — обычные view поверх индексов, а если MV, то refresh только по pg_cron. *Рекомендация синтеза: начать с обычных view (проще, нет класса проблем с refresh), MV — по факту медленных запросов; контракт колонок нужен в любом случае (требование Frontend).*
2. **Таблица доставки уведомлений.** Backend: `notification_deliveries` с очередью (queued/sent/failed, attempts, cron-свип — outbox-паттерн); DBA: `notification_log` как журнал (sent/failed/delivered). Семантики разные: очередь с ретраями vs лог фактов. *Рекомендация: outbox-вариант Backend (он же решает ретраи), имя и поля зафиксировать в DATABASE.md; ack-семантику UX (К6) встроить туда же.*
3. **Механизм идемпотентности confirm.** Backend: отдельная таблица `ingest_batches` с сохранённым result и `on conflict do nothing`; DBA: `client_request_id` в ai_logs + журнал `ingest_requests`. *Рекомендация: вариант Backend — возврат сохранённого result при дубле обязателен (клиент должен получить те же id), ai_logs связывать тем же client_request_id.*
4. **Схема ai_logs.** Три варианта (Backend, DBA, AI) с разными наборами полей. *Рекомендация: за основу — вариант AI (самый полный: токены, tool_calls, edit_fields, source_span), сверить с полями Backend/DBA и зафиксировать в DATABASE.md одной миграцией.*
5. **Архитектура ТВ.** Frontend: подписанный tv_token → Supabase-JWT с ролью tv; Backend: служебный пользователь tv@company с ролью tv + private broadcast-канал (публикация только service role); DBA: таблица `tv_events` с предмаскированным payload_guest + Postgres Changes под RLS. Совместимы частично, но канал (broadcast vs Postgres Changes) и источник данных (view vs tv_events) — развилка. *Рекомендация: auth-пользователь с ролью tv (Backend) + tv_events как источник (DBA — единственный вариант, где guest-маскирование гарантировано на записи, а не на клиенте); tv_control — private broadcast по схеме Backend.*
6. **Vercel AI SDK.** Backend рекомендует стримить /voice/query через AI SDK («и так в плане недели 7»); AI-специалист и Frontend флагуют его как незаявленную зависимость (useChat = второй state-слой рядом с TanStack Query), решение требуется до недели 3. *Рекомендация: @anthropic-ai/sdk напрямую + ручной SSE-стриминг; AI SDK не вносить, PLAN нед. 7 поправить.*
7. **Контракт «вопроса» сотрудника.** DBA: enum-тип `question` либо `meta.answered_at`, проставляемый при ответе (рекомендует второе); UX: `meta.is_question` + «вопрос закрыт любым последующим сообщением директора». Разные условия закрытия. *Рекомендация: `meta.is_question` на сообщении + `meta.answered_at`, проставляемый триггером при первом ответе директора — дёшево для счётчика стопки и однозначно.*

**Сошлись независимо (арбитраж не нужен, зафиксировать как решения):** hold-final для заморозки очков (Backend+DBA+UX); статус `scheduled` в enum (Backend+DBA); мульти-исполнитель = N независимых задач-копий (AI+UX); загрузка аудио клиентом в Storage по signed URL (Backend+Frontend); менеджерская видимость = глубина 1 (DBA, согласуется с CONCEPT); фикстуры 30 фраз = СТТ-гейт = few-shot = evals — один корпус (AI+Frontend+DBA+UX).

## 5. Топ-10 улучшений (ценность/усилия)

1. **`prompt` Whisper со списком имён сотрудников** — главный дешёвый рычаг точности казахских имён; одна строка кода, внести до СТТ-гейта. [AI]
2. **Тихие часы доставки 08:00–21:00** — директор встаёт в 5:00, сотрудники не должны получать push в 6 утра; авто-`scheduled_send_at` с пометкой на /confirm. [UX]
3. **Единый хук `useRealtimeQuery`** (snapshot+resubscribe+setQueryData) — переводит «свежесть лент» из «помнить всем» в «нельзя сделать иначе». [FRONTEND]
4. **Стриминг аудио-чанков во время записи** (timeslice) — к отпусканию кнопки аудио уже на сервере; главный рычаг метрики <3 сек. [FRONTEND]
5. **Список индексов от DBA** (task_messages, point_transactions, orders, recurrence_rules…) — вписать в DATABASE.md, агент сам не поставит. [DBA]
6. **Наблюдаемость: Sentry + алерты** на рост failed-доставок и ok=false в ai_logs — соло-разработчик без алертов узнает о падении пушей от директора. [BACKEND]
7. **Компактный режим /confirm при 5+ сущностях** (однострочные свёрнутые карточки, «Отправить N», sticky) — снимает риск «узкого горлышка» мульти-сущностей. [UX]
