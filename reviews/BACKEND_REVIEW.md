# Ревью: Senior Backend — WAG Pulse

## Вердикт

Готовность бэкенд-документации к агентной разработке — **4/10**. Направление и состав эндпоинтов понятны, но три несущих механизма описаны лозунгами, а не контрактами: идемпотентность confirm («через client_request_id» — без схемы, скоупа и поведения при дубле), надёжность push-цепочки (pg_net — fire-and-forget, очереди и статуса доставки нет, хотя «индикатор недоставки» обещан в MVP недели 2) и способ исполнения «одной SQL-транзакции» из Next.js route handler'а (supabase-js транзакций не умеет — агент либо напишет неатомарный код, либо начнёт изобретать). Плюс полностью отсутствует тема сред (dev/prod Supabase), лимитов Vercel на аудио и rate limiting. Агент, строящий по этим докам, соберёт работающий happy path и молча заложит потерю пушей, двойные вставки и таймауты на длинных голосовых.

## Критические проблемы

### 1. «Одна транзакция» невозможна через supabase-js — не сказано, КАК её делать
**Где:** BACKEND.md §1 `/api/voice/confirm` («Одна транзакция: insert announcements / tasks / point_transactions...»), §4 магазин («проверка баланса и stock **в одной SQL-транзакции**... select for update»).
**Последствие:** supabase-js не поддерживает multi-statement транзакции и `select ... for update`. Агент либо сделает серию отдельных insert'ов (частичная запись при сбое: задачи созданы, очки — нет), либо потащит `pg` с прямым коннектом в serverless (исчерпание пула).
**Решение:** зафиксировать в BACKEND.md правило: любая многотабличная атомарная операция = Postgres-функция `security definer` в миграции, вызываемая через `supabase.rpc()`. Перечислить конкретные функции: `confirm_voice_batch(payload jsonb, client_request_id uuid)`, `create_shop_order(user_id, item_id)`, `cancel_shop_order(order_id)`. Route handler — только auth/валидация/вызов RPC.

### 2. client_request_id: механизм идемпотентности не спроектирован, в схеме БД его нет
**Где:** BACKEND.md §1 confirm («Идемпотентность через client_request_id»); DATABASE.md — ни одной таблицы/колонки под это.
**Последствие:** двойной тап по «Всё верно → Отправить» или ретрай на плохой связи (стройплощадка, IndexedDB-очередь из FRONTEND.md — ретраи заложены в дизайн!) = задачи и очки создаются дважды. Application-level проверка «select, потом insert» гонку двух одновременных запросов не ловит.
**Решение:** таблица `ingest_batches(id, company_id, author_id, client_request_id uuid, result jsonb, created_at)` + `unique(company_id, client_request_id)`. Внутри `confirm_voice_batch`: `insert ... on conflict do nothing`; если конфликт — вернуть сохранённый `result` (id созданных сущностей), не создавая ничего. UUID генерируется клиентом при монтировании экрана /confirm и переживает ретраи. Добавить таблицу в DATABASE.md.

### 3. Push-цепочка ненадёжна by design: pg_net — fire-and-forget, очереди недоставленных нет
**Где:** BACKEND.md §2 («Триггер: Postgres trigger → pg_net → Edge Function send-push»); CONCEPT.md §8 и PLAN недели 2 требуют «индикатор недоставки у директора».
**Последствие:** pg_net не ретраит и никому не сообщает об ошибке (ответы падают в `net._http_response`, которую никто не читает). Упала Edge Function / истёк ключ / 5xx у push-сервиса — уведомление потеряно навсегда, и узнать об этом технически невозможно. Обещанный индикатор недоставки строить не из чего.
**Решение:** таблица `notification_deliveries(id, company_id, user_id, task_id, channel enum('push','telegram'), status enum('queued','sent','failed'), attempts int, last_error, created_at, sent_at)`. Триггер вставляет строку `queued` (а не зовёт HTTP). Edge Function `send-push` разбирает очередь (дёргается pg_net'ом как «пинок» + страховочный pg_cron-свип каждую минуту по зависшим `queued`/`failed` с attempts < 3). Индикатор директору = запрос по этой таблице. Без неё вся глава §2 — декорация.

### 4. Условие Telegram-fallback противоречит собственному риск-анализу и не ловит главный кейс
**Где:** BACKEND.md §2: fallback «если у пользователя **нет активных подписок**». CONCEPT.md §8: «китайские Android убивают service worker» — т.е. подписка ЕСТЬ, web-push отвечает 201, но устройство пуш не показывает.
**Последствие:** на проблемных Xiaomi/Huawei (PLAN недели 9 прямо ждёт таких) fallback не сработает никогда — подписка-то активна. «Марат не получил» останется невидимым.
**Решение:** два триггера fallback'а: (а) нет подписок ИЛИ web-push вернул ошибку → Telegram сразу; (б) эскалация по факту: pg_cron каждые 5 минут — задачи в статусе `sent` старше N минут (предлагаю N=10, в company.settings) у пользователей с telegram_chat_id → продублировать в Telegram, отметить в notification_deliveries. «Доставлено» мерить не ответом push-API, а фактом открытия/принятия задачи.

### 5. Лимиты Vercel убьют /api/voice/transcribe: body 4.5 МБ и таймаут по умолчанию
**Где:** BACKEND.md §1 transcribe («Вход: аудио... 1. Сохранить в Storage... 2. Whisper. Ретрай ×2 с backoff»).
**Последствие:** (а) у Vercel serverless жёсткий лимит тела запроса 4.5 МБ — длинное голосовое или m4a с iOS (Safari пишет AAC с битрейтом заметно выше 24kbps-цели из FRONTEND.md) упрётся в 413; (б) дефолтный maxDuration + Whisper на минутном аудио + два ретрая с backoff = обрыв функции посреди ретрая, «голосовое не теряется» нарушено ещё до Storage.
**Решение:** аудио грузит КЛИЕНТ напрямую в Supabase Storage по signed upload URL (эндпоинт `/api/voice/upload-url` выдаёт путь `voice/{company_id}/{user_id}/{uuid}.webm`), в transcribe передаётся только `audio_path`. В transcribe/parse/query проставить `export const maxDuration = 60` (query — стриминг через AI SDK). Ретраи Whisper — максимум 1 внутри запроса, дальше ретрай с фронта по сохранённому пути. Зафиксировать это в BACKEND.md как схему, иначе агент напишет «multipart в route handler» — самый очевидный и самый ломкий вариант.

### 6. /api/tv/control и канал tv_control: авторизация описана «или-или», а аутентификация самого /tv не описана вообще
**Где:** BACKEND.md §5 («проверка через RLS on realtime **или** серверный прокси-endpoint»); DATABASE.md RLS («ТВ-режим работает через отдельный ограниченный token/anon-роль» — без деталей).
**Последствие:** Supabase Realtime broadcast по умолчанию (без private channels + политик на realtime.messages) позволяет ЛЮБОМУ с anon key и company_id публиковать в канал — любой сотрудник переключает ТВ в кабинете директора, а «anon-роль для ТВ» в лоб = данные компании доступны всем, кто узнал URL киоска.
**Решение:** выбрать и зафиксировать: публикация — ТОЛЬКО через `POST /api/tv/control` (проверка role=director по сессии, публикация service role), канал — private channel с authorization-политикой «подписка — да, публикация — никому кроме service role». Аутентификация киоска: отдельный служебный пользователь `tv@{company}` с ролью `tv` в profiles (роль добавить) и RLS-доступом только к событийным view; логин на устройстве один раз. Описать в обоих доках одинаково.

### 7. Отложенная отправка сломана на уровне статусной модели и push-триггера
**Где:** DATABASE.md pg_cron №3 («publish tasks where scheduled_send_at <= now() and **status is null/draft**») vs enum статусов в DATABASE.md/CLAUDE.md, где нет ни null, ни draft, и «не расширять без причины». Плюс BACKEND.md §2: push-триггер «на tasks» — на insert он отправит пуш о задаче, которая должна уйти утром.
**Последствие:** агент упрётся в несуществующий статус и придумает свой; сотрудник получит ночью пуш о «завтрашней» задаче — фича дискредитирована.
**Решение:** добавить в enum значение `scheduled` (это и есть «причина» из CLAUDE.md — зафиксировать её комментарием в миграции), RLS: assignee не видит задачи в `scheduled`, push-триггер — только на переход `scheduled/insert → sent`. Cron №3: `update ... set status='sent' where status='scheduled' and scheduled_send_at <= now()`.

### 8. Идемпотентность авто-очков ссылается на колонку, которой нет в схеме
**Где:** BACKEND.md §3 («Идемпотентно: unique-ключ (task_id, rule_code)») vs DATABASE.md `point_transactions` — колонки `rule_code` нет.
**Последствие:** агент, делающий миграции строго по DATABASE.md (как велит CLAUDE.md), не сможет построить требуемый unique-ключ; overdue-checker раз в 15 минут будет штрафовать одну просрочку многократно.
**Решение:** добавить в DATABASE.md `rule_code text null` + partial unique index `(task_id, rule_code) where source='auto_rule'`. Заодно решить продуктовый кейс done→rework→done: правило «бонус только за первый переход в done» — тоже закрывается этим же ключом.

### 9. Таблицы ai_logs нет в DATABASE.md, а на ней держится половина продуктовой аналитики
**Где:** BACKEND.md §1 и §7 («писать source в ai_logs», «все AI-вызовы логировать в ai_logs»); CONCEPT.md §8 («мониторить долю правок в ai_logs»); PLAN недели 5 («ежедневно читать ai_logs»). В DATABASE.md — отсутствует.
**Последствие:** агент выдумает схему; «доля правок» вообще не логируется нигде — на /confirm правки происходят на фронте, а confirm-эндпоинту сравнивать не с чем.
**Решение:** добавить в DATABASE.md: `ai_logs(id, company_id, user_id, kind enum('stt','parse','query'), model, source enum('voice','typed','shared') null, latency_ms int, ok bool, error text, input_len int, output jsonb, created_at)` + в `/api/voice/confirm` передавать исходный распарсенный массив и подтверждённый: сервер пишет diff (edited bool, edit_kinds text[]) в тот же лог. Иначе главная метрика недели 5 не соберётся.

### 10. Среды: одна Supabase или две — не сказано нигде
**Где:** отсутствует во всех доках; PLAN недели 1 («Supabase проект, Vercel» — в единственном числе).
**Последствие:** агенты будут гонять миграции и тестовые данные на проде, где с недели 5 живой пилот; VAPID-ключи и push-подписки перемешаются между средами (подписка привязана к ключу — смена ключа = все подписки мертвы).
**Решение:** два проекта Supabase (dev — free tier), миграции через supabase CLI: локально → `db push` в dev → в prod только из CI/main. Vercel: preview-окружения смотрят в dev, production — в prod; отдельные пары VAPID, отдельный тестовый Telegram-бот. Прописать раздел «Environments» в BACKEND.md со списком env-переменных по средам.

## Дыры проектирования (агент будет гадать)

1. **Как populate'ится `telegram_chat_id`?** Fallback описан, а привязка аккаунта — нет. Рекомендую: deep-link `https://t.me/<bot>?start=<one-time-code>`, код генерится в профиле сотрудника в PWA, `tg-webhook` по /start сопоставляет code→user_id и пишет chat_id. Плюс валидация вебхука через `secret_token` Telegram (в env).
2. **Чем аутентифицируется Edge Function `send-push` при вызове из pg_net?** Иначе эндпоинт, шлющий пуши от имени компании, открыт всему интернету. Рекомендую: заголовок `x-internal-secret` из Vault/env, pg_net-вызов формирует его из настройки БД; функция сверяет.
3. **Каким эндпоинтом транскрибируются голосовые СОТРУДНИКОВ?** FRONTEND.md: композер «🎤 голосовое (транскрибируется)», BACKEND.md описывает transcribe только как вход директорского конвейера. Рекомендую: тот же `/api/voice/transcribe` с параметром `context: 'director_input'|'task_message'`; для task_message — без parse, результат пишется в `task_messages(type='voice', content=transcript, file_url)`; роль не ограничивать, но rate limit жёстче (см. ниже).
4. **Rate limiting — отсутствует как класс.** Все /api/voice/* жгут платные API. Рекомендую: лимит в БД или Upstash Ratelimit: директор — 30 transcribe/час, сотрудник — 10/час, query — 20/час; 429 с человекочитаемым сообщением. Зафиксировать числа в company.settings.
5. **Конвенция путей Storage и политики.** «Политики зеркалят RLS задач» — красиво, но политика storage.objects пишется по пути. Рекомендую зафиксировать: `voice/{company_id}/{user_id}/{uuid}.webm`, `reports/{company_id}/{task_id}/...` — тогда политики выражаются через `(storage.foldername(name))[1] = company_id` + join к tasks. Без конвенции агент сложит всё в корень и политики не напишет.
6. **Auth-модель route handler'ов.** Как проверяется сессия и роль (middleware? per-route helper `requireRole('director')`?). Рекомендую: единый `lib/auth.ts` с `getSessionProfile()` + декларативная проверка роли в начале каждого handler'а; список «эндпоинт → роль» таблицей в BACKEND.md.
7. **Параметры ретраев и таймаутов AI-вызовов.** «Ретрай ×2 с backoff» — какой backoff, какой таймаут одного вызова Whisper/Claude? Рекомендую: timeout 30с на вызов, backoff 1с/3с, и «второй STT-провайдер в конфиге» (CONCEPT.md) оформить как `lib/stt.ts` с интерфейсом `transcribe(audio): Promise<...>` и env `STT_PROVIDER=whisper|deepgram` — иначе обещанный fallback-провайдер потребует переписывания.
8. **Refresh mv_pulse_summary «по триггерной функции»** (DATABASE.md) — `refresh materialized view concurrently` из триггера = долгие блокировки в чужой транзакции. Рекомендую: на 45 человек mv вообще преждевременна — обычные view поверх индексов; если всё же mv, refresh только по pg_cron (каждую минуту), из триггеров не дёргать.
9. **Что видит директор про отложенные задачи до отправки** и можно ли отменить? Рекомендую: статус `scheduled` виден автору в «Мои отправленные», отмена = delete (задача ещё никому не доставлена).
10. **push_subscriptions без company_id** — нарушает собственное правило DATABASE.md «везде company_id not null» и ломает RLS-паттерн «фильтр по company_id». Рекомендую добавить company_id (денормализация от user — приемлема) либо явно задокументировать исключение: «доступ только service role, RLS deny all».

## Противоречия между документами

1. **Telegram-триггер:** BACKEND.md §2 «если нет активных подписок» ↔ CONCEPT.md §8 «китайские Android убивают service worker... Telegram-fallback обязателен» + «индикатор недоставки» — второе требует эскалации по факту непринятия, первое её исключает (подписка есть → fallback молчит).
2. **rule_code:** BACKEND.md §3 «unique-ключ (task_id, rule_code)» ↔ DATABASE.md point_transactions — колонки нет.
3. **ai_logs:** BACKEND.md §7 «логировать в таблицу ai_logs» ↔ DATABASE.md — таблица не определена, хотя «единственный источник правды по схеме» строится по DATABASE.md.
4. **Статус отложенных:** DATABASE.md pg_cron №3 «status is null/draft» ↔ DATABASE.md enum статусов (нет draft, поле not null по смыслу) и CLAUDE.md «enum, не расширять без причины».
5. **shop_final:** DATABASE.md enum содержит `shop_final`, но тут же «выдача → hold остаётся финальным (или пара release+final — выбери один паттерн)» — док одновременно вводит значение и сомневается, нужно ли оно. Решение переложено на агента; фиксирую: hold-остаётся-финальным, `shop_final` из enum убрать.
6. **company_id везде:** DATABASE.md «Общие правила: везде company_id not null» ↔ там же push_subscriptions без company_id.
7. **Сроки MVP:** CONCEPT.md §7 «MVP — 3 нед» ↔ PLAN_12_WEEKS «Недели 1–4: MVP». Мелочь, но агент-планировщик споткнётся.
8. **Индикатор недоставки:** PLAN неделя 2 ставит его в скоуп ↔ BACKEND.md не содержит ни таблицы статусов доставки, ни эндпоинта для него — фича недели 2 не имеет бэкенд-спецификации.

## Улучшения

- **[high] Outbox-паттерн для всех side-эффектов confirm.** Пуши, Telegram, эффекты — из notification_deliveries (см. критич. №3), а не из веера триггеров: одна точка ретраев и наблюдаемости.
- **[high] Наблюдаемость:** Sentry (route handlers + Edge Functions) и алерт на рост `failed` в notification_deliveries / `ok=false` в ai_logs. Соло-разработчик без алертов узнает о падении пушей от директора — худший канал.
- **[mid] Токены и стоимость в ai_logs** (input/output tokens, цена) — бюджет AI-вызовов станет виден к неделе 5, до сюрприза в биллинге.
- **[mid] Чистка push_subscriptions:** BACKEND.md упоминает 410; добавить 404 и NotRegistered, плюс еженедельный cron-свип подписок с N подряд ошибок.
- **[mid] `/api/voice/query` — стримить ответ** (Vercel AI SDK и так в плане недели 7) и жёстко ограничить `max_tokens`; tool-обёртки выполнять под RLS-контекстом директора (anon client + JWT), а не service role — иначе один prompt-injection в транскрипте читает всю БД.
- **[mid] Идемпотентность recurrence-runner:** сдвигать next_run_at и создавать задачу в одной SQL-функции (`update ... returning` + insert), иначе перекрытие двух прогонов cron создаст дубль.
- **[low] Healthcheck для ТВ:** `/api/health` + heartbeat-строка от киоска, чтобы «ТВ завис» замечался не глазами.
- **[low] Хранение webm+opus:** зафиксировать нормализацию имени/расширения файла для Whisper (Safari отдаёт mp4/m4a) — иначе редкие 400 от OpenAI при детекте формата.

## Вопросы владельцу продукта

1. Через сколько минут молчания сотрудника дублировать уведомление в Telegram (и дублировать ли всегда или только при недоставке push)?
2. «Марат не получил» — это «push не доставлен» или «задачу не открыл/не принял за N минут»? Каков N для красного индикатора у директора?
3. Аудио задач: слушать может только адресат и директор, или менеджер поддерева тоже? Срок хранения голосовых (Storage растёт бесконечно — храним всё или чистим через 6/12 мес)?
4. Повторное `done` после rework — начислять ли бонус «в срок» второй раз? (Предлагаю нет, но это правило мотивации.)
5. Отложенную задачу директор может отозвать до отправки — нужно ли это в MVP-скоупе итерации 4 или бэклог (в CONCEPT отзыв задач уже в бэклоге, но отложенные — особый случай: они ещё не доставлены)?
6. Гостевой режим ТВ — по умолчанию включён всегда, или обычный режим в кабинете допустим постоянно? Кто переключает?
7. Месячный бюджет на AI-API (Whisper+Claude) — от него калибруются rate limit'ы и выбор ретраев.

## Чего не хватает в доках для агентной разработки

1. **API-контракты по каждому эндпоинту:** request/response схемы (zod), коды ошибок, формат ошибки (`{error: {code, message_ru}}`), таблица «эндпоинт → роль → rate limit». Сейчас описания на уровне абзаца.
2. **Спецификация SQL-функций (RPC):** сигнатуры `confirm_voice_batch`, `create_shop_order`, `cancel_shop_order`, `apply_auto_rule` — раз транзакции только через них (критич. №1), их контракт и есть контракт бэкенда.
3. **Схемы недостающих таблиц:** ai_logs, ingest_batches (идемпотентность), notification_deliveries — в DATABASE.md, с RLS.
4. **Фикстуры парсера:** 30–50 реальных русских/смешанных фраз (те же, что для СТТ-гейта недели 1) + эталонный JSON к каждой — это и тест-сьют парсера, и few-shot-банк. Без них «дорабатывать промпт на реальных фразах» неисполнимо агентом.
5. **State-machine задач формально:** таблица переходов «кто → из какого статуса → в какой» (сотрудник не может sent→done, директор не может accepted→done минуя pending_review и т.д.) — сейчас переходы размазаны по трём докам.
6. **Env-матрица:** полный список переменных (включая недостающие: `TELEGRAM_WEBHOOK_SECRET`, `INTERNAL_FN_SECRET`, `DEEPGRAM_API_KEY`, `CRON_SECRET`) × среды dev/prod × где живут (Vercel / Supabase secrets).
7. **Конвенция путей Storage** и текст политик бакетов (см. дыру №5).
8. **Сценарии отказов таблицей:** «Whisper 5xx / Claude невалидный JSON / push 410 / pg_net timeout / двойной confirm» → ожидаемое поведение системы и пользователя. §7 BACKEND.md покрывает 2 случая из ~10.
