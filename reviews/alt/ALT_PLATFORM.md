# Альтернативы: Архитектор платформы доставки

## Постановка: как я понял задачу своей области из брифа

Мне нужно выбрать **форму доставки продукта на телефоны** для трёх очень разных ролей:

1. **Сотрудник (~45 человек, потом сотни в SaaS)** — личные телефоны без MDM, много бюджетных Android (Xiaomi/Redmi), встречается **Huawei без Google-сервисов**, часть iPhone. Ключевые требования: тривиальная установка (очный онбординг за 2 минуты), **гарантированная доставка уведомлений** («не увидел поручение» = провал), работа при плохом интернете на объектах (действия не теряются → нужна оффлайн-очередь), плавная геймификация на слабом железе.
2. **Директор** — один пользователь, требователен к полировке (эталон Kaspi/Telegram), главный KPI — скорость «голос → карточка на подтверждении», плюс пульт управления ТВ и голосовые вопросы к данным.
3. **ТВ-экран** — киоск в кабинете, живая лента, управляется с телефона директора.

Ограничения проекта: один разработчик, пишущий ИИ-агентами, 12 недель до полного развёртывания, пилот на 5 людях через 4–5 недель, облачный бюджет — десятки $/мес, разовые — сотни. Закон РК о персональных данных, риск региональных блокировок мессенджеров.

Критически важное следствие из брифа, которое сузит выбор заранее: **дистрибуция нативного бинарника на iPhone без сторов и без MDM для компании в 45 человек практически закрыта Apple-ом** (разбор ниже), а **Huawei без GMS ломает стандартный push-канал FCM**. То есть «идеального» нативного канала уведомлений на весь зоопарк устройств не существует — придётся строить доставку как **многоканальную систему с подтверждением получения**, а не как «один push-провайдер».

## Кандидат A — PWA (веб-приложение с установкой на домашний экран)

**Суть.** Одно веб-приложение (любой современный фреймворк), Service Worker, оффлайн-кэш и очередь действий (IndexedDB + Background Sync/ретраи), Web Push (VAPID), установка «На главный экран». Один код на все роли (сотрудник, директор, ТВ — просто разные роуты одного приложения).

**Сильные стороны именно для этих условий:**
- **Одна кодовая база = один разработчик реально успевает.** Нет второго стека, нет сборок под две ОС, нет ревью сторов. Деплой = обычный веб-деплой, фикс бага доезжает до всех телефонов мгновенно — для соло-сопровождения после запуска это огромно.
- **Онбординг за 2 минуты выполним**: открыть ссылку → «Добавить на экран» → разрешить уведомления. Очный формат снимает главную слабость PWA (пользователь сам не догадается установить) — здесь установку делает админ руками.
- **Оффлайн-очередь действий** («принял», отчёт с фото) — Service Worker + IndexedDB решают это штатно; фото кладём в очередь и дозаливаем при появлении сети. Это ровно требование «действия не теряются».
- **ТВ-режим бесплатно**: тот же URL в киоск-браузере на любой Android-приставке за ~$30–50. Никакой отдельной платформы.
- **Медиа-конвейер директора**: MediaRecorder для записи голоса в браузере работает и на iOS Safari (с 14.3+), и на Android — голосовой ввод не требует натива.
- **Huawei без GMS частично закрывается**: Web Push в Chrome на Android идёт через FCM и на Huawei **не работает**, но Firefox (движок Mozilla autopush, без GMS) и родной Huawei Browser с их push-стеком дают обходные пути; в худшем случае — fallback-канал (см. риск ниже).
- Анимации: современный веб (CSS transforms/WAAPI/канвас) на Redmi среднего уровня тянет «полёт карточки» при дисциплине разработки (только transform/opacity, без layout thrash). Это вопрос аккуратности, не платформы.

**Слабые стороны / риски:**
- **iOS push — главный риск.** Web Push на iOS работает **только с 16.4+ и только после установки на домашний экран**; надёжность доставки хуже нативной (реже, но случаются «молчаливые» пропуски), и пользователь может удалить иконку — подписка умирает тихо. На старых iPhone (< iOS 16.4) push-а нет вообще. Вердикт: **PWA-push нельзя делать единственным каналом уведомлений на iOS**.
- Android-вендоры (особенно Xiaomi/MIUI и Huawei) агрессивно убивают фоновые процессы; для PWA это менее болезненно, чем для приложения (push доставляет системный браузер), но «100% доставки» не гарантирует никто.
- Нет значка-бейджа/полноценных нотификационных фич на части устройств; нет доступа к нативным API (не нужны по брифу — контакты/BLE не требуются).
- iOS-PWA «полировка Kaspi» достижима, но требует ручной возни (safe areas, отсутствие bounce, standalone-режим) — ИИ-агенты это делают, но нужен явный чек-лист.

**Влияние на 12 недель соло + ИИ-агенты:** максимально благоприятное. Веб — среда, где качество генерации кода ИИ-агентами наивысшее (TypeScript/React — самый большой обучающий корпус), нет циклов «собрать → подписать → раздать». Пилот на 5 людях через 4 недели реалистичен.

**Стоимость:** хостинг — $0–20/мес (Vercel/Cloudflare и т.п.), Web Push (VAPID) — бесплатен, ТВ-приставка — $30–50 разово. Никаких $99/год Apple.

## Кандидат B — Нативная кроссплатформа (React Native/Expo или Flutter)

**Суть.** Одно приложение под iOS и Android, нативные push (APNs/FCM), нативные анимации.

**Сильные стороны:**
- **Лучшие в классе уведомления на iOS**: APNs — единственный по-настоящему надёжный push-канал на iPhone. Плюс нативный бейдж, критические алерты, звуки.
- Нативная плавность анимаций на слабом железе (Flutter особенно), нативная запись аудио, фоновая дозагрузка фото надёжнее.
- Expo (EAS) сильно снижает боль сборки для соло-разработчика; ИИ-агенты пишут RN/Expo хорошо (React-экосистема), Flutter — тоже прилично, но корпус меньше и Dart дальше от остального стека (бэкенд/веб всё равно будет на TS).

**Слабые стороны / риски — и это дисквалифsiцирующий блок:**
- **Дистрибуция на iOS без сторов и без MDM фактически невозможна для этой компании.** Разбор честно, по пунктам:
  - *Ad Hoc*: до 100 устройств/год, нужно собирать UDID каждого личного iPhone, профиль истекает через год, добавление устройства — пересборка. Для личных телефонов сотрудников — унизительная процедура, «2 минуты онбординга» не выйдет.
  - *Apple Developer Enterprise Program*: формально существует, но требует **100+ сотрудников**, строгую проверку и запрещает установку на устройства не-сотрудников. Компания в 45 человек **не пройдёт**.
  - *TestFlight*: реально рабочая лазейка (до 10 000 тестеров), но внешние тестеры требуют бета-ревью Apple, сборки **протухают через 90 дней** (сотрудник в отпуске вернулся — приложение не открывается), и это нарушение духа правил для продакшн-использования: Apple может прикрыть. Для SaaS-горизонта — несерьёзный фундамент.
  - *App Store как «внутреннее» приложение*: гайдлайн 3.2 требует, чтобы бизнес-приложения для сотрудников шли через Apple Business Manager / Custom Apps — а это снова MDM-подобная инфраструктура и managed Apple ID, чего нет.
  - Итог: **легальный устойчивый путь на iPhone — только App Store с ревью**, а это +1–2 недели на первый релиз, задержки на каждый фикс, аккаунт $99/год, и риск реджектов у соло-разработчика в самый горячий момент.
- **Huawei без GMS**: FCM не работает; нужен отдельный интеграционный слой HMS Push Kit (AppGallery) или свой канал — ещё одна платёжка и ветка кода.
- Двойная стоимость сопровождения: каждый фикс = сборка, подпись, ревью, ожидание обновления у пользователей. Для одного человека после запуска — постоянный налог.
- 12 недель: настройка EAS/подписей/сторов легко съедает 2–3 недели чистыми. Пилот через 4 недели — на грани срыва.

**Стоимость:** Apple Developer $99/год, Google Play $25 разово, EAS Build ~$0–19/мес (лимиты бесплатного тарифа малы), суммарно терпимо, но главный расход — время.

**Вердикт по B:** как *единственная* форма — нет. Как **возможный второй этап** (тонкая нативная оболочка вокруг того же веба ради APNs-push, опубликованная в сторах на 8–12 неделе) — да, это осмысленный путь эволюции.

## Кандидат C — Telegram Mini App + бот

**Суть.** Бот — канал уведомлений и авторизации; Mini App (WebApp внутри Telegram) — весь UI. Компания уже живёт в Telegram.

**Сильные стороны — их больше, чем принято думать:**
- **Уведомления решены идеально и бесплатно.** Сообщение бота — это пуш Telegram, который **доставляется на Huawei без GMS, на старых iPhone, на MIUI** — Telegram сам пробил все вендорские ограничения, у сотрудников он уже разрешён и не убивается системой. Это единственный кандидат, где «не увидел поручение» почти исключено технически. Плюс сообщение бота само по себе — карточка поручения с кнопками «Принял / Уточнить / Не могу» (inline keyboard) — сотруднику можно вообще не открывать Mini App для базового ответа.
- **Установка = нуль.** Онбординг: сотрудник сканирует QR → нажимает Start → авторизован (initData даёт подписанную личность). 30 секунд, не 2 минуты.
- Авторизация бесплатна и беспарольна: телефон уже привязан к Telegram-аккаунту.
- ИИ-агенты отлично пишут и ботов (grammY/aiogram), и Mini Apps (это обычный веб).
- Голосовые директора можно принимать прямо voice-сообщением боту — привычный жест, ноль UI.

**Слабые стороны / риски — тоже серьёзные:**
- **Оффлайн почти отсутствует.** Mini App — это webview, который Telegram загружает по сети; Service Worker-кэширование внутри WebApp ненадёжно и не специфицировано, CloudStorage API — маленькое key-value (лимиты порядка тысячи ключей), Background Sync недоступен. На стройке без сети сотрудник **не откроет** карточку и не поставит отчёт в очередь. Для требования «действия не теряются» это прямое противоречие. Частично лечится дублированием через кнопки в самом сообщении бота (Telegram сам доставит нажатие при появлении сети), но отчёт с фото офлайн — нет.
- **Платформенный риск.** В регионе мессенджеры периодически замедляют/блокируют (кейсы РФ 2018, Казахстан — отключения интернета и мессенджеров в январе 2022). Вся операционка компании, завязанная на доступность Telegram, — единая точка отказа, которой ты не управляешь. Плюс Telegram может менять правила ботов/Mini Apps в одностороннем порядке.
- **Полировка ограничена контейнером**: свой сплэш, жесты, полноэкранность, тонкая анимация — всё в рамках того, что разрешает WebApp API; «ощущение Kaspi» упирается в шапку Telegram над твоим интерфейсом. Fullscreen-режим для Mini Apps появился, но контроль всё равно не твой.
- ТВ-режим и десктопный сценарий директора — вне Telegram всё равно нужен обычный веб.
- Персональные данные по закону РК: данные пролетают через серверы Telegram (тексты поручений, имена) — для внутреннего употребления обычно приемлемо, но для SaaS-продажи другим компаниям станет вопросом в анкетах безопасности.
- SaaS-горизонт: «наш продукт живёт внутри Telegram» — слабая позиция для продажи (не все компании СНГ сидят в TG; WhatsApp-компании отпадают).

**Влияние на срок:** самый быстрый путь к пилоту (бот с карточками — неделя работы). Но продукт упирается в потолок оффлайна и полировки к неделям 6–8.

**Стоимость:** $0/мес за доставку и авторизацию. Хостинг бота копеечный.

## Кандидат D — Гибрид: PWA-ядро + Telegram-бот как канал доставки (директору и сотруднику — одно веб-ядро, ТВ — тот же веб)

**Суть.** Продукт — **одно PWA** (роуты сотрудника, директора, ТВ). **Уведомления — двухканальные с эскалацией**: Web Push как основной канал + **Telegram-бот как гарантированный fallback и квитанция**. Каждое поручение имеет цикл подтверждения доставки: нет реакции на Web Push за N минут → бот шлёт сообщение с deep-link в PWA (и inline-кнопкой «Принял» прямо в чате). Telegram здесь — **транспорт, а не платформа**: UI, данные и оффлайн живут в PWA.

**Сильные стороны:**
- Закрывает **каждое** жёсткое условие ровно тем инструментом, который в нём силён: оффлайн-очередь и полировка — PWA; гарантированная доставка на весь зоопарк (Huawei, старые iPhone, MIUI) — Telegram; ТВ — тот же веб.
- Риск блокировки Telegram деградирует в неудобство, а не в катастрофу: основной канал (Web Push + открытая PWA) продолжает работать, Telegram — лишь один из каналов. Обратное тоже верно: молчащий iOS-web-push страхуется ботом.
- Один стек, одна кодовая база, один деплой — сопровождаемо одним человеком; бот — это ~сотни строк, не вторая платформа.
- SaaS-готовность: канал доставки — плагин (Telegram сегодня, WhatsApp Business API или SMS завтра для других компаний), ядро не меняется.
- Архитектурно навязывает правильную вещь: **таблицу доставок с состояниями** (отправлено → доставлено → увидено → отвечено) и эскалацией. Это же даёт директору ответ «кто не отчитался» бесплатно.

**Слабые стороны / риски:**
- Два канала = логика дедупликации и эскалации, которую надо спроектировать (иначе сотрудник получает двойные уведомления и раздражается). Это +3–5 дней работы.
- Всё ещё нет APNs-надёжности на iOS «из коробки» — но связка «web push + telegram» перекрывает провал каждого канала по отдельности.
- Бот требует, чтобы Telegram был у всех (по брифу — есть).

**Влияние на срок:** пилот через 4 недели достижим (недели 1–3 — PWA-ядро и голосовой конвейер, неделя 4 — бот-fallback). ИИ-агенты сильны в обеих частях (веб + бот-фреймворки).

**Стоимость:** как у A: $0–20/мес, ТВ-приставка $30–50 разово, Telegram — $0.

## Отдельный вопрос: обязана ли это быть одна платформа для директора и сотрудника?

**Одна кодовая база — да; один UX — нет.** Требования действительно кардинально разные: директору нужен «кокпит» (запись → подтверждение → пульс → пульт ТВ), сотруднику — «карточка и три кнопки». Но это различие **продуктовое, а не платформенное**: оно решается разными роутами/оболочками внутри одного веб-приложения, а не разными технологиями. Разводить их по платформам (директору натив, сотрудникам PWA/TG) — значит утроить работу одного человека ради нулевой пользы: у директора один известный телефон, его устройство можно просто **подобрать под продукт** (если у него iPhone — установить PWA и включить уведомления при личной настройке; его-то онбординг точно очный). Единственный случай, когда директору оправдан отдельный нативный клиент, — если запись голоса/пуши на его конкретном iPhone окажутся недостаточно надёжными; тогда **одна** тонкая нативная оболочка для **одного** пользователя (даже через Ad Hoc/TestFlight — для одного устройства это допустимо) — дешёвая страховка, не меняющая архитектуру.

## Мой выбор и почему

**Кандидат D: PWA-ядро + Telegram-бот как гарантированный канал доставки и fallback-интерфейс ответа.**

- **Скорость до пилота:** веб — самый короткий путь; никаких сторов, подписей, ревью. Пилот на 5 людях к неделе 4–5 реалистичен, и каждый фикс доезжает мгновенно — критично, когда первые недели пилота = поток багов.
- **Сопровождение одним человеком:** один стек (TypeScript насквозь), один деплой, нет «протухающих» сборок и ежегодных сертификатов. «Скучно и надёжно»: веб + бот — две самые зрелые, самые предсказуемые технологии из всех рассмотренных.
- **Качество генерации ИИ-агентами:** TypeScript/React/Node — лучший в мире корпус для кодогенерации; бот-фреймворки тоже. Flutter/Dart и нативные подписи iOS — заметно хуже поддерживаемая агентами территория (много состояния вне кода: сертификаты, профили, консоли).
- **Главный риск продукта — доставка уведомлений — закрыт не верой в один канал, а системой** с квитанциями и эскалацией. Это единственная честная конструкция при парке «Huawei без GMS + старые iPhone + MIUI».
- Эволюция заложена: к неделям 8–12 (или после запуска) можно завернуть то же веб-ядро в тонкую store-оболочку (Capacitor/Expo WebView + APNs) — если практика пилота покажет, что iOS-пуши недотягивают.

## Что бы заставило меня передумать (условия-триггеры)

1. **Пилот покажет реальную потерю Web Push на iPhone сотрудников** (> ~5% «не увидел» при работающем боте-fallback — терпимо; если и бот игнорируют из-за мьюта чата — нужен натив с критическими алертами) → добавить store-оболочку с APNs (переход к B как надстройке, не переписывание).
2. **Доля iPhone < iOS 16.4 среди сотрудников окажется заметной** (нет Web Push вообще) → усилить роль Telegram-канала до основного для этих устройств или ускорить store-оболочку.
3. **Блокировка/деградация Telegram в РК** → fallback переезжает на SMS-шлюз (~$0.01–0.03/SMS, при 45 сотрудниках копейки) или WhatsApp Business API; PWA-ядро не трогаем — это и есть причина, почему Telegram не должен быть платформой.
4. **SaaS-клиенты потребуют «приложение в сторе» как признак серьёзности** (частая иррациональная, но реальная закупочная норма) → та же оболочка вокруг того же ядра.
5. **Если бы компания была 100% Android без Huawei** — чистая PWA (A) без бота была бы достаточна; наличие iPhone + Huawei в одном парке — именно то, что делает гибрид обязательным.
6. **Если бы дедлайн был 4 недели на всё** — выбрал бы C (чистый Telegram): самый быстрый минимум, сознательно пожертвовав оффлайном и полировкой.

## Неочевидное: что все обычно упускают в подобных продуктах

1. **Push — это транспорт, а не гарантия; проектировать надо «подтверждённую доставку».** Все спорят «PWA vs натив» про *отправку* уведомлений, хотя провал продукта наступает на *приёме*. Правильная единица проектирования — жизненный цикл доставки (sent → delivered → seen → acted) с эскалацией по таймауту и экраном директора «кому не доставлено». Как только это спроектировано, выбор push-технологии становится заменяемой деталью.
2. **Тихая смерть подписки.** iOS-PWA удалили с экрана, MIUI отозвал разрешение, сотрудник сменил телефон — подписка умирает без единого сигнала. Нужен фоновый health-check подписок (еженедельный тихий пинг + отчёт «у кого канал мёртв») — этого не делает почти никто, а для «не увидел = провал» это обязательный контур.
3. **Онбординг очный — это суперсила, а не костыль.** 90% слабостей PWA (никто сам не устанавливает, не даёт разрешение на пуши) существуют только в самообслуживании. Здесь установку делает админ за 2 минуты — значит, надо сделать **админский чек-лист онбординга внутри продукта** (экран «настрой телефон новичка»: установить, разрешить пуши, отправить тестовый пуш, увидеть подтверждение). Это фича, а её никогда не закладывают в скоуп. Для SaaS она же станет киллер-фичей внедрения.
4. **Бюджетный Android — это не про FPS анимаций, а про память и «возврат в приложение».** MIUI выгружает вкладку/приложение агрессивно; сотрудник открывает продукт по пушу 10 раз в день с холодного старта. Оптимизировать надо время холодного старта до интерактивной карточки (< 2–3 сек на Redmi), а не красоту 60fps. Все меряют анимации, никто не меряет cold start по тапу на уведомление.
5. **Фото-отчёт со стройки — главный убийца оффлайн-очереди.** Очередь из JSON-действий делают все; очередь из 8-мегабайтных фото при EDGE-соединении — никто. Нужны клиентское сжатие до отправки и resumable-загрузка, иначе «действия не теряются» останется правдой только для кнопок.
6. **Двойные уведомления бесят сильнее, чем отсутствующие — узнаёшь об этом поздно.** Мультиканальность без дедупликации приведёт к тому, что сотрудники замьютят бота — и убьют fallback-канал своими руками. Правило «второй канал стреляет только если первый не подтвердил доставку за N минут» должно быть в архитектуре с первого дня.
