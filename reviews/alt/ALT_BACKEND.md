# Альтернативы: Senior Backend/Infra

> Слепое исследование: только продуктовый бриф, без знания о принятых в проекте решениях.
> Дата: 2026-08-14. Цены и юридические факты проверены веб-поиском на дату отчёта.

## Постановка: как я понял задачу своей области из брифа

Нужен бэкенд для внутренней платформы на ~45 человек с горизонтом SaaS по СНГ, который обеспечивает:

1. **Голосовой конвейер**: загрузка аудио с телефона директора (шумная запись, минуты длиной) → STT (русский + казахские имена) → LLM-парсинг в структурированные объекты → экран подтверждения → рассылка адресатам. Латентность «голос → карточка» — главный конкурентный параметр, значит конвейер должен быть асинхронным, но быстрым, с надёжным сохранением исходного аудио (плохая связь, ретраи).
2. **Транзакционные данные**: задачи со статусами, очки (по-хорошему — append-only журнал), магазин, рейтинг, лента. Классическая реляционная модель с авторизацией «сотрудник видит только своё».
3. **Realtime**: живая лента на ТВ-экране, живой дашборд директора, обновление карточек у сотрудников без перезагрузки.
4. **Гарантированная доставка уведомлений** как отдельная подсистема с эскалацией: «не увидел поручение = провал».
5. **Офлайн-устойчивость** действий сотрудника на стройплощадке: очередь исходящих действий на клиенте + идемпотентный приём на сервере.
6. **Фоновые механики**: cron (напоминания, эскалации, дедлайны, streak), очередь (STT/LLM-джобы, рассылка), вебхуки (Telegram-бот).
7. **Юрисдикция данных**: закон РК № 94-V — и это не формальность, разбираю отдельно.

Ограничения, которые давят сильнее всего: **один разработчик, 12 недель, пилот через 4–5 недель, пишет ИИ-агентами, десятки долларов в месяц**. Значит, критерий №1 — не «архитектурная красота», а суммарное количество инфраструктурных обязанностей, которые я НЕ беру на себя, и качество генерации кода агентами для выбранной технологии. «Скучно и надёжно» здесь — прямой аргумент.

Отдельно фиксирую: **PWA почти безальтернативна на клиенте** (личные телефоны, Huawei без GMS, очный онбординг за 2 минуты, без MDM и сторов) — это ограничивает выбор бэкенда тем, у кого нормальный Web Push (VAPID) и HTTP/WebSocket API, а не только нативные SDK.

## Кандидат A: Supabase (облачный, managed)

**Суть.** Postgres как ядро + слой сервисов: Auth (email/OTP/magic link), Row Level Security как модель авторизации, Realtime (изменения таблиц по WebSocket), Storage (S3-совместимый, для аудио и фото-отчётов), Edge Functions (Deno, для вебхуков и AI-вызовов), pg_cron. Всё в одном проекте, деплой фронта отдельно (Vercel/Cloudflare).

**Сильные стороны именно для этих условий.**
- **Реляционная модель — родная.** Задачи/статусы/очки/магазин — это транзакции, join'ы и constraint'ы. Append-only журнал очков с `SUM()` и заморозкой при покупке — это Postgres-задача, а не документная. Не надо изобретать консистентность поверх NoSQL.
- **RLS решает «сотрудник видит только своё» декларативно** — одна политика вместо проверок в каждом эндпоинте. Для соло-разработчика это меньше кода = меньше дыр.
- **Realtime из коробки** закрывает ТВ-экран, дашборд и живые карточки без своего WebSocket-сервера — а свой WebSocket-сервер это именно та вещь, которую соло-человек потом сопровождает ночами.
- **Качество генерации ИИ-агентами — лучшее в классе.** Supabase + Next.js — вероятно, самая представленная связка в обучающих данных LLM после «просто Express». Агенты знают идиомы RLS, миграций, supabase-js, типогенерации. Это напрямую конвертируется в скорость 12-недельного плана.
- **Миграции = SQL-файлы**, локальная разработка через `supabase start` (Docker) — dev/prod для одного человека получается почти бесплатно.
- **Нет lock-in по данным**: под капотом обычный Postgres, `pg_dump` уносится куда угодно, включая VPS в РК (важно для юридической траектории, см. ниже).
- **Storage + возобновляемые загрузки** — для аудио с плохой связи это критично, не надо писать свой upload-сервис.

**Слабые стороны / риски.**
- **Нет региона в РК** (ближайшие — Франкфурт/Сингапур/Мумбаи). По ст. 12 закона № 94-V база персональных данных должна находиться на территории РК — облачный Supabase формально не проходит. Для внутреннего пилота на 5 людях с письменными согласиями (ст. 16 о трансграничной передаче допускает передачу при согласии субъекта) — приемлемый управляемый риск; для продажи SaaS другим компаниям РК — нет.
- **Edge Functions (Deno) — худшая часть платформы**: лимиты wall-clock (~150–400 с), холодные старты, отладка хуже Node. Whisper на 3-минутном аудио влезает, но конвейер «STT → LLM → фан-аут уведомлений» на грани. Митигируется выносом тяжёлой обработки в Next.js route handlers / фоновые джобы, но это надо заложить в архитектуру сразу.
- **Realtime при обрывах связи требует дисциплины**: reconnect + refetch надо писать самому, иначе на стройке будут «зависшие» экраны.
- **Ценовые сюрпризы при росте** (egress, compute add-ons) — на 45 людях не проявятся, на SaaS — считать.

**Влияние на 12-недельный срок.** Максимально положительное: недели 1–2 — схема+RLS+auth, к неделе 4–5 пилот реалистичен. Инфраструктурного кода почти нет — агенты пишут продуктовый.

**Стоимость.** Free-тир хватит на пилот; Pro — **$25/мес** (8 GB БД, 100 GB storage, 500 realtime-соединений, 2 млн вызовов функций) — с запасом на всю компанию. Разово — $0. Плюс Vercel Free/Pro ($0–20).

## Кандидат B: Firebase (Firestore + FCM + Cloud Functions)

**Суть.** Google-экосистема: документная Firestore с клиентскими SDK и офлайн-кэшем, FCM для push, Cloud Functions, Hosting.

**Сильные стороны.**
- Лучший в индустрии **клиентский офлайн-кэш** (Firestore SDK) — ровно та боль «действия не должны теряться», решённая за меня.
- FCM — эталон дешёвого push для нативного Android.
- Зрелость, обучающих материалов море, агенты пишут уверенно.
- Щедрый бесплатный тир — на 45 человек почти наверняка $0–10/мес.

**Слабые стороны / риски — здесь они фатальные.**
- **Huawei без GMS — прямое попадание в наш парк устройств.** Нативный FCM на таких телефонах не работает вообще; в PWA-варианте push идёт через браузер, но фирменный Huawei Browser Web Push не поддерживает — то есть флагманская гарантия доставки Firebase рушится именно на нашем худшем устройстве. Нужен HMS Push Kit (вторая интеграция) или... Telegram-фолбэк — но тогда преимущество FCM обнуляется.
- **Firestore — документная БД, а продукт реляционный.** Рейтинг по SUM транзакций очков, «кто не отчитался» (join задач и отчётов), заморозка очков — всё это в Firestore превращается в денормализацию, клиентские агрегаты и облачные функции-триггеры, поддерживающие счётчики. Это классический источник рассинхрона, и именно голосовые вопросы директора («что там по Казхрому?») требуют произвольных выборок, которые в Firestore мучительны — а в SQL это один запрос, который LLM ещё и сгенерирует сам.
- **Жёсткий vendor lock-in**: данные из Firestore не «pg_dump'нешь» на VPS в РК. Юридическая траектория (данные в РК) закрыта навсегда.
- Данные — в дата-центрах Google (US/EU), тот же вопрос ст. 12, но без пути миграции.
- Биллинг «оплата за чтения документов» с ТВ-экраном, поллящим ленту, — классический сценарий случайного счёта.

**Влияние на срок.** Старт быстрый, но недели 6–10 съест борьба с моделированием реляционных сценариев в документной БД и вторым push-каналом для Huawei.

**Стоимость.** ~$0–15/мес на этом масштабе. Дёшево, но цена не компенсирует архитектурное несоответствие.

## Кандидат C: Convex

**Суть.** Реактивный TypeScript-бэкенд: функции-запросы/мутации в TS, автоматическая реактивность на клиенте (подписки без ручного realtime-кода), встроенный планировщик и очереди, транзакционность.

**Сильные стороны.**
- **Реактивность по умолчанию** — ТВ-экран и живой дашборд получаются «бесплатно», это красивейшее совпадение с продуктом.
- Транзакционные мутации в TS — журнал очков делается корректно без SQL.
- Встроенные scheduled functions — cron/эскалации без внешнего крона.
- Один язык (TS) на всём стеке — агентам комфортно.

**Слабые стороны / риски.**
- **Молодая проприетарная платформа**: свой язык запросов вместо SQL, данные в облаке Convex (США), выгрузка возможна, но эквивалентного self-host пути с той же реактивностью нет (open-source вариант существует, но сопровождать его соло — отдельная работа). Юридическая траектория РК — плохая.
- **Представленность в обучающих данных LLM на порядок ниже**, чем у Postgres/Supabase: агенты чаще галлюцинируют API, меньше готовых паттернов auth/upload/push. Для разработчика, пишущего «руками ИИ-агентов», это прямой налог на каждый день.
- Файловое хранилище и работа с большими аудио — слабее и дороже специализированных.
- Произвольная аналитика («кто не отчитался за месяц») без SQL — писать руками кодом.
- Ценообразование по вызовам функций/пропускной способности — реактивный ТВ-экран 24/7 надо считать.

**Влияние на срок.** Первые 2 недели — быстрее всех (реактивность даром), дальше — замедление на всём, что вне «happy path» платформы, и на каждой галлюцинации агента.

**Стоимость.** Free-тир на пилот; Professional ~$25/мес.

## Кандидат D: PocketBase на VPS (в РК или Hetzner)

**Суть.** Один Go-бинарник: SQLite, auth, файлы, realtime (SSE), админка, JS-хуки/расширение на Go. Ставится на любой VPS за 10 минут.

**Сильные стороны.**
- **Единственный кандидат, тривиально дающий «данные физически в РК»**: VPS у PS.kz/hoster.kz — и ст. 12 закрыта буквально, без юридической эквилибристики. Для SaaS-продаж компаниям РК это станет козырем.
- Эксплуатационная простота для соло-человека — эталонная: один процесс, один файл БД, бэкап = копия файла (litestream — репликация почти даром). 45 пользователей для SQLite — ничто.
- $5–10/мес и полный контроль.

**Слабые стороны / риски.**
- **Авторизационная модель слабее RLS**: правила доступа — выражения в админке, сложные сценарии (директор видит всё, сотрудник — своё, ТВ — публичный срез, потом мультитенантность SaaS) быстро упираются в написание кастомных Go/JS-хуков — то есть в самосбор, только внутри чужого каркаса.
- Очередей и крона нет — свои горутины/хуки; конвейер STT→LLM с ретраями пишется руками.
- SSE-realtime проще и грубее (нет презенс-каналов, реконнекты руками).
- SQLite → Postgres миграция при росте SaaS — реальный проект, а не команда.
- **Представленность у LLM-агентов заметно ниже** Supabase/Firebase; расширение на Go — отдельный язык в стеке.
- Bus-factor проекта: по сути один мейнтейнер у самого PocketBase.

**Влияние на срок.** Пилот — реально к неделе 5, но недели 8–12 уйдут на руками написанные очереди, push-слой и правила доступа. Итог ближе к верхней границе срока.

**Стоимость.** VPS $5–15/мес (PS.kz ~5–8 тыс. тг/мес за адекватный VPS). Разово — $0.

## Кандидат E: Appwrite (self-hosted в РК или их облако)

**Суть.** Open-source BaaS «как Firebase»: коллекции (поверх MariaDB), auth, storage, functions, realtime; self-host через Docker Compose (~десяток контейнеров).

**Сильные стороны.**
- Self-host в РК возможен → ст. 12 закрывается, при этом функциональность шире PocketBase.
- Полный набор сервисов под одной крышей, приличные веб-SDK.

**Слабые стороны / риски.**
- **Худшее из двух миров для соло-эксплуатации**: это не один бинарник, а флот контейнеров (шлюз, воркеры функций, очереди, БД), который надо обновлять, мониторить и чинить одному человеку. Апгрейды между версиями исторически болезненны.
- Данные — документные коллекции поверх MariaDB, но **без прямого SQL** — та же реляционная боль, что у Firestore, без его офлайн-кэша.
- Представленность у агентов — средненькая; облако Appwrite — данные не в РК.

**Влияние на срок.** Неделя-две только на приручение self-host инсталляции; продуктовый код медленнее, чем на Supabase. Худший баланс из всех рассмотренных.

**Стоимость.** VPS покрупнее ($15–25/мес, 4–8 GB RAM) или облако от $15/мес.

## Кандидат F: «VPS + Postgres + свой API» (Hetzner или хостинг в РК)

**Суть.** Полный самосбор: VPS (Hetzner CX ~€5–10 или PS.kz), Docker Compose: Postgres + Node/TS API (Fastify/Nest либо Next.js standalone) + Caddy + воркер очереди (BullMQ/pg-boss) + MinIO/диск для файлов. Долгоживущий сервер, а не serverless.

**Сильные стороны.**
- **Абсолютный контроль и лучшая юридическая позиция**: сервер в РК — данные в РК, точка.
- **Долгоживущий процесс идеально ложится на нашу нагрузку**: очереди STT/LLM-джоб, cron эскалаций, вебхук Telegram-бота, стриминг/докачка аудио — всё это естественно в постоянном процессе и неестественно в serverless (таймауты, холодные старты, состояние). Честно скажу: по чистой архитектуре это самый правильный кандидат.
- Стоимость минимальна и предсказуема; Postgres — навсегда переносим.
- Агенты прекрасно пишут Fastify/Prisma/BullMQ — это мейнстрим.

**Слабые стороны / риски.**
- **Каждый «бесплатный» сервис BaaS здесь пишется и, главное, сопровождается**: auth (сессии, OTP), realtime (свой WebSocket + reconnect-логика), upload с докачкой, миграции, бэкапы, мониторинг, TLS, обновления ОС, fail2ban. По отдельности всё тривиально; суммарно это **2–3 недели чистого инфраструктурного кода до первой продуктовой фичи** — то есть пилот на неделе 4–5 превращается в пилот на неделе 7–8.
- Авторизация — императивные проверки в каждом эндпоинте: у соло-разработчика с агентами это самый вероятный источник дыры «сотрудник увидел чужое».
- Единственная машина = единственная точка отказа, и дежурный по ней — тот же один человек. Упавший ночью сервер — упавшие уведомления.

**Влияние на срок.** Главный риск всего проекта — сорвать пилот недели 4–5. Не рекомендую как старт, рекомендую как **пункт назначения** (см. выбор).

**Стоимость.** €5–15/мес VPS + $1–2 бэкапы. Разово — $0 (или сотни, если брать выделенный сервер в РК заранее — не нужно).

## Сквозные решения (независимо от кандидата)

**Serverless vs долгоживущий сервер.** Нагрузка продукта — не «миллион коротких запросов», а: минуты аудио, очереди AI-джоб, cron-эскалации, вебхуки бота, WebSocket. Это профиль **долгоживущего процесса**. Чистый serverless (Lambda-стиль) сюда ложится плохо. Компромисс, который я выбираю: managed-BaaS несёт БД/auth/realtime/storage, а «длинные» операции живут в Next.js route handlers (Vercel functions с лимитом до минут — Whisper влезает) + **pg_cron/pg-boss-подобная очередь в самой БД** (таблица jobs + cron-тик) вместо отдельного брокера. Отдельный Redis/RabbitMQ на этом масштабе — запрещаю сам себе: это лишний сервис на сопровождении.

**Доставка уведомлений как система, а не как «отправили push».** Это подсистема с состоянием:
1. Таблица `notifications` с жизненным циклом: `created → delivered(канал) → seen → acked` — доставка подтверждается фактом, а не отправкой.
2. **Ярус 1 — Telegram-бот**: компания уже живёт в Telegram; у бота ~100% доставка на любом устройстве, включая Huawei без GMS; онбординг — QR с deep-link за 30 секунд из тех самых «2 минут». Именно Telegram, а не push, должен быть контрактным каналом гарантии.
3. **Ярус 2 — Web Push (VAPID)** из PWA: быстрый нативный путь для Android/Chrome и iOS 16.4+ (после «на экран Домой»); на Huawei — честно считаем недоступным.
4. **Ярус 3 — SMS-эскалация** через локального провайдера (Mobizon/SMSC.kz, ~10–15 тг/SMS) только для критичного: «поручение не принято N часов». На 45 людях это сотни тенге в месяц.
5. Эскалация по cron: нет `seen` за X минут → следующий канал; нет `acked` за Y часов → директору в сводку «кто не увидел». Outbox-паттерн: запись о намерении отправки коммитится в той же транзакции, что и событие, воркер разгребает — иначе при падении между «записали задачу» и «отправили push» уведомление теряется молча.

**Офлайн сотрудника.** Клиентская очередь действий (IndexedDB) + идемпотентные мутации с client-generated UUID; сервер обязан переживать повторную доставку. Это дешевле и надёжнее, чем «синхронизация БД» в стиле Firestore.

**Деплой и среды для соло.** Две среды, не три: **local dev** (Docker-стек BaaS локально + сид-данные) и **prod**; staging для одного человека — театр. Миграции только файлами в git, применяются через CI (GitHub Actions) — никогда руками в прод-консоли. Preview-деплои фронта (Vercel) бесплатно дают «показать директору до релиза». Секреты — в env платформы; бэкап БД — ежедневный автоматический + еженедельная проверка восстановления (бэкап без теста восстановления — это молитва).

**Где живут данные по закону РК — и что это значит.** Ст. 12 закона № 94-V: база, содержащая персональные данные, должна храниться **на территории РК** (требование действует с 2016). Трансграничная передача (ст. 16) допускается, в частности, при согласии субъекта. Практическая стратегия трёх горизонтов:
- *Пилот (внутренний, 5–45 сотрудников):* облачный BaaS (Франкфурт) + письменные согласия сотрудников на обработку и трансграничную передачу (они и так нужны для публичного рейтинга!) + минимизация ПДн в облаке (ФИО, телефон, должность — без ИИН и лишнего). Риск низкий и осознанный.
- *SaaS для чужих компаний РК:* согласиями чужих сотрудников не отделаться на переговорах — вопрос «где данные?» станет блокером продаж. К этому моменту нужен хостинг в РК.
- *Мост между ними:* выбирать сейчас только те технологии, чей стек **переносим на VPS в РК** (Postgres — да; Firestore/Convex — нет). Аудио и фото — тоже персональные данные (голос, изображения), не только строки в БД.

## Мой выбор и почему

**Supabase (облако, Франкфурт) + Next.js на Vercel; очередь и cron — внутри Postgres (таблица jobs + pg_cron); Telegram-бот как гарантийный канал доставки; запланированный «выход» на VPS+Postgres в РК при переходе к SaaS.**

Почему именно так, по трём заданным осям:
- **Скорость до пилота.** Supabase убирает из 12 недель весь инфраструктурный слой (auth, realtime, storage, RLS) — недели 1–5 тратятся на продукт: голосовой конвейер, экран подтверждения, карточки, доставка. Ни один другой кандидат не даёт пилот на неделе 4–5 с таким запасом; самосбор (F) почти гарантированно его срывает.
- **Сопровождение одним человеком.** Managed Postgres с бэкапами, «нечему падать ночью» на моей стороне, миграции файлами, две среды. PocketBase близок по простоте, но перекладывает на меня очереди, push-слой и сложные правила доступа; Appwrite — наоборот, взваливает флот контейнеров.
- **Качество генерации ИИ-агентами.** Связка Next.js+Supabase+Postgres — самая «выученная» LLM-ами из всех кандидатов; SQL агенты пишут лучше, чем проприетарные query-языки (Convex) или денормализационные трюки (Firestore). Для разработчика, пишущего руками агентов, это множитель на весь срок.

Ключевая страховка выбора: **всё ценное лежит в переносимом Postgres**. Если Supabase подорожает, испортится или юридический вопрос обострится — `pg_dump` и переезд на кандидата F (VPS в РК), который я сознательно держу как «взрослую» конечную форму, а не как старт.

Firebase отклонён из-за Huawei-парка и документной модели под реляционный продукт; Convex — из-за проприетарности, юрисдикции без пути миграции и слабой представленности у агентов; PocketBase — достойный второй выбор, проигравший из-за самописных очередей/доступа и SQLite-потолка для SaaS; Appwrite — из-за эксплуатационной тяжести для одного человека.

## Что бы заставило меня передумать (условия-триггеры)

1. **Юрист/заказчик требует «данные в РК» с первого дня** (например, среди сотрудников госслужащие, или директор не готов подписывать согласия на трансграничную передачу) → PocketBase на VPS в РК для пилота, с миграцией на Postgres в РК к SaaS.
2. **Пилот показал, что Telegram-бот покрывает 100% сотрудников и им достаточно** → давление в сторону ещё более простого стека (кандидат D или даже «бот + PocketBase»), PWA-push можно отложить.
3. **SaaS взлетел: 5+ компаний-клиентов в РК** → немедленно исполнять «выход»: self-hosted Postgres-стек на VPS/выделенном сервере в РК (кандидат F), Supabase остаётся dev-средой или уходит совсем.
4. **Счёт Supabase стабильно выше ~$60–80/мес** на одной компании (egress от аудио/фото?) → аудио в отдельный S3-совместимый сторадж (или сразу переезд по п. 3).
5. **Realtime Supabase окажется хрупким на стройплощадочном интернете** (жалобы на «мёртвые» экраны) → перейти на модель «poll раз в 20–30 с + push-invalidation», это дешевле борьбы с WebSocket-реконнектами.
6. **Появился второй разработчик/деньги на DevOps** → аргумент «одному человеку нечего сопровождать» ослабевает, кандидат F становится доступен раньше.

## Неочевидное: что в этой области все обычно упускают в подобных продуктах

1. **Доставка — это состояние, а не событие.** Все строят «отправку уведомлений», почти никто — таблицу жизненного цикла `delivered/seen/acked` с эскалацией по cron и outbox-паттерном. А ведь флагманская фича директора «кто не увидел поручение?» — это буквально SELECT по этой таблице: подсистема гарантии доставки и аналитическая фича продукта — одно и то же.
2. **Аудио — тоже персональные данные.** Голос сотрудника и фото с объекта подпадают под закон РК так же, как ФИО в таблице. Планируя «данные в РК», все считают базу и забывают bucket с медиа — а он по объёму и есть 95% данных.
3. **Push ≠ гарантия по вине самих телефонов.** На бюджетных Xiaomi/Huawei агрессивные «оптимизаторы батареи» убивают и FCM, и Web Push независимо от вашего кода. Поэтому гарантийный канал в СНГ-компании — мессенджер, где пользователь и так живёт (Telegram), а push — лишь быстрый путь. Кто проектирует «push основной, Telegram фолбэк» — перепутал ярусы.
4. **Очередь в Postgres, а не рядом с ним.** Соло-разработчику брокер (Redis/Rabbit/SQS) не нужен: таблица jobs + `FOR UPDATE SKIP LOCKED` + cron-тик покрывают STT-конвейер и эскалации, живут в тех же бэкапах и транзакциях, что и данные. Каждый лишний stateful-сервис — это тот, кто разбудит вас в отпуске.
5. **Идемпотентность — фундамент офлайна.** «Не терять действия на плохой связи» решается не хитрой синхронизацией, а скучно: client-generated UUID на каждой мутации и сервер, спокойно принимающий дубли. Это надо заложить в API с первого эндпоинта — дорасти до этого потом почти невозможно.
6. **Согласия на рейтинг — продуктовая фича, а не бумажка.** Публичный рейтинг очков по закону РК требует согласия каждого — значит, экран «согласен участвовать в рейтинге» должен быть в онбординге с первого дня, и схема БД должна уметь «сотрудник без публичного рейтинга», иначе один отказавшийся ломает витрину.
7. **Самая дорогая минута конвейера — не STT и не LLM, а загрузка аудио с плохой связи.** Скорость «голос → карточка» решается возобновляемой загрузкой и параллельной отправкой чанков во время записи, а не выбором модели распознавания. Все меряют бенчмарки Whisper, никто — процент недозагруженных записей из машины директора.
